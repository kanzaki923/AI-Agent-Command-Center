# アーキテクチャ

構想は `concept.md`。この文書は「いまの実装がどういう形をしているか」と「守るべき契約」をまとめる。実装を変えたら同じコミットでここも直す。

## 1. 全体構成

```
apps/desktop      Tauri 2 + React UI（Core Daemon のクライアント）
packages/protocol ドメイン型・イベント型・Control API 契約（zod スキーマ）
packages/client   Control API の型付きクライアント（UI / CLI / テストが使う）
packages/daemon   Core Daemon（Node.js 22 常駐プロセス）
packages/cli      `acc` コマンド（Control API クライアント）
```

- pnpm workspace のモノレポ。内部パッケージは TS ソースを直接 export する（`exports` が `src/index.ts` を指す）。ビルドが必要なのは配布物（daemon バンドル、desktop）だけ。
- ランタイムは Node.js 22（Bun は Agent SDK 互換性・配布の検証が済むまで見送り）。
- 人間（UI / CLI）も LLM（Orchestrator / Worker）も、**同じ Control API ディスパッチャ**を通る。LLM 向けツールは API メソッド定義から自動生成し、Capability で絞り込む。

## 2. Core Daemon

### 2.1 起動と接続

- データディレクトリ：`ACC_HOME`（既定 `~/.acc`）。`acc.sqlite`、`config.json`（LiteLLM の URL / キーなど。リポジトリには置かない）、`worktrees/`、`daemon.json`（接続情報）。
- `127.0.0.1:47821`（`ACC_PORT` で変更）で待ち受け。HTTP `GET /health`（認証なし。`{ ok, service: "acc-daemon", pid, version, protocolVersion }`。ランチャーは `service` と `pid` で自分のデーモンか確かめる）、WebSocket `/ws?token=...`。
- 起動時にランダムトークンを生成し `daemon.json` に `{ port, token, pid, startedAt, version }` を書く（終了時に削除）。クライアントはこれを読んで接続する（同一ユーザー以外・ブラウザの任意ページからの操作を防ぐ）。WebSocket の upgrade は `Origin` も確かめ、デスクトップ（`tauri://localhost` / `http(s)://tauri.localhost`）とループバックの開発サーバ、`Origin` なし（CLI 等）だけを通す。
  - トークンは同じ OS ユーザーのプロセスなら読める。エージェントの書いたコード（Worker のテストやビルド、統合のテスト）は同じユーザーで動くので、トークンを読んで「human だけ」の操作（`integration.approve`、Grant、設定など）を人間として呼べる。字面の規則（§2.10）・環境変数の許可リスト・`Origin` の検査はこれを防げず、承認の数を増やしても塞がらない（Worker がコマンドを動かした時点で開いている）。根本対策は OS レベルの隔離（エージェントを `ACC_HOME` を読めない別の権限で動かす。未対応）で、それまでは後から見える記録（`tool.decided`）で補う（UI 以外の接続からの `integration.approve` を目立たせる監査は未対応）。同じ `ACC_HOME` で生きているデーモンがいれば 2 つ目は起動せず exit 0 で終わる（同時起動で bind に負けた側も、勝者の `daemon.json` を確かめて exit 0。ランチャーは exit 0 を「他が担当」とみなして勝者に接続する。ポートを別のプログラムが使っていれば exit 1）。
- 停止は `system.shutdown`（人間だけ。`tool: false`。実行中の Run があれば `force` なしでは `conflict`）。応答を返してからサーバ・モジュール・DB を閉じ、`daemon.json` を消してプロセスを終える（`ctx.requestShutdown()` → `Daemon.closed`）。CLI は `acc daemon stop`。
- 再起動時、`running` / `queued` / `awaiting_approval` のまま残った Run は `interrupted`（`statusReason: "daemon_restart"`）にし、イベントを残す。あわせてその Run の pending Approval を `cancelled`（その出番も `resolved`。質問の出番は残す。§2.16）、ワークスペースロックと `session.activeRunId` を解放する（`core/recovery.ts`）。その後の各モジュールの照合（中断された Worker の Task、統合、Orchestrator の再開）は §2.8・§2.12。
- DB は Node 組み込みの `node:sqlite`（WAL）。ドライバは `core/db.ts` の `Db` インターフェースの裏に隠す。エンティティのテーブルは「絞り込み用のインデックス列 + `data`（エンティティ全体の JSON、読み書き時に zod で検証）」の形。フィールド追加にマイグレーションは要らず、絞り込み列を足すときだけ要る。
- テーブルを作り直すマイグレーション（`rebuildsTables`。例 `core/0002_nullable_project`）が既存の DB に未適用なら、適用の前に `VACUUM INTO` で `acc.sqlite.bak-<version>`（あれば `-2`…）を作る。新しい enum 値を古いデーモンは読めないので、ダウングレードはこのバックアップに戻して行う。
- 起動時のバックフィル（冪等）：マイグレーション直後に `core/backfills.ts` が全会話の `rootSessionId`（列と JSON）を親をたどって埋め直す。各モジュールの `start` で、cost が終端 Run から使用量台帳を埋めて `Session.cost` を再集計し、attention が承認待ち・失敗 / レビュー待ちの Task から出番を作り（1 回だけ、`runOnce`）、home が会話の状態を一度だけ導出する。一度だけの手順は `schema_migrations` に `backfill/<module>/<name>` として記録する。
- `config.json` の設定（`Settings`）は `settings.get` / `settings.update` で読み書きする。API キーは API・イベント・ログに平文で出さない（`hasApiKey` / `apiKeyMasked` だけ返す）。環境変数 `ACC_LITELLM_BASE_URL` / `ACC_LITELLM_API_KEY` が設定値より優先される。

### 2.2 プロトコル（WebSocket 上の JSON-RPC 風）

```
→ { "id": 1, "method": "session.create", "params": {...} }
← { "id": 1, "result": {...} }   または   { "id": 1, "error": { "code": "...", "message": "..." } }
← { "type": "event", "subscriptionId", "event": Event }   // events.subscribe 後に push
← { "type": "delta", "subscriptionId", "delta": { runId, sessionId, messageId, kind, text, index } }
                                                          // ストリーミング断片（永続化しない）
```

- 契約は `packages/protocol/src/api.ts`（メソッド → params / result / permission / description）と `wire.ts`（封筒・エラーコード）が唯一の定義。params は strict（未知のキーは `invalid_params`）。
- エラーコード：`invalid_params` / `not_found` / `forbidden`（Capability 違反）/ `budget_exceeded` / `conflict`（ロック等）/ `limit_exceeded`（同時実行数・深さ）/ `internal`。契約にあるが未実装のメソッドは `not_found`（`data.reason: "not_implemented"`）。
- 取りこぼしのない購読：`events.subscribe` は購読時点のログ先頭 `lastSeq` を返し、それより後のイベントはすべて push される。再接続時、クライアントは再購読 → `events.list({ since: 最後に受けた seq })` で欠けを埋め、`seq` で重複を除く（`@acc/client` が自動で行う）。
- WebSocket 接続の Actor は `human`（`client` クエリでラベル付け）。LLM のツール呼び出しはデーモン内から `ctx.call(agentActor, ...)` で同じディスパッチャを通る。

### 2.3 モジュール

`packages/daemon/src/` 配下。各モジュールは自分のディレクトリに閉じ、`index.ts` で `defineModule({ name, migrations?, register(ctx) })` を export する。`register` で API メソッド・イベント購読・サービスを登録し、一覧は `src/modules.ts`。

- モジュール間の呼び出しはサービス経由：提供側が `ctx.provide('runs', impl)`（型は `Services` インターフェースへの declaration merging）、利用側は呼び出し時に `ctx.service('runs')`。
- マイグレーションはモジュールごとに持ち、ID を `<module>/0001_xxx` と名前空間で分ける（`core` → `modules.ts` 順に適用）。

### 2.4 Control API と Capability

- params・result・`permission`（既定はメソッド名）・`description`（英語。LLM ツール説明にも使う）・`tool`（LLM に出してよいか）は protocol の `api` に宣言する。デーモン側は `defineMethod(name, { scope?, handler })` で実装だけを書く。
- ディスパッチャの順序：メソッド解決 → params 検証 → `scope` 解決 + `PolicyEngine.check(actor, permission, scope)` → handler → result 検証。
- 呼び出しには必ず `Actor` が付く：`human`（UI/CLI のトークン）、`agent`（`sessionId`, `runId`）、`system`。
- `human` / `system` は全権。`agent` は、その Run（`subject.kind = run`）またはその Session（`subject.kind = session`）に有効な Capability Grant が `permission`（`"*"`、`"task.*"` のようなパターン）と `scope` を許すときだけ実行できる。判定は**ディスパッチャで強制**し、ハンドラやプロンプトに任せない。
- scope：プロジェクトに関わるメソッドは `scope` で触るプロジェクトを返す。プロジェクト限定の Grant を持つ agent は、範囲外のプロジェクトや、プロジェクトを絞らない一覧（`session.list` で `projectId` なし等）を拒否される。`scope` を持たないメソッド（`system.*` 等）はプロジェクト制限の対象外。
- Grant の委譲：子 Grant の permissions・scope・limits は親の部分集合でなければ作れない。委譲深さは初期値 1（Orchestrator → Worker まで。Worker は Worker を起動できない）。
  - 判定は `policy/grants.ts`。agent が委譲するとき、親 Grant は (a) `grant.create`（Worker 起動時は `task.spawnWorker`）を持ち、(b) 子の各パターンを包含し（`"*"` ⊇ 全部、`"task.*"` ⊇ `"task.create"`）、(c) 子の projectIds ⊆ 親、(d) limits ≤ 親（`maxDepth` は 1 段ごとに 1 減る）、(e) `depth = 親.depth + 1 <= settings.maxDelegationDepth`。省略した scope・limits・`expiresAt` は親から引き継ぐ（広がらない）。
  - `limits.maxWorkers` は Grant の subject ごとに「起動して、まだ終わっていない子 Run（`parentRunId`）」の数で判定する（`policy.assertCanSpawnWorker`）。subject が Session なら、そのセッションのどの Run が起動した子も数える（先の Orchestrator Run が終わっても、残った Worker は枠を使い続ける）。
- agent が `task.spawnWorker` / `task.retry` 以外で Run を始められるのは（`session.send`・`run.retry`）、(a) 自分の木の中の、`session.spawn` で起こした子（`brief` を持つ）で、その Session Grant がすべて子の基本の権限か自分の Grant から委譲したもの、または (b) 自分が作ったチャットセッション（`parentSessionId` = 自分のセッション）で Session Grant を持たないもの、だけ（`policy.assertAgentMayStartRun`）。(a) で実行中でないエージェントの子を動かすときは子の枠（`maxChildren`）も数える。強いセッションをその Grant と予算で動かしたり、子や Worker を委譲・上限の外で増やしたりさせない。
- セッションのワークスペースと Task は、セッションにプロジェクトがあればそのプロジェクトのものに限る（`session.create` / `session.update`。移動でずれる場合も拒否）。
- LLM に見せるツールの一覧づくりは呼び出しではないので、外したメソッドを `policy.denied` に記録しない（`PolicyEngine.peek`）。
- Grant の有効範囲：`run`（その Run の終了で失効）、`session`（期限 `expiresAt` まで）、`work`（その会話と子孫の作業が落ち着くまで：実行中の Run・開いた出番・終わっていない Task（子孫が担当、または子孫が作成）・未処理の受信箱が 0。判定は `sessionState.isWorkSettled`）。Session に付けた `lifetime: run` の Grant は `work` として扱う（データは書き換えない）。`work` の失効は Run の終了（その会話と祖先を確かめる）と `session.state_changed` で判定し、デーモンの停止・再起動では失効しない（中断された指揮役が権限を持ったまま再開できるように）。Run を subject にした Grant は従来どおりその Run の終了で失効し、起動時のスイープも Run の Grant だけを扱う。剥奪は委譲先へ連鎖する。付与・剥奪は `grant.created` / `grant.revoked`（`work` の失効は reason `work_settled`）、使用は `tool.called`、agent の拒否は `policy.denied` として残る。
- 会話のスコープ：メソッドの `scope` は触る会話を `sessionIds` で返せる（`session.*` は対象の会話）。agent は Grant の subject の会話（Run の Grant なら自分の会話）を根とする部分木の中しか触れない（親をたどって判定。兄弟の木・親は `forbidden`）。例外は `scope.allSessions` を持つ Grant（右腕 §2.20）：どの木にも届き、`session.list` / `session.tree` / `cost.summary` も全体を見る（`policy.seesAllSessions`、`ownTreeOnly`）。委譲では親が `allSessions` を持つときだけ子に付けられる（規則 (c)）。`assertAgentMayStartRun` もこの Grant には適用しない（右腕が木の根に `session.send` できるように。根は自分の Grant と予算で動く）。
- Control API の Capability とは別に、エージェントの**ツールの使用**（ファイル・コマンド・Web）はデーモンの権限ゲートが決める（§2.10）。どこまで任せるか（`Project.permissionProfile`、`settings.defaultPermissionProfile` / `autoMode`、覚えた許可 `permissionRule.*`、`approval.respond` の `remember`）を変えられるのは人間だけ（agent が `project.update` で `permissionProfile` を変える、`remember` を付けて回答するのは Grant があっても `forbidden`）。プロジェクトの `repoPath`・`folderPath`（agent が作業場所にできるフォルダの基準）・`testCommand`（デーモンがシェルで動かす）も、作るときも変えるときも人間だけ。

### 2.5 Budget

- `BudgetAllocation` はツリー。`limitUsd`、`allocatedUsd`（子へ配分済み）、`reservedUsd`（実行中に確保）、`spentUsd`。
- 不変条件：`allocated + reserved + spent <= limit`（例外は下記の「消費の事実を優先」）。LLM の 1 回の呼び出し（chat / orchestrator Run）は reserve → settle（差額を解放）、事後にしかわからない消費（Agent Runtime）は `recordSpend`（§2.6）。子の終了で未使用分を親へ返却。
- コストの出どころを `reported`（LiteLLM が返した値）/ `estimated`（トークン数×単価）/ `unknown` で区別する。
- 実装は `policy/budget.ts`（`ctx.service('budget')`）。金額は内部で整数マイクロドルとして扱い、検査と更新は 1 つの `BEGIN IMMEDIATE` トランザクションで行う（別接続からの同時予約でも超過しない）。予約は `budget_reservations` に永続化し、再起動時に未確定のものを取り消す。
- 返却：release は子孫から先に閉じ、空き（limit − allocated − reserved − spent）だけを親の `allocatedUsd` から減らす。消費済み分は親の `allocatedUsd` に残る。予約が残っている Budget、終わっていない Run が `budgetId` に持つ Budget は release できない（`conflict`）。返却済みの Budget で Run は始められない。実際の消費が予約を超えた場合は、消費の事実を優先して記録する（以後その Budget には空きがない）。
- agent が配分できるのは自分の Budget（自分の Run・Session・担当 Task が subject、または `run.budgetId`）からだけで、返却できるのは自分の Budget とその直下だけ。ルート Budget は人間だけが作る。
- 超過の伝播：Budget が limit を超えて使った分は、親の `allocatedUsd` に足す（親も超えれば根まで）。親は子が実際に使った額を常に数えている。使える額は `available`（自分の空き。祖先のどれかが超過していればその負の空きで頭打ち）で、予約と実行の継続はこれで判定する。根が超過すると木の実行はすべて止まる（§2.17）。
- 変更：`raise`（人間だけ。子なら超過で親が負担済みの分を除いて親から切り出し、親に空きが足りなければ親も上げる）、`setLimit`（下げた差は親へ返す。使用済みより下げない）、`adjustSpend`（推定の補正。負も可）、`reallocate`（返却済みの子を同じ額で親からもう一度切り出す。再試行用）。
- イベント：`budget.updated` は作成・配分・返却・変更と、spent の変化（1 Budget につき 1 秒に 1 回まで）だけ。予約・予約の取り消しでは出さない（起動時の未確定の予約の取り消しは `daemon_restart` で出す）。`budget.threshold`（`pct` 50 / 80 / 100）は、その Budget と子孫の spent の合計が limit のその割合を越えたとき、Budget と祖先ごとに 1 回。

### 2.6 Run ライフサイクル

`created → queued → running → completed`。途中で `awaiting_approval`、終端は `completed / failed / cancelled / interrupted`。

- 実行枠は 2 系統：`agent` の Run は `settings.maxConcurrentAgents`（既定 10。旧 `maxConcurrentRuns` を読む）、LLM だけの Run（`chat` / `orchestrator`）は `settings.maxConcurrentChats`（既定 16）。上限を超えた Run は `queued` で待ち、系統ごとに空きができた順（FIFO）に始まる（エージェントが枠を埋めていても指揮役と会話はすぐ答えられる）。実行枠は `running` と `awaiting_approval` が占有する（承認待ちもプロセスやロックを持ったままのため）。旧プリセットの指揮役の Run が `task.wait` / `integration.wait` で眠っている間は、その枠を待ち行列に貸す（`runs.lendSlot`）。待ちから戻った Run は、枠が埋まっていても続ける（一時的に上限を超えうる）。
- 1 つの worktree に書き込める Run は同時に 1 つ（ワークスペースロック）。ロック待ちの Run は `queued` のまま残り、後ろの Run は先に始まってよい。ワークスペースが `removed` / `error` になった Run は待たずに `failed`（`workspace_unavailable`）。
- 1 セッションで同時に動く Run は 1 つ（`runs.start` は `conflict`）。`session.send` はこれを受け止めて断らない：受信箱（§2.13）が差し込むか、今の Run の後に回す。
- デーモンが自分で止めた Run は `failed` で、`statusReason` とエラーコードに理由が入る：`turn_limit`（1 実行のモデル呼び出しの上限）、`loop_detected`（同じツール呼び出し・同じ本文の 3 連続）。割り込みで止めた Run は `cancelled`（`superseded`）、`session.stop` で止めた Run は `cancelled`（`stopped_by_user`）。
- `run.retry`：Task の Worker（`agent` で `taskId` あり）は `task.retry` として行う（Task の状態・権限・上限・予算の規則がそのまま効く）。Integrator の Run は再試行できない（統合から改めて Integrator に任せる）。
- 実際の処理は Run の種類ごとの Executor（`ctx.service('runs').registerExecutor(kind, fn)`）が `RunController` 経由で行う（`chat` は sessions、`agent` は runtime、`orchestrator` は orchestrator）。登録は各モジュールの `start()` で行う。終端状態は RunManager だけが決める。
- `agent` Run で `workspaceId` を省くと、セッション → Task のワークスペースを Run に記録してそのロックを取る（Executor が書き込む先と、ロックの対象を一致させる）。`chat` Run はロックを取らない。
- キャンセルは即座に `cancelled` にして signal を abort する。実行枠とロックは Executor が止まってから返す（止まらなければ 10 秒で強制解放。強制解放の後で確定した LLM 呼び出しの実費も、Run の使用量と Budget に記録する）。デーモン停止時は `running` / `queued` を `interrupted`（`daemon_shutdown`）にする。
- 「いま何をしているか」は `Run.activity`。変化は `run.updated`（`changes: ["activity"]`）で届き、使用量の加算も `run.updated`（`["usage"]`）。activity は実行中だけ意味を持つ。
- 予算（Budget を持つ Run）：
  - LLM 呼び出しの前に `ctl.reserveBudget()` で `settings.llmCallReserveUsd`（既定 $0.25）を予約し、終わったら `hold.settle(usage)` で実額に確定、失敗した呼び出しは `hold.cancel()`。予約が入らない（空き < 予約額）呼び出しは拒否するので、同じ Budget を共有する Run が同時に動いても、1 回の実額が予約額以下である限り上限を超えない（`runToolLoop` が使う）。Run の終了時に残った予約は取り消す。
  - Agent Runtime は使用量を事後に `reportUsage` で報告し、そのたびに `recordSpend` する。始める前に空きがなければ（または返却済みなら）`ctl.assertBudgetLeft()` で拒否する。消費を Budget に記録できなかった Run は、上限なしに続けさせず予算切れとして止める（使用量は Run に残る）。
  - 残り（`available`：limit − allocated − reserved − spent、祖先の超過で頭打ち）が 0 以下になった Run、予約できずに拒否された Run は `failed`（`statusReason: budget_exhausted`、エラー `budget_exceeded`）。1 日の上限で止めた・拒否した Run は `statusReason: daily_limit`（§2.17）。
- 終了時に実行枠とロックを返し、その Run に紐づく `lifetime: run` の Grant は policy モジュールが失効させる（`grant.revoked`）。
- 使用量と予算の処理は `runs/usage.ts`（`UsageAccountant`）：`reportUsage`・`reserveBudget` / `BudgetHold.settle`・`assertBudgetLeft`。Run に記録した使用量は同じトランザクションで `ledger.record` にも渡す（`Session.cost` の唯一の入口。§2.17）。`emitDelta` の断片は `streams.append` にも渡す（§2.19）。`Run.trigger`（`user` / `wake` / `spawn` / `schedule` / `resume` / `retry` / `system`）は `StartRunInput.trigger`（既定 `user`）。

### 2.7 イベント

全状態変化は `events` テーブルに追記し（単調増加 `seq`）、購読者へ配信する。UI の Timeline Mode と Orchestrator の状況判断はこれを読む。型は `packages/protocol/src/events.ts` の `eventPayloads` が唯一の定義。

- 封筒に `projectId / sessionId / runId / taskId` を持ち、絞り込みは payload を見ずに行える。`bus.emit` は payload の形（`{ run }`、`{ session }` 等）から参照を自動で埋める。
- `bus.emit` は呼び出し側のトランザクション内で追記し、**コミット後に**配信する（ロールバックされたイベントは誰にも届かない）。
- 配信は `seq` 順を保つ：コミット後フック（`Db.afterCommit`）は登録順に 1 本のキューで実行し、フックの中で別のトランザクションがコミットしても、そのフックは残りの後ろに並ぶ（例：トランザクション内で `runs.start` した Run の起動イベントが、同じトランザクションで後から出したイベントより先に届かない）。クライアントは `seq` で重複を除くため、順序が崩れると欠けて見える。
- 状態を変えるメソッドは、同じトランザクションで「エンティティ更新 + イベント追記」を行う。`*.updated` には変わったフィールド名を `changes` に入れる。

### 2.8 Workspace と Integration

- **Workspace**：worktree は `<ACC_HOME>/worktrees/<projectId>/<workspaceId>`、ブランチは既定 `acc/<slug>-<id末尾8文字>`（slug はラベルかタスク名の ASCII 部分、なければ `ws`）。リポジトリ本体は `kind: main` のワークスペースとして初回参照時（`workspace.list` で projectId 指定など）に登録し、削除できない。git は `workspace/git.ts` の `git(cwd, args)` で引数配列のまま spawn する（シェルを通さない）。実行ファイルは PATH の絶対パスの項目から探した絶対パス（`runtime/env.ts` の `findOnPath`。Windows は名前だけだと cwd＝worktree を先に探すので、エージェントが置いた `git.exe` が動いてしまう。モックの `run` 手順、Claude Code の CLI の場所も同じ。`taskkill`・`rundll32` は `System32` の絶対パス）。worktree の中身はエージェントが書くので、デーモンの git はリポジトリ由来のプログラムを実行しない：毎回 `-c core.fsmonitor=false -c core.hooksPath=<null デバイス>`（コミット・マージは `--no-verify` も）、環境は許可リスト（`runtime/env.ts` + `GIT_CONFIG_*`）。linked worktree の `.git` ファイルは、作業ツリーの外の `<common>/worktrees/<name>` を指し、その `gitdir` が戻ってくるときだけ使い、`GIT_DIR` / `GIT_WORK_TREE` で固定する（書き換えられていれば git を実行せずエラー）。
- **ロック**：書き込める Run は 1 つ。Run のロックはメモリ + `Workspace.lockedByRunId`（再起動時に `core/recovery.ts` と workspace モジュールの `start` が終わった Run のロックを外す）。統合など daemon 内部の作業は `hold()` でメモリだけのロックを取る。ロック中は削除不可。
- **削除**：`workspace.remove` は worktree だけ消してブランチは必ず残す（成果物を失わない）。未コミットの変更があると `force` なしでは拒否。ロックの確認と同時に（await の前に）自分でロックを取るので、削除の途中で Run が始まって作業ディレクトリを消されることはない。
- **diff**：`baseRef`（既定はワークスペースの baseRef）と HEAD の merge-base に対し、コミット済み・未ステージ・未追跡をすべて含めて出す。未追跡は一時 index（`GIT_INDEX_FILE`）に `add -A` して拾い、エージェントの index は触らない。パッチは 2M 文字で切る（ファイル別統計は完全）。
- **コミット**：`commitAll` の author/committer は `Project.commitAuthor`、未設定なら `AI Agent Command Center <acc@localhost>`。デーモンがコミットするのは Task の Run・Integrator の Run の終了時と、会話の worktree を統合するとき（`integration.create`）だけ。会話の Run は何もコミットしない（頼まれていないコミットは、人から見て想像できない）。
- **Artifact**：`ctx.service('artifacts')` の `record` / `recordDiff` / `recordCommit` / `recordTestResult` で記録し `artifact.created` を出す。projectId・taskId はワークスペースや Run から補う。確認の状態は `setReview`（`artifact.updated`）。成果物としての扱いは §2.15。
- **Integration**：`integration.create` は `taskIds` / `workspaceIds` / `sessionIds`（会話の worktree。agent が指定できるのは自分の木の会話だけ）のどれか 1 つで元を指定する。子の会話の worktree は Task を名指さないので、その会話の Task を元の Task として数える（反映でその Task が done になる）。Task のない（会話の）worktree に未コミットの変更があれば、先に `会話「<会話のタイトル>」の変更` としてコミットする（Run が使用中のものと Task の worktree は触らない。ただし使用中の Run が呼び出し元自身なら、その呼び出しを待っているのでコミットする：リードが子の仕事と自分の仕事をまとめるとき）。そのうえで反映先（既定 `Project.defaultBranch`）から `acc/integration-<id末尾8文字>` を専用 worktree に作り、merge ×N → verify → apply の手順を `pending` で並べる。`integration.run` はすぐ返し、裏で毎回反映先の最新から `git merge --no-ff` を順に行い、`Project.testCommand` をシェルで実行する（タイムアウト既定 10 分、出力は末尾 64KiB を test_result Artifact に。環境はエージェントと同じ許可リスト + `CI=true`。出力に LiteLLM のキーやデーモンのトークンがあれば `[REDACTED]` にする）。
  - テストはエージェントの書いたコードをユーザーの権限で動かす。**慎重プロファイル（§2.10）では**、人間が始めていない試行（agent の `integration.run`、Integrator の解消後の再開など）は、実行の前に `integration` 種別の Approval（`payload: { action: "verify", command }`、`integrationId` つき、`runId` なし）を出して待つ（状態は `verifying` のまま。回答できるのは人間だけで、agent・system からは Grant があっても `forbidden`。却下は `failed`（`tests_not_approved`）、停止・再起動で待ちが切れたら取り消す。UI は統合のカードで尋ねる）。標準・おまかせでは待たない：Worker がすでに同じコードを同じユーザー・同じ環境で承認なしに動かしているので、ここで止めても守れるものが増えないため（§2.1）。手順ごとに `integration.updated` を出す。
  - 状態：`running` → `verifying` → `awaiting_approval`（反映待ち）／`conflict`（マージ中止済み、統合ブランチは直前の状態）／`failed`（テスト失敗・その他）。`conflict` / `failed` / `awaiting_approval` からは再実行できる。同じプロジェクトの統合と承認は 1 件ずつ直列に実行する。承認（反映）の途中は、`integration.run` / `reject` / `resolveWithAgent` / 二重の承認を `conflict` にする（呼び出した時点で反映中の印を付ける）。順番待ちの試行は、始まる時点で `running` でなければ何もしない。
  - テストコマンドの終了はシェルの `exit` で決める。残ったバックグラウンドプロセスが出力のパイプを持ち続けても、1 秒待ってパイプを閉じて終える（POSIX はプロセスグループごと止める）。
  - 統合結果の diff は `role: evidence`（子の変更とは別に採用するものではない）。反映（`applied`）で含まれる Task は `done` になる（§2.15）。
  - 事前承認：`artifact.review accept`（人間）が作る統合は `preApprovedBy` を持ち、その採用が始めた試行だけは検証が通ると採用した人として自動で反映する（`run(..., { autoApply })`）。早送りできなければ `awaiting_approval` のまま `error.code: apply_failed` に理由を残す。再実行や Integrator の解消後の試行は人間が見ていないコードを含みうるので、通常どおり承認を待つ。
  - `integration.approve` は **human のみ**（agent・system は Grant があっても `forbidden`、LLM ツールにも出さない）。反映は早送りだけ：反映先がどこかの作業ツリーでチェックアウト中なら、そこが clean のときだけ `merge --ff-only`（dirty なら `conflict`）、どこにもチェックアウトされていなければ旧値つき `update-ref`。反映先が進んでいたら `conflict`（再実行を促す）。
  - 却下・失敗でも worktree とブランチは残す。再起動で中断された統合は `failed`（`daemon_restart`）になる。
  - **Integrator**（concept §6.1 の 5）：`integration.resolveWithAgent({ integrationId, instructions? })` は `conflict` の統合だけ。統合用 worktree にコンフリクトしたマージを再現し（マーカー入り）、コンフリクトしたマージの直後に `fix` 手順を挟んで状態を `running` にしてから（`integration.wait` は待ち続ける）、その worktree で `agent` Run（Task なし。権限・深さ・予算は Worker と同じ規則で `orchestrator/workers.ts` が起動）を始め、`Integration.resolverRunId` に記録する。プロンプトはコンフリクトしたファイルと両側の Task の目標・完了条件・要約（`acc-mock` 計画は渡さない）。Run が `completed` で、マージがコミット済み（`MERGE_HEAD` なし）・未解決ファイルなし・取り込むブランチが HEAD に含まれる・マーカーが残っていない、を確かめたら **再開モード**で続ける：統合ブランチを作り直さず、すでに含まれるソースは「取り込み済み」とし、残りのマージと検証を行う。満たさなければ worktree を再現前に戻して `conflict`（`error.code: resolution_failed`、理由つき）。通常の `integration.run` は反映先から作り直すので `fix` 手順と解消結果は消える。
- **Project の検査**：`project.inspectRepo({ path })`（`tool: false`、読み取りだけ）は、絶対パスか・存在するか・git リポジトリのルートか（サブフォルダならルートを `repoRoot` で示す）を日本語の `reason` つきで返し、`defaultBranch`（origin/HEAD → main / master → 現在のブランチ）、`currentBranch`、`isDirty`、`suggestedName`（フォルダ名）、`suggestedTestCommand`（package.json の `test` スクリプト + lockfile で pnpm / yarn / bun / npm、Cargo、Go、pytest）、登録済みなら `existingProjectId` を返す。UI が `project.create` の前に呼ぶ。

### 2.9 Task と依存 DAG

- `dependsOn` は同じプロジェクトの既存 Task だけ。未知の ID・循環は `invalid_params`。
- 依存待ちの Task（`pending` / `ready` / 依存による `blocked`）の状態はデーモンが自動で保つ：依存がすべて `done` → `ready`、依存が `failed` / `cancelled` / `blocked` → `blocked`（`statusReason: dependency_failed | dependency_cancelled | dependency_blocked`）、解消すれば `pending` / `ready` に戻る。`dependency_*` 以外の `blocked`（人間待ちなど）は自動では戻さない。
- 状態変更は `ctx.service('tasks').setStatus(...)` に集約し、依存先への波及も同じトランザクションで `task.updated` を出す。キャンセルは未完了のサブタスク（`parent_cancelled`）と、それらの終わっていない Run にも及ぶ（コミット後に `runs.cancel`、`statusReason: task_cancelled`）。

### 2.10 Agent Runtime

コーディングエージェントの実行基盤。契約は `contracts.ts` の `AgentRuntime` / `AgentEvent` / `RuntimesService`。

- `ctx.service('runtimes')` に `mock`（オフライン）と `claude-agent-sdk` を登録する。既定は `settings.defaultRuntime`。null（未登録の名前も）は「自動」で、デーモンのプロセス（`main.ts` の `detectAgentRuntime`）なら Claude Code の CLI が見つかれば `claude-agent-sdk`、なければ `mock`。テストとスクリプトの `createDaemon` / `startDaemon` は検出しないので、自動はいつも `mock`（本物のエージェントに届かない）。自動のとき、モックのモデル（`mock/*`）の会話と、モックのモデルの親が起こす子は `mock` のまま（デモがオフラインのまま）。Run が使うのは `run.runtime` → `session.runtime` → 既定の順。`settings.get` / `settings.update` は `agentRuntime`（`configured`・`effective`・`detected`、自動がモックになる理由 `reason`）を返し、設定画面の「エージェント」が読む。
- **答えたモデルを記録する**：エージェントの会話・Run・費用の台帳に書くモデルは、頼んだモデルではなく実際に答えたモデル。ランタイムは `AgentEvent` の `model` で知らせる（Claude Code は `system/init` の `model`、そのあと本体の API メッセージの `message.model` が変わったとき。サブエージェントと `<synthetic>` は数えない。モックは `mock/mock-agent`、モックのモデルならそのモデル）。実行器はそれ以降の発言の `model` にし、`ctl.setModel` で Run の `model` を替える（run.updated `["model"]`。台帳は Run の `model` で記帳する）。
- **Claude Code が動かせないモデルを会話に付けない**：Claude Code は名簿の GPT などを動かせず、黙って自分の既定で答える（`resolveModelRouting` はそういうモデルを渡さない）。エージェントの会話は、メンバー・プロジェクト・設定の既定のモデルを、ランタイムが動かせるときだけ受け継ぎ、そうでなければ `model: null`（`agentDefaultModel`）。人でもエージェントでも、動かせないモデルを名指しすれば `session.create` / `session.update` / `session.send` は理由つきで断る（`assertAgentModel`。動かせるのは LiteLLM があればその名前、なければ Claude のモデル。モックは何でも）。
- `agent` 種別の RunExecutor（`createAgentExecutor`）：ワークスペースのパスで Runtime を動かし、`AgentEvent` を `RunController` に流す。プロンプトは Task（目標・完了条件）＋起動メッセージ＋作業場所ごとの 1 段落（§2.14）。git のワークスペース（`worktree` / `main`）だけ終了時に変更を記録する。Task の Run と、統合の worktree での Run（Integrator）は `workspaces.commitAll` し、コミットができたら、またはエージェントが自分でコミットしていて作業場所の diff が最新の diff Artifact と違えば、`artifacts.recordDiff` で diff Artifact を記録する（本物の Claude Code の子は自分で `git commit` することがあり、そのときもコードの変更として残す）。Task のない会話の Run はコミットせず、作業場所の diff（未コミットを含む）が最新の diff Artifact と違うときだけ記録する（失敗しても Run は失敗させない）。
- **ツール権限は層に分けてデーモンが決める**（プロンプトに任せない。目標は「安全で、承認依頼 0」。承認は決められないときの妥協。経緯は `docs/snapshot/20261029_auto-mode.md`）。Run ごとの `ToolGate`（`runtime/gate.ts`）が、すべてのランタイム（claude・mock）で上から順に評価する：

- コストの出どころ：ストリームの `usage.cost` > `x-litellm-response-cost` ヘッダ（ストリーミングで 0 のときは無視）を `reported`、なければ単価表（`llm/pricing.ts` の `PriceBook`）で `estimated`（キャッシュの読み・書きはそれぞれの単価。なければ入力の 0.1 倍・1.25 倍）。単価は LiteLLM の `/model/info`（取れれば。1 時間キャッシュ。別名もこれで分かる）→ 組み込みの Claude の表 → 知らないモデルは既知の最高単価（0 にしない）。チャットの呼び出しはキャッシュだけを見る（`/model/info` を取りに行くのは Claude ランタイムの推定のとき）。本物の LiteLLM はストリームの最後の usage チャンクに `cost`（LiteLLM の価格表による。キャッシュの読み書きも含む）を入れ、ストリームではヘッダを送らない。`prompt_tokens` はキャッシュの読み書きを含む。
- 無応答：LiteLLM は止まった上流のストリームを自分のタイムアウト（既定 6000 秒）まで開いたままにするので、Gateway が LiteLLM から何も届かない時間（応答ヘッダ待ちを含む）を `idleTimeoutMs`（既定 5 分）で打ち切り、`llm_timeout` で失敗させる。
- エラー：LiteLLM は上流のエラーを `litellm.XxxError: AnthropicException - b'{...}'` ＋「LiteLLM: model group … No fallback was attempted.」で包む。`llm/gatewayErrors.ts` で上流のメッセージだけを取り出し、HTTP ステータスごとの日本語の説明を付ける（Claude ランタイムの失敗理由も同じ関数を使う）。LiteLLM にないモデルは 404 ではなく 400「Invalid model name passed in model=…」なので `llm_model_not_found` にする。上流の 401 / 404 の後、LiteLLM はそのデプロイメントを数秒止め、次の呼び出しは上流に届かず 429（`all_deployments_in_cooldown`）になる。429 / 5xx は LiteLLM も再試行する（既定で計 3 回）が、LiteLLM 自身の失敗や諦めた後に備え、Gateway も**トークンを 1 つも受け取っていない**呼び出しの 429 / 5xx / 接続失敗だけを最大 2 回再試行する（`Retry-After` を尊重、なければ 1 秒・2 秒。20 秒を超える `Retry-After` は待たない）。LiteLLM のキー・チーム・ユーザーの予算超過（`budget_exceeded`、`Budget has been exceeded!`、`ExceededBudget`）は `llm_quota_exceeded` にし、再試行しない（Claude ランタイムの失敗も同じ code）。
- Anthropic の extended thinking：LiteLLM は thinking を `reasoning_content` と `thinking_blocks`（署名つき）で流す（ブロックの本文の断片のあと、署名つきの断片で閉じる。その断片の本文は 1.106 では空、1.105 では全文の繰り返しなので、足さずに置き換える）。thinking が有効なモデルでは、ツール呼び出しのターンを thinking ブロックなしで送り返すと Anthropic が 400 を返すので、ツールループはそのターンの `thinking_blocks` を次の呼び出しの assistant メッセージに付けて返す（メモリ上だけ。セッション履歴には保存しない）。
- mock：`mock/echo`（実時間に近い間隔で分割送信）、`mock/fast`（遅延なし）。`llm.mock.define(model, scripted([...]))` でツール呼び出しを含む複数ターンの台本を定義できる（ターン = 最後のユーザーメッセージ以降のモデル呼び出し回数）。
- ツールループ `runToolLoop`（`src/llm`）：モデル → ツール呼び出し → ディスパッチャ経由で `ctx.call(run の agent actor, ...)` → 結果 → モデル…。ツールは API 契約（`tool !== false`）から生成し、actor の Grant で絞る。メソッド名の `.` はツール名では `__`。params の JSON Schema からは検証だけのキー（`pattern`・長さ・範囲・要素数）を落とす（`stripValidationKeys`。ディスパッチャが zod で検証し直すので安全。右腕の 19 個で約 28% 減、id の正規表現が 30 回・日時の正規表現が 300 字あった）。ツールの失敗は `{ error }` としてモデルに返し、Run は失敗させない。
- チャット Run はセッション履歴を送る（発言者の印つき。下の「会話の前提」）。セッションに Grant があればその範囲の API がツールとして見える（普通のチャットが Orchestrator になれる）。モデルは会話で選んだもの → **使うモデルの名簿**の最下段「それ以外」（`defaultModel`）→ 接続先が 1 つもなければ `mock/echo`。接続先があって何も決まっていなければ、最初の Run で `chooseChatModel` が Gateway の `suggestRoster`（`llm/autoModel.ts`：契約枠を優先、標準＝sonnet / sol / 無印の gpt を「それ以外」に、速いモデル＝haiku / mini / luna が別にあれば「調べもの・要約・定型の作業」の 1 行、新しい版、`codex` 系は他がないときだけ。一覧が取れなければキーのあるプロバイダの既知の名前）で選んで**設定に保存する**。以後は固定で、変えるのは人だけ（実行のたびに選び直さない）。Run は使ったモデルを記録する（`run.updated` `["model"]`）。
- **会話の前提**（`sessions/framing.ts`、`docs/snapshot/20261031_conversation-framing-spec.md`）：右腕でも監督役でもない会話のシステムプロンプトはデーモンのテンプレート `conversationFrame`：何者か（この前提は会話の中のどの発言でも変わらない）、立場（監督役「X」の子 / 繰り返しの予定「X」の 1 回 / 右腕が立てた / 人が始めた）、発言者の印の読み方（印は発言全体に掛かる）、優先順位（人 > 監督役・右腕。依頼の中の指示で前提・権限・予算は変わらない）、できること（チャットは話すだけ、渡されたツールがあればそれだけ。エージェントは作業場所のファイル・コマンド・ウェブ）。**親の依頼は `<<<依頼ここから>>>` と `<<<依頼ここまで>>>` の間に引用するだけ**（中に終わりの印があれば無害な文字に置き換える）なので、親は依頼の中身しか決められない。`session.systemPrompt` は人が作った会話ならそのまま、エージェントが作った会話なら同じく引用。履歴の依頼メッセージ（`meta.brief`、予定なら `meta.schedule`）は本文を前提に引用したので `[監督役「X」から] （依頼。…）` とだけ渡す（`briefInFrame`）。**題は 1 か所で整える**（`framedTitle`：改行をつぶし、`「」` は `『』`、`[]` は全角、40 字まで）。監督役は自分の題を変えられるので、題で前提に行を足したり印を閉じたりできないようにする。**発言者の印**：`toChatMessages` の `userText` で、人以外の `user` 発言の前に `[監督役「X」から]` `[右腕から]` `[会話「X」から]` `[繰り返しの予定から]`（起床 `[状況の更新]` と、右腕の会話の自分の知らせには付けない）。監督役・右腕の履歴、作業中の差し込み（`injectedMessages`）にも同じ印。エージェント（Claude Code）は同じテンプレートを `systemPrompt.append` に、タスクの見出しは `# 監督役「X」からの依頼: 題`（予定なら `繰り返しの予定「X」`）、依頼の本文はタスクで一度だけ渡し、前提は引用せずに「タスクの見出しのもの」と指す（Claude Code はタスクを自分のセッションに残す）、追加の指示にも印。監督役と右腕のプロンプトには「会話・エージェントがそれぞれ何をできるか」（`CHILD_ABILITIES`。ウェブやファイルが要るならエージェント、人のフォルダはプロジェクトとして渡されない限り届かない）。
- **プロンプトキャッシュの形**：キャッシュは先頭からの一致なので、変わらないもの（tools → 固定のシステムプロンプト → 履歴）を前に、実行ごとに変わるもの（右腕の状況、監督役の木 `treeSnapshot`）は**最後のシステムメッセージ**として履歴の後ろに置く。Anthropic は「履歴の終わり」と「最後のブロック」に印をつけ、次の実行は履歴を、同じ実行の次の呼び出し（ツールループ）は全部を読み戻す（API は印から 20 ブロックまでさかのぼって前回の書き込みを探すので、印が毎回後ろへ動いても当たる。ただし、**メッセージの途中で書いたキャッシュは、そのメッセージがそこで終わる形では読めない**。本物で確認：`docs/snapshot/20261031_supervisor-window-cache.md`）。「履歴の終わり」は最後の後ろのシステムメッセージの前に置く。履歴の途中の system（再開の通知など）の前には置かない（そこに固定されて、以後の履歴が読まれなくなる）。最後のブロックの印は書き込みが 1.25 倍なので、次の発言まで 5 分より空くツールなしの会話では少し損になる。それでも会話を続けるときの読み戻し（0.1 倍）が効くので付ける。Anthropic では、後ろのシステムメッセージを、途中の system を受け付けるモデル（`acceptsMidSystem`：5.x 以降の Opus / Sonnet / Haiku、Opus 4.8、Fable、Mythos。本物で Haiku 5.5・Sonnet 5 / 5.5・Opus 5.5 を確認、Haiku 4.5 は 400）には `role: system` のメッセージとして送る。ただし API が許す場所だけ（user の直後で、最後か次が assistant）。そうでないものと、受け付けないモデルには、user の発言として送る。そのときは先頭に `[アプリから]`（`APP_NOTE_LABEL`）を付け、右腕・監督役のプロンプトでその意味を伝える。user の発言として送ると、状況が最後の発言と同じメッセージに入るので、実行をまたいだ履歴のキャッシュは効かない。それでも 400 を返したモデルは、その場で user の発言の形で送り直し、以後もそうする。OpenAI（gpt-5.6 以降は自動で前方一致、1,024 トークン以上）は `instructions` に変わらない部分だけを入れる。
  - **LiteLLM 経由**（`docs/snapshot/20261031_litellm-prompt-caching-verified.md`）：裏が Claude のときだけ、同じ 4 か所に印を付ける（Claude 以外に送ると、LiteLLM はそのまま上流に流すか、有料の明示キャッシュに変える）。
    - 付ける場所：最後のツールは top-level の `cache_control`（Bedrock はここしか読まない）。system・user・tool はメッセージ自体。ツール呼び出しつきの assistant は最後の `tool_calls[i]`（メッセージ自体の印は、content が null だと消える）。空の発言には付けない。
    - LiteLLM は 5 つ目以降の印も削らないので、4 つまではこちらで守る。
    - 裏が Claude かどうか：前回の応答の `x-litellm-model-name` → `/model/info` の `litellm_params.model`（`PriceBook.deploymentOf`）→ 名前そのもの、の順に見て `claude` を含むか。別名（`team-sonnet` など）は、最初の呼び出しでは印なしになることがある。
    - **LiteLLM 1.104.0 以上が前提**。それより前は、後ろのシステムメッセージも先頭の `system` にまとめるので、履歴のキャッシュが毎回外れる。`x-litellm-version` を見て、一度だけ警告をログに出す。
    - 1.104 以降、後ろのシステムメッセージは、途中の system に対応するモデル（LiteLLM の価格表の `supports_mid_conversation_system`）には `role: system` のまま、それ以外には `Operator note …` の文を付けた user の発言として送られる。どちらでも、それより前は変わらない。
  - 子・根の会話は前提（`conversationFrame`）が会話の途中で変わらず、履歴も追記だけなので、そのまま効く。履歴の窓（監督役 `supervisor.contextMessages` の 40 件、会話の `CHAT_HISTORY_LIMIT` の 200 件）は、上限の半分ずつまとめて切る（`windowLength`。送るのは上限の半分〜上限の件数）。1 件ずつ切ると先頭が毎回ずれて、履歴のキャッシュが毎回外れる。まとめて切ると、外れるのは切った直後の 1 回だけ。親の題を変えると子の前提と印が変わり、その子のキャッシュは一度作り直しになる。効き具合は呼び出しのログで見る（§2.17）。
- **使うモデルの名簿**（`settings.modelRules`、`llm/roster.ts`、`docs/snapshot/20261030_model-roster-spec.md`）：`{ model, when }` の並び（最大 20 行）。上から順に見て最初に `when` が当てはまった行のモデルを使い、どれにも当てはまらなければ `defaultModel`。選ぶのは割り振る側：右腕（`assistant.startWork`、`delegate: false` のとき）と監督役（`session.spawn`）。システムプロンプトに番号つきの名簿と、行ごとの典型的な 1 回（20 呼び出し × 入力 8k・出力 800）の費用・エージェントに使えるか（LiteLLM があれば接頭辞なしの名前、なければ Claude のモデル）を渡す（`rosterPromptBlock`。設定が変わるまで同じなので、キャッシュできる接頭辞に入る）。判断のための追加のモデル呼び出しはしない。**名簿の外は Core Daemon が拒む**：エージェントが `session.create` / `session.spawn` / `session.update` / `session.send` / `assistant.startWork` で名簿にないモデル（`mock/*` は除く）を名指すと `invalid_params`、エージェント（Claude Code）が動かせないモデルも同様。名簿が空なら制限しない。人は自由。`models.list` の各モデルに `runUsd`（典型的な 1 回の費用。契約枠と mock は 0、単価が分からなければ null）を付ける。実行中に届いた発言は区切りで差し込まれ（§2.13）、1 実行のモデル呼び出しは `supervisor.maxModelCallsPerRun` まで。右腕の会話（§2.20）だけは、モデルの順序（会話で選んだもの → `settings.assistant.model` → 名簿の「それ以外」 → 接続先がなければ `mock/right-hand`）、system prompt（役割＋全部の木の状況）、日次上限を `assistant` サービスが差し込む。
- `session.send` の `hint`（最大 500 字）：会話には出さず、モデルにだけ渡す 1 行の文脈（メッセージの `meta.hint`）。いまは右腕の system prompt だけが読む（ホームの作業場所の選択）。`workModel` は人がその依頼に選んだモデル（`meta.hint.model`）：右腕には `モデルの指定:` の行で伝え、`assistant.startWork` は Run のきっかけになった人のメッセージにそれがあれば、右腕が何を渡しても、名簿になくても、そのモデルで会話を立てる（人が選んだものなので名簿の制限はかけない）。`workPlace { kind: folder | worktree, projectId }` は人がその依頼に選んだ場所（`meta.hint.place`）：同じように右腕の `workspace` / `projectId` より優先し、`folder` はそのプロジェクトの `folderPath`、`worktree` はそのプロジェクトのコードで会話を立てる（委任なら根はそのプロジェクトの会話で、子がその場所を使う）。プロジェクトにその場所がなければ `conflict`。人が選んだフォルダなので `assertAgentFolder` はかけない。
- 履歴の組み立て（`toChatMessages`）：ツール呼び出しの結果がそろう前に保存された発言（実行中に差し込まれたもの）は、結果の後ろに回す（モデルが見た順と同じにし、呼び出しと結果の組を崩さない）。
- `session.search`：FTS5 の trigram で部分一致（日本語向け）。3 文字未満の語は LIKE で補う。索引はトリガーで同期する。
- Session 自身の Budget（subject `session`、`active`）があれば、`session.send` の Run はそれを `budgetId` にする。

### 2.12 Orchestrator と Worker

Orchestrator は**セッション種別ではなく役割**（concept §3.1）。チャットに Grant を与えると、そのチャットが他のエージェントを率いる。

- **任せる（指揮役）**：入口は `session.delegate`（§2.13）。`session.grantOrchestration` はその別名（`maxWorkers` → `maxChildren`、`lifetime: run` → `work`、省いたものは `session.delegate` の既定）。コードの縦の流れも `session.spawn`（worktree の子、成果物の採用 = 反映。`e2e:slice`）を通る。以下の `task.*`・待機の流れは「旧プリセット」として、それを持つセッション（既存の Grant、人間の `grant.create`）のために残す。
- **旧プリセットの付与**：`grantOrchestratorPreset(ctx, { sessionId, projectId?, maxWorkers=2, lifetime='run', budgetUsd?, expiresAt? }, actor)`（人間だけ。メソッドはなく、テストは `testing.ts` の `grantOlderPreset` で付ける）。プリセット `ORCHESTRATOR_PERMISSIONS`（`task.*`、session / run / workspace / artifact / approval / events の読み取り、`run.cancel`、`integration.create/run/resolveWithAgent/get/list/wait`、`orchestrator.*`、`project.get`）を、そのプロジェクト限定・`limits { maxWorkers, maxDepth: 1 }` で付ける。`integration.approve`・`grant.*`・`budget.*`・設定は含めない。`budgetUsd` はセッションのルート Budget になる。
- **Run 種別**：`session.send` はセッションの Grant が `task.spawnWorker` を許すとき Run を `orchestrator` にする。Executor（`orchestrator/executor.ts`）はチャットと同じツールループに、役割・プロジェクト（`projectId: ...`）・上限を書いた短い system prompt を前置きし、ツールは同じ API 契約とディスパッチャから作る。`task.wait` / `integration.wait` は LLM のツールではない（`tool: false`）ので、旧プリセットのセッションにだけ Executor が足す。モデル呼び出しの上限とループ検出は §2.13 と同じ。
- **`task.spawnWorker`**：`ready` / `failed` / 人間待ちの `blocked` の Task だけ。`policy.assertCanSpawnWorker`（権限・プロジェクト・`maxWorkers`・深さ）→ worktree（Task に既にあれば再利用、なければ Task 名で作成）→ Worker セッション（`agent`、`parentSessionId` = 呼び出し元、Task・ワークスペース付き）→ `agent` Run（`parentRunId` = 呼び出し元の Run、`runtime` は指定 → 既定（上の「自動」を含む）を解決して記録）→ Task を `running`（`assigneeSessionId`・`workspaceId`）。worktree 作成以外は 1 トランザクションで、上限の判定から Run 開始まで await を挟まない。
  - agent が呼ぶと、Worker の Run に委譲 Grant（既定 `WORKER_DEFAULT_PERMISSIONS` = Task / ワークスペース / Artifact の読み取りを親が持つ範囲で、`lifetime: run`、`limits { maxWorkers: 0, maxDepth: 0 }`）を付ける。Worker は Worker を起動できず、Grant も作れない。
  - 予算：呼び出し元の Run に Budget があれば、そこから `budgetUsd`（省略時は空き ÷（残りの Worker 枠 + 1）。1 つ分は呼び出し元が自分の LLM 呼び出しのために残す）を切り出して Worker セッションの Budget にする。
- **`task.retry({ taskId, feedback?, integrationId? })`**：元の Worker に差し戻す。「元の Worker」は担当セッションのうち、その Task のために作られ（`session.taskId`）、同じプロジェクトで、Session Grant を持たない `agent` セッションだけ（それ以外なら新しい Worker を起動する）。前の Run の Budget を使い続けるのも、それがそのセッションに切り出したものであるときだけ。agent は `task.update` で担当セッションをその Task のセッション以外に向けられない（別プロジェクトのセッションは誰でも不可）。`review` / `failed` / `ready` / 人間待ちの `blocked` の Task で、Worker セッションと worktree が残っていれば、そのセッションに差し戻しメッセージ（指摘＋ `integrationId` があればその統合のエラー・テストコマンド・出力の末尾 4000 文字）を足し、同じ worktree・ブランチで新しい `agent` Run（`retryOfRunId` = 前の Run、Runtime は自分のセッションを再開）を始めて Task を `running` にする。権限・上限・委譲 Grant は spawn と同じで、Budget は前の Run のものがまだ有効なら使い続ける。Worker が一度もいない Task は `task.spawnWorker` と同じ（指摘は追加の指示になる）。
- **Worker の終了**（`run.status_changed` の終端を orchestrator モジュールが購読）：その Task を担当中（`running` かつ担当セッション）なら、`completed` → `review`（変更なしは `statusReason: no_changes`、`resultSummary` に最後の発言）、`failed` / `cancelled` → `failed`（`worker_failed` / `worker_cancelled`）、`interrupted`（デーモンの停止・再起動）→ `ready`（`statusReason: interrupted`。`task.retry` で同じ worktree から再開できる）。worktree とブランチは残す。人間がキャンセルした Task などはそのまま。起動時にも同じ照合をする。
- **Orchestrator の再開**（concept §8.4、`orchestrator/resume.ts`。旧プリセットだけ。指揮役は §2.13）：起動時（全モジュールの start の後）、`daemon_restart` / `daemon_shutdown` で `interrupted` になり、まだセッションの最新 Run である `orchestrator` Run ごとに、そのセッションへ system メッセージ（`ORCHESTRATOR_RESUME_NOTICE` で始まり、中断した Run の ID・そのセッションが作った Task と統合の状態）を 1 回だけ投稿する。`settings.autoResumeOrchestrators` と `settings.autoResume`（既定 true）かつセッションの Orchestrator Grant がまだ有効なら、そのメッセージを起点に新しい `orchestrator` Run を始める（`lifetime: run` の Grant は `work` として扱われ、中断では失効しない）。モデルは `task.list` で状態を読み直し、中断された Task を `task.retry` で再開して計画を続ける。
- **待機**：`task.wait({ taskIds, mode: any|all, until: settled|review_or_terminal|terminal, timeoutMs })` は状態を確かめてから `bus.waitFor` で眠り（ポーリングしない）、`call.signal` で打ち切る。返すのは `reached`（ID）と全 Task の `TaskSnapshot`（状態・理由・ブランチ・最新 Run と activity・承認待ち数・diff 統計・要約）。`integration.wait` は統合が `awaiting_approval` / `conflict` / `failed` / 確定状態になるまで待つ。LLM のループは「spawn → task.wait(all) → integration.create → run → integration.wait → 報告」だけで済む。
- **判断の記録**：`orchestrator.decision` イベント。LLM は `orchestrator.recordDecision` で残し、デーモンも自分の判断（Worker を起動した・Task をレビュー待ち / 失敗にした）を `system` actor で残す。参照は呼び出し元（Orchestrator）のセッションと Run に付ける。
- **`mock/orchestrator`**（`orchestrator/mockModel.ts`）：`session.spawn` がツールにあれば指揮役の状態機械（`mockSupervisor.ts`、§2.13）、なければ以下の旧プリセットの流れ。旧プリセットの流れはツール結果だけを見て次の手を決める決定的なモデル。判断の記録つきの報告は「記録だけの返事 → ツールなしの報告」の 2 回に分ける（ツール付きの報告は結果のたびに繰り返されるため）。目標 → `task.create` ×2（ドキュメントとテスト、完了条件と mock Worker 用の `acc-mock` 計画つき。テスト側はテストを実行し、続く `git push` は絶対ルールで拒否されて、理由を読んでコミットだけして終える。おまかせでは統合の反映まで承認は 0。慎重ではテストの実行が承認になり、却下されたら失敗）→ `task.spawnWorker` ×2 → `task.wait` → `integration.*` → 日本語の報告。途中で失敗があれば統合せず報告する。統合が `conflict` なら `integration.resolveWithAgent` を 1 回だけ呼んで待ち直し、まだ `conflict` なら人間に相談する。テスト失敗では `task.retry`（`integrationId` つき）を対応案として示す。再開メッセージの後は `task.list` → 中断 Task の `task.retry` → 通常の流れ（作成済みの統合があれば作り直さず `integration.run`）。目標に「README」を含むと両 Task が README.md に追記する（コンフリクトの再現用）。本物のモデルと同じツールしか使わない。
- **デモモード**：`system.setupDemo({ name='launch-demo' })`（冪等）。git なしの「新製品ローンチ準備」：`<ACC_HOME>/demo/<name>` のフォルダ（製品概要 `brief.md`）、`folderPath` のプロジェクト、`mock/orchestrator` の「デモ: 新製品ローンチ準備」を `session.delegate`（4 人・$3・`lifetime: session`）で任せた状態にし、定期実行が使えれば週次レポート（月曜 9:00）を 1 本足す。結果の `repoPath` はそのフォルダ。目標（`DEMO_GOAL_HINT`）を送ると、指揮役が調査・FAQ（質問 1 件つき）・告知文の 3 人に任せる。旧デモの Node プロジェクトは `DEMO_FILES` として監査の場面（`scripts/audit-scene.ts`）用に残す。

### 2.13 受信箱と起床（T1 Supervisor）

指揮役（supervisor）は**イベント駆動**：1 回の実行は「計画・指示して返事をしたら終わる」。子が動いている間、指揮役の会話には実行がない（いつでも話しかけられる）。仕様は `docs/snapshot/20261029_redesign-spec.md` §3.2・§3.10・§3.13。

- **任せる**：`session.delegate`（人間だけ。`sessions/methods/delegate.ts` → `orchestrator/grant.ts`）がチャットに `SUPERVISOR_PERMISSIONS`（`session.spawn/send/stop/resume/tree/get/messages/update`、`artifact.list/get/read/review/publish`（publish は自分の結論。話し合いのまとめなど）、`attention.list/respond`、`human.ask`、`cost.summary`、`orchestrator.recordDecision`、`project.get`）を付ける。`allowSchedules` なら `schedule.*`、プロジェクトに `repoPath` があるときだけ `integration.create/run/get/list/resolveWithAgent`・`workspace.diff`。`limits { maxChildren（既定 4）, maxSchedules, maxDepth: 1 }`、プロジェクトがあればその限定（なければ会話の木のスコープだけ）、ルート予算（既定 $3。既にあれば使い続ける）。もう一度呼ぶと前の Grant を取り消して作り直す。`session.undelegate` で外す。役割の判定は「`session.spawn` を許す Grant を持つ」（`inbox/supervision.ts` の `isSupervisor`）。`session.grantOrchestration` は `session.delegate` の別名（§2.12）。
- **リード（コードの会話が自分の仕事を分ける）**：親のないエージェントの会話がプロジェクト（リポジトリあり）の worktree で動くと、実行の始まりに daemon（system `lead`）が指揮役の権限を付ける（`orchestrator/grant.ts` の `ensureLeadGrant`。ボタンなし：頼まれた仕事が許可）。中身は `supervisorPermissions({ schedules: false, code: true })`、そのプロジェクト限定、`maxChildren` 4・深さ 1、`lifetime: session`、reason `lead`。予算は作らない（会話だけのときと同じく今日の上限の中で使う。会話に予算があればそれが子も縛る）。子・繰り返しの発火・Task の Worker・すでに率いている会話には付けない。ツールは Grant から作るので、最初の実行から `session_spawn` などが渡り、前提（`conversationFrame` の `leadLines`）に「並列に分けるとき」の段落が入る：子は `session_spawn`（mode agent、そのプロジェクトの worktree）、自分では worktree を作らない、待たずにターンを終える（`[状況の更新]` で起こされる）、子の変更を確かめてだめなら `artifact_review`（redo）、全員終わったら `integration_create`（`sessionIds`：子、最後に自分）と `integration_run`。起床はエージェントの会話なら Claude Code の実行（`runKindFor`、Runtime は自分のセッションを再開）。親の実行中に来た更新は、その実行の終わりに渡る。
- **子の worktree は親の今から**（`Spawner.fromCallersBranch`）：worktree の親（agent の実行）が `baseRef` を書かずに同じプロジェクトの worktree の子を起こすと、daemon が親の途中の変更をコミットし（`会話「題」の途中の変更`）、親のブランチから子の worktree を切る。子は既定ブランチではなく親の最新の作業の上で始まる。`baseRef` を書けばそのまま。
- **受信箱**（`inbox/`、サービス `inbox` / 具体クラス `supervisorInbox`、表 `inbox_items`）：起床の唯一の入口。`deliver(sessionId, { kind, refs, actor, interrupt?, model? })` が決める：
  - 発言（`user_message`、メッセージ付きの `answer`）：実行がなければすぐ新しい Run（trigger `user`、答えは `wake`）。実行中の会話・指揮役は次の区切りで差し込み（`injected`）、エージェントは今の Run の後（`queued`。1 通ずつ順に Run）。エージェントへの `interrupt` は今の Run を `cancelled`（`superseded`）にして新しい Run に渡す（Runtime は自分のセッションを再開）。待っている発言は `Message.delivery: queued`、渡した時点で `delivered`（`message.updated`）。人間の発言は止まっている会話の `supervision` を `active` に戻す。**作業の選択（`workPlace` / `workModel`、右腕への依頼）を持つ人の発言は 1 通で 1 Run**：差し込まず、ほかの発言とまとめず、それで始まった Run にはほかの発言を差し込まない（`assistant.startWork` は Run の trigger の選択を使うので、2 つ目の依頼が 1 つ目の作業場所で動かないように）。後ろの発言はそれを追い越さない。チャットの履歴（`chatHistory`）は `queued` の発言を含めず、後の Run が受け取った発言は、その Run の始まりの位置（受け取った Run の id の時刻）に並べる（実行中の Run の最後の返事より前に保存されていても、返事の後に読ませる）。
  - それ以外（`child_update` / `budget` / `resume`、メッセージなしの `answer`）は指揮役を起こす材料。`supervisor.wakeDebounceMs`（1.5 秒）待ってまとめ、1 通の system メッセージ（`[状況の更新]` で始まる LLM 向けの本文 + `meta.wake` の `WakeItemView`）と `orchestrator` の Run（trigger `wake`）にする。項目は `consumedByRunId` 付きで consumed（`inbox.added` / `inbox.consumed`）。子の更新は起こす時点の状態で書き（もう動いている子は省く）、同じ子の未処理の項目は新しいもので置き換える。
  - `drain(runId)`：区切りで渡す発言を取り出す（Executor の `inject`）。Run の開始時にも呼び、履歴に入っている発言を delivered にする。
- **子の更新**：子の Run の終了・`task.updated`・`attention.*`・`session.state_changed` のたびに子の状態を §3.7 の導出（`home/state.ts`）で読み、`done / failed / review / needs_you` に入ったら（状態と最新 Run の組で 1 回）、親が指揮役なら `child_update`。親への子の結果の報告はここが唯一の出どころ（T2 の終わり方は報告しない）。`stopped` は `session.stop` が知らせる（止めたのが親自身なら知らせない）。
- **日次上限の間は起こさない**：今日の上限に達している間（`ledger.dailyLeft() <= 0`）は起床をせず、項目を pending のまま残す。出番 `budget` が閉じたら（引き上げ・設定の変更）`pokeAll` で残った会話を起こす。
- **ツールループ**（`llm/toolLoop.ts`）：`inject` を区切り（そのターンのツール結果をすべて返した後）と「ツールなしで答えた直後」に呼び、届いていれば続ける。差し込みの本文は「（作業中に届いた発言）」で始まる。`failOnTurnLimit` で `maxTurns` 超えを `RunStopError('turn_limit')`、同じツール呼び出し（引数込み）か同じ本文の 3 連続を `RunStopError('loop_detected')`。モデルが応答を断った（終了理由 `content_filter`。Anthropic の `refusal` も、Responses API の `incomplete_details.reason: content_filter` も各プロバイダでこれにそろえる）ら、空の返事で完了にせず `LlmError('llm_refused')` で失敗にする。費用は数え、断る前に出た本文は残し、ツール呼び出しは実行しない。同じ依頼はまた断られるので再試行しない。チャットと指揮役の Run は `supervisor.maxModelCallsPerRun`（24）で使う。
- **指揮役の Executor**（`orchestrator/executor.ts`）：中立の system prompt（`buildSupervisorPrompt`。コードの断片は repo があるときだけ）＋木のスナップショット（`treeSnapshot`：`[id] 「題」 state=… outputs=…`）、最初の依頼、直近の `supervisor.contextMessages`（40）件まで（半分ずつまとめて切る。上の「プロンプトキャッシュの形」）。起床のメッセージは user のターンとして送る。
- **暴走の防止**：`turn_limit` / `loop_detected` で失敗した Run は出番 `stuck` を開き `supervision: paused`。人間の発言なしの起床が 1 時間に `supervisor.maxWakesPerHour`（30）に達したら `paused` + `stuck`。`paused` の会話は起こさない（項目は pending のまま）。指揮役の Run が一時的なエラー（429 / 5xx / タイムアウト / 接続断）で失敗したら 1・5・15 分後に `resume` 項目で起こし直し、4 回目からは出番 `failure`。
- **止める・再開**：`session.stop({ sessionId, tree=true })` は指定した会話と、子孫のうちまだ作業がある会話（実行中の Run、`pending / ready / running / blocked` の Task、指揮役）を `supervision: paused`、それらの終わっていない Task を `paused`、実行中の Run を `cancelled`（`stopped_by_user`）にする（Task を先に止めるので、Run の終了を追う側は失敗にしない）。作業を終えた子（done・確認待ち `review`・failed）はそのまま（「停止中」に見せず、再開で終わった作業をやり直さない）。`session.resume({ sessionId, tree=true, message? })` は止まっている会話を `active` に戻し、止めた時点で切れた作業を同じ会話で Run（trigger `resume`）し直し、Task を `running` に戻す。指揮役自身はすぐには動かさず、溜まった項目か `message` で起きる。agent が再開できるのは `assertAgentMayStartRun` が許す会話だけ。
- **再起動**（`orchestrator/resume.ts` の `resumeAfterRestart`、全モジュールの start の後）：中断された Run ごとに `resume` 項目を 1 つ。`settings.autoResume` なら、指揮役は通常の起床、子のエージェント（旧プリセットの Worker 以外）は同じ会話・作業場所で新しい Run（trigger `resume`、本文「再起動で中断されました…」）。再開の Run 自身が中断されたら、もう自動では再開しない（再起動のループで費用を使い続けない）。普通の会話は再開しない。
- **モックの指揮役**（`orchestrator/mockSupervisor.ts`）：最後に来たもので決める状態機械。目標 → `session.spawn` ×3（調査・データ・文書。ローンチの目標なら調査・FAQ・告知文、repo があれば 1 つは worktree）＋ `recordDecision` → 結果に本文だけ → 起床ごとに「n/3 件が終わりました」→ 全員そろったら成果物の題を並べた最終報告（ツールなし）。質問は依頼文に答えがあれば `attention.respond`、なければ人に残す。「いま何してる？」は `session.tree`、「止めて」は動いている子の `session.stop`、「N 人追加して」は最初の依頼で `session.spawn` × N（＋ `recordDecision`）。
- テスト：`inbox/supervisor.test.ts`（受け入れ）、`inbox/inbox.test.ts`、`llm/toolLoop.test.ts`、`orchestrator/mockSupervisor.test.ts`。`inbox/testkit.ts` は `session.spawn`（T2）・`session.tree`（T7）がスタブの間だけ代役を入れる。

### 2.14 子を起こす・作業場所・完了（T2）

仕様は `docs/snapshot/20261029_redesign-spec.md` §3.3・§3.4・§3.12。契約は `SpawnerService.spawn`（実装 `sessions/spawn.ts` の `Spawner`、`session.spawn` と定期実行が使う）、型は `ext/spawn.ts`。

- **子 = 会話 + Task + 作業場所 + 予算 + 権限**：`session.spawn` は 1 トランザクションで、子の会話（`kind` = `mode`、題はそのまま、`parentSessionId`・`rootSessionId`・`brief`）、その作業を記録する Task（`tasks.createChildTask`：プロジェクトなし可、`dependsOn` = `after` の兄弟の Task、`autoStart`）、最初のメッセージ（`role: user`、本文 = 依頼と完了条件、`meta.brief`。定期実行の発火は `meta.schedule`）を作り、`orchestrator.decision`「「◯◯」を任せました」を残して、すぐ返す。プロジェクトは指定 → worktree のもの → 親のもの、の順。
- **作業場所**（`mode: chat` は持たない）：`none`（既定）→ `<ACC_HOME>/scratch/<sessionId>`（`kind: scratch`。会話のアーカイブから 30 日で削除。起動時と 1 日 1 回の掃除）、`folder` → ユーザーのフォルダ（`kind: directory`。その場で書き換え、git なし。フォルダ 1 つにレコード 1 つなので書き込める実行は 1 つ。agent が指定できるのはプロジェクトの `folderPath` の中だけ（`assertAgentFolder`。字面と実パスの両方で判定し、中のジャンクションで外へ出られない。右腕の `assistant.startWork` と AI が作る繰り返しの `run.workspace` も、作るのは system actor だが同じ検査をする。繰り返しは持ち主の会話のプロジェクトで判定）。agent は `session.update` で会話の作業場所（`workspaceId`）を付け替えられない。ACC_HOME とそれを含むフォルダは不可。`workspace.remove` してもフォルダは消さない）、`worktree` → 既存の git worktree（`repoPath` が必要）。git を既定にしない。`session.create` の `workspace` も同じ規則（`prepareWorkspace` / `attachWorkspace`）。
- **権限**（`policy.assertCanSpawnChild`。判定から実行開始まで 1 トランザクション）：agent は `session.spawn` を許す Grant（プロジェクトの範囲・自分の木の中）を持ち、委任の深さに空きがあること（既定 1：子は子を起こせず、子を親にもできない。超えると `limit_exceeded`）。同時に動ける子は `limits.maxChildren`（なければ `maxWorkers`）。枠が埋まっていれば子は作るが始めず（`runId: null`）、空いたら daemon が始める（待てるのは 1 つの親につき 16 まで）。人間・system は制限なし。
- **子の権限**：daemon（system）が基本の権限（`artifact.publish`・`human.ask`・`session.get`・`artifact.list`、reason `child`、lifetime `work`、`maxChildren: 0`）を必ず付ける。親の Grant からは委譲しないので、親が `artifact.publish` を持たなくても子は公開できる。`permissions` を渡すと、それは呼び出し元の Grant から部分集合の規則で委譲する（深さ +1）。
- **予算**：呼び出し元の Run に予算があればそこから切り出す（指定額、なければ「空き − 予約 2 回分」を残りの子の枠 + 1 で割った額。chat の子は 1 回の予約額を下回らない）。切り出せなければ何も作らずに `budget_exceeded`。予算のない agent は配分できない。人間は根の予算を付けられる。
- **始め方**：`after` の兄弟が `done` になる（Task が `ready` になる）か、親の子が終わって枠が空くと、一度も始まっていない `autoStart` の子を daemon が始める（trigger `spawn`）。起動時にも残りを始める。中断（`interrupted`）された子の再開は §2.13。
- **終わり方**（`workers.onRunEnded` → `onChildRunEnded`。`brief` を持つ会話の Task だけ。`outputs.finalize` の後）：完了 → 開いた質問があれば `blocked`（`waiting_for_human`）、確認が要れば（finalize・`reviewBy: human`・この Run のコードの変更）`review`（親が `session.spawn` を持てば親に `child_update`、なければ子に出番 `review`）、それ以外は `done`。失敗 → `failed`（予算切れの出番 `budget` は §2.17 の cost モジュールが開く、`turn_limit` / `loop_detected` は `stuck`、`daily_limit` は全体の出番に任せる、その他は `failure`）。止めた → `paused`（`stopped`。`session.stop` を通らない停止だけここから親に `child_update`、親自身が止めたときは知らせない。`superseded` は何もしない）。再起動 → `ready`（`interrupted`）。それ以外の親への報告は受信箱（§2.13 の子の更新）。Run の終了から Task が動くまで（成果物の確定中）の状態は `working`（§2.19）。予算の返却は §2.17。子の会話で新しい Run が始まると（回答・やり直し・メッセージ）Task は `running` に戻る。
- **やり直し**：子の `task.retry` は同じ会話・同じ作業場所で新しい Run（trigger `retry`、Runtime のセッションを再開）。親から動かす規則は `session.send` と同じ（§2.4）。予算は有効なら使い続け、返却済みなら呼び出し元から切り出し直す。chat の子には `session.send` で伝える。
- **Runtime への入力**：`writeRoot` = 作業場所、`readRoots` = プロジェクトの `folderPath` / `repoPath`（存在し、作業場所でも ACC_HOME を含むものでもないもの）。ゲート（`runtime/policy.ts`、コマンドは `commandPolicy.ts` の `readable`）は読み取り root の中の読み取りを作業場所の中と同じに扱い、書き込みは `outside_write` のまま、中の資格情報（名前で判定）は拒否、ACC_HOME を含む root は無視する。プロンプトは作業場所ごとの 1 段落で、git・コミット・worktree に触れるのは git のワークスペースだけ。子には「最後に何をしたかをまとめる（成果物として残る）／人の判断が要れば質問を残して区切る」を添える。
- `task.spawnWorker` の会話の題も Task 名だけ（「Worker:」なし）。判断の記録にブランチ名・ランタイム名を書かない。
- **プロジェクトを外す**（`project.update { archived: true }`）：一覧と作業場所の選択から消えるので、見えないところで動き続けないよう、そのプロジェクトの会話（とその下）で動いている作業を止め、繰り返しをオフにする（会話のアーカイブと同じ。`stopProjectWork`）。会話・成果物・フォルダはそのまま。戻しても止めたものは止まったまま。外したプロジェクトでは会話を始められず（`session.create` が `conflict`）、`inspectFolder` / `inspectRepo` の登録済みにも数えない（同じフォルダを足し直せば新しいプロジェクト）。誰が決められるかの検査（`checkHumanOnly`）は値の検査より先。
- `project.inspectFolder`：絶対パス・存在・フォルダか・アプリのデータフォルダ（`ACC_HOME`）を含まないか・その中でないかを日本語の理由つきで確かめ、git の中ならリポジトリのルート・既定ブランチ・テストコマンド、登録済みのプロジェクト（`folderPath` か `repoPath` が一致）を返す。読み取りだけ。`project.create` / `update` の `folderPath` も、`ACC_HOME` を含む場所（ホームフォルダ・ドライブのルート）は `invalid_params` で断る（エージェントがそこに書けると、データベースとトークンに届くため。中のフォルダはデモのプロジェクトが使うので、ここでは断らない）。

### 2.15 成果物とコードの工程（T3）

§1.5・§3.4・§3.5。実装は `outputs/`（公開・読み取り・確認・finalize）と `integration/`（記録・統合）。型は `ext/outputs.ts`。

- **成果物**：ユーザーに見せる `role: output`（`document` / `data` / `link` / `files` / `diff`＝コードの変更）と、確認の記録 `role: evidence`（`commit` / `test_result`、統合結果の diff）。`source` は `published`（公開）/ `final_message`（最後の回答）/ `tracked_writes`（書いたファイル）/ `workspace_diff`。`review.state` は `none` / `pending`（人の判断待ち）/ `accepted` / `rejected`、変化は `artifact.updated`（`["review"]`）。旧 `note` / `file` の行は書き換えず、`artifact.get` / `list` とイベントで `document` / `files` として見せる（`outputs/legacy.ts`。`kind: document` の絞り込みは旧 note も拾う）。`artifact.list` の `role` は旧行を kind の既定で判定、`rootSessionId` は木の全会話。
- **`artifact.publish`**（agent の実行からだけ）：その実行の会話・Task・作業場所に付く。`path` / `paths` は作業場所の中だけ（字面と実パスの両方、`.git` は不可。ゲートの書き込み判定と同じ）。上限は document 1 MB、data 5,000 行・2 MB（CSV / JSON のファイルからも読める）、files 500 件（フォルダは展開、`.git` とシンボリックリンクは飛ばす）、link は http / https だけ。理由は日本語＋英語でエージェントに返す。
- **`artifact.read`**：UTF-8 の `limit` バイト（既定 64 KiB、文字の途中で切らない）を `offset` から。data は CSV、link は URL、files は 1 ファイルを作業場所から読む（`path`。作業場所の外を指していれば拒否、バイナリは拒否）。
- **スコープ**：`artifact.get` / `read` / `review` / `list`（会話を指定したとき）は成果物の会話を `CallScope.sessionIds` で返す。agent は自分の木の成果物しか触れない。
- **finalize**（`outputs.finalize(run)`、子の実行の終了時に T2 が呼ぶ）：公開済み → worktree なら最新のコードの変更（executor がコミット後に記録した diff。変更のない再実行は作業場所の最新 diff）→ フォルダ / scratch なら公開していない書き込み（`tool.called` の Write / Edit / MultiEdit / NotebookEdit から。エラーになった呼び出し・外・`.git`・消えたファイルは除く。シェルの書き込みは見えない）を 1 つの `files` に → 何もなければ最後の assistant 本文を `document` に。`needsReview` はコードの変更があるか `brief.reviewBy: human`。待つ成果物は `review.state: pending`。同じ実行で何度呼んでも増えない。
- **`artifact.review`**：`accept` は人間だけ（agent は Grant があっても `forbidden`）。コードの変更は、その変更だけの統合を `preApprovedBy`（採用した人）付きで作って実行し、テストが通れば自動で反映する（作業場所の最新の diff だけ採用できる。反映中の二重採用は同じ統合を返す）。それ以外の成果物はすぐ `accepted`、その実行に待つものが残らなければ Task を `done` にして子の予算を返す。`redo` は人間と、自分の木の agent（依頼者）。Task があれば `task.retry`（指摘を付けて同じ子・同じ作業場所。失敗した採用の統合があればそのテスト出力も渡す。`done` の Task は `review` に戻してから）、なければ `session.send`。その成果物と同じ実行の待ちの成果物は `rejected`。
- **統合の追従**（`integration.updated` を購読）：`applied` → 含まれる Task を `done`、その作業場所の diff を `accepted`、子の切り出した予算を返す、関係する出番を解消。採用の自動反映でない `awaiting_approval`（指揮役の統合、手動の再実行、反映先が早送りできなかった採用）→ 出番 `review`（作った指揮役の会話、採用なら子の会話。refs `integrationId`）。採用の統合が `failed` / `conflict` → 子の会話に出番 `failure`（「〜のテストが失敗」、choices やり直し / 終える）。`rejected` / `cancelled` → 出番を解消。
- mock の手順 `publish`（`artifact.publish` の params）は Control API ツールを通して公開する（Grant になければツールのエラーとして続ける）。

### 2.16 出番と質問（T4）

spec 20261029 §1.6・§3.6。`attention/`：`AttentionManager`（`ctx.service('attention')`、表 `attention` の唯一の書き手）、メソッド `human.ask` / `attention.list` / `attention.respond` / `attention.dismiss`、型は `ext/attention.ts`。

- **出番を開く**：`open(input)`。題は 1 行 80 字に丸め、choices / allowText は種類の既定（`ATTENTION_DEFAULT_CHOICES`）、並び順 `priority` は種類の基本値＋作成時刻（`attention/priority.ts`。承認 → 質問 → 予算 → 止まっている → 失敗 → 確認待ち、同じ種類は古い順）。同じ種類・会話・`refs` の開いた出番があればそれを返す（質問は題も同じとき。`budgetId` のない予算＝日次上限などはアプリ全体で 1 件）。`attention.opened` / `attention.resolved` の envelope は会話とプロジェクトだけ（Run・Task のイベント一覧には入れない）。
- **だれが開くか**：承認は attention 自身が `approval.requested` から（会話のない統合の承認は統合を作ったエージェントの会話。見つからなければ出番にしない）。題は `approvalTitleFor`（`runtime/tools.ts`）の名詞句「pnpm add zod を実行」「faq.md を編集」で、「承認しますか」を付けない（古い題の承認も payload から作り直す）。質問は `human.ask`。失敗・確認待ちは子の終わり方（§2.14）、予算は台帳（§2.17）、止まっているは指揮役（§2.13）が `open` を呼ぶ。
- **自動で閉じる**（`attention/sync.ts`、コミット済みのイベントだけを見る）：承認の回答・取り消し → その承認の出番。会話に新しい Run（`run.created`：再試行・再開・指示） → その会話の failure / stuck。Task が `review` を出た → その review、`running` / `done` / `cancelled` → failure / stuck。成果物の `review.state` が accepted / rejected、統合が applied / rejected / cancelled → その review。予算に空きが戻った（増額）・返却 → その budget。会話のアーカイブ → 承認以外の出番。
- **`session.archive`**：木ごと UI から見えなくなるので、見えないところで働き続けないよう、アーカイブするときに木の中で動いている・指揮しているものを `session.stop`（`tree: true`）と同じく止め、木の会話が持つ有効な繰り返しを `enabled: false` にする。戻しても再開しない（止まった木として見える）。
- **`human.ask`**（agent だけ。permission `human.ask`、自分の会話）：出番 `question` を作って `{ attentionId, status: 'asked' }` を返す（非ブロッキング）。選択肢は `c1`…（先頭が primary）、80 字を超える質問は題を丸めて全文を detail に。選択肢がなく allowText も false は不可。refs `{ askedBySessionId, runId }`。
- **`attention.respond`**：開いた出番だけ（対応済みは `conflict`。人間と指揮役の早い者勝ち）。choiceId はその出番の選択肢、text は allowText のときだけ。agent は自分の木（scope `sessionIds`）の、自分以外の会話の question だけ（他は `forbidden`）。振り分け（`attention/respond.ts`、応答者として呼ぶ。失敗したら出番は開いたまま）：approval → `approval.respond`、failure.retry → `task.retry`（refs の Task、指示は feedback）/ `run.retry`、review.accept → `integration.approve` / `artifact.review accept`、review.redo と文章だけの review → `artifact.review redo` / `task.retry` / `integration.reject`、budget.add_N → `budget.raise`（その予算で止まった最新の Run は `run.retry` で続ける）、budget.raise_today_10 → `cost.raiseDaily`（直近 1 日に日次上限で止まった各会話の最新の Run を `run.retry` で続ける。指揮役は受信箱が起こす）、stuck.continue → `session.resume`（文章は message）、*.stop → `session.stop`、それ以外の文章だけ → `session.send`。

### 2.17 費用と予算（T5）

§1.10・§3.8。サービスは `ledger`（`cost/service.ts` の `UsageLedger`）、型は `ext/cost.ts`、表は `usage_ledger`（金額は整数マイクロドル、`day` は `settings.limits.timezone` の日付、`input_tokens` のうちプロンプトキャッシュから読んだ・書いた分 `cache_read_tokens` / `cache_write_tokens`）・`cost_daily_raises`・`cost_notices`。

- **台帳が唯一の入口**：Run に記録する使用量（`runs/usage.ts` の `UsageAccountant`：`reportUsage`・`BudgetHold.settle`）は同じトランザクションで `ledger.record` に 1 行を足し、`Session.cost`（`ownUsd`、自分と子孫の `treeUsd`、`source` は含めた行のうち最も弱いもの）を会話と祖先すべてに加算する（`Session.cost` を書くのは台帳だけ）。`session.cost_updated` は会話ごとに 1 秒に 1 回まで（最初の変化はすぐ、残りはまとめて後で 1 回。`cost/throttle.ts`）。起動時、台帳に行のない終端 Run を足し、`Session.cost` を台帳から再集計する。
- **推定と確定**：Runtime は実行中の使用量を `phase: estimate` で報告できる（Claude はトークン数×単価、mock は手順ごと）。推定はその場で Run・台帳・予算に積むので、上限は実行中に効く。次の `final` の報告がそれまでの推定を置き換え、差は `component: adjust` の行（負も可、トークン数も）と `BudgetService.adjustSpend` で補正する。確定値の出どころが `unknown`（Runtime も価格を知らない）で推定より小さいときは推定を残す。確定の来なかった推定（中断など）はそのまま `estimated` で残る。分類器の費用（`component: classifier`）は補正の対象外。
- **予算の上限**：予算の空き（`available`、§2.5）が 0 以下になった Run は止める。祖先が超過して空きがなくなったときは、その祖先の下で動いている Run もすべて止める。Agent Runtime には `AgentRunInput.maxBudgetUsd`（`spendCapUsd`：予算の空きと今日の残りの小さいほう、どちらもなければ null）を渡す。
- **1 日の上限**：`settings.limits.dailyUsd`（既定 $20、null で無効。初回の確認は出さない）＋その日だけの引き上げ（`cost.raiseDaily`、人間だけ）。LLM 呼び出しの予約の前、Agent の開始前、使用量の報告ごとに `ledger.assertDailyLeft` で確かめ、超えていれば新しい呼び出しを拒否し（`budget_exceeded`、`data.reason: daily_limit`）、動いているエージェントをすべて止める（`statusReason: daily_limit`）。日と上限の組ごとに 1 回だけ `cost.limit_reached` と出番 `budget`（題「今日の費用が上限（$20）に達しました」、choices `raise_today_10`「今日だけ +$10」/ `open_settings`「設定」。前の日次の出番が開いていれば作らない）を出す。`raise_today_10` は `attention.respond` が `cost.raiseDaily({ addUsd: 10 })` に送る。`open_settings` は UI が設定画面を開く選択肢で、daemon への respond は `conflict`。今日に余裕ができたら（`cost.raiseDaily` の後、`settings.updated` の `limits.*` の後）開いている日次の出番を閉じる（`resolveDailyNotices`）。指揮役は上限に達している間は起こさない（§2.13）。
- **子の予算の返却**：子の会話が担当する Task が `done` / `failed` / `cancelled` / `review` になり、その会話に動いている Run がなくなったら、その会話を subject にした切り出しの Budget（親あり）を返却する（`cost/returns.ts`。Run の終了と Task の変化の後、と起動時）。人間が付けた会話の根の Budget は返さない。その Budget 自身が尽きて失敗した Task（`budget_exhausted`）も返さない（返すと出番 `budget` が閉じ、人が増やせなくなる）。再試行（`task.retry`、子のやり直しも）は、呼び出し側に予算がなければ返却済みの Budget を `reallocate` で親から同じ額だけ切り出し直す。
- **出番**：予算切れで失敗した Run は出番 `budget`（refs `budgetId`、+$1 / +$5 / 止める）。Run の種類によらずここだけが開く（子の終わり方も開かない）。LiteLLM のキーの予算超過（`llm_quota_exceeded`）は全体で 1 件の出番 `budget`（choices なし。LiteLLM の管理者に頼むしかない）。
- **メソッド**：`cost.summary`（`today` / `7d` / `30d` / 期間、`groupBy` は `day` / `project` / `root` / `model`、`rootSessionId` はその会話と子孫。agent は自分の会話の木だけ。`daily` に今日の上限と使用額）、`cost.raiseDaily`、`budget.raise`、`session.setBudget`（会話の Budget を作る・変える・null で返却。人間だけ）。
- **キャッシュの効き**：`Usage.cacheReadTokens` / `cacheWriteTokens`（`inputTokens` の内数、報告があったときだけ）をプロバイダが返す：Anthropic 直は `cache_read_input_tokens` / `cache_creation_input_tokens`、OpenAI Responses は `input_tokens_details.cached_tokens`、LiteLLM は `prompt_tokens_details.cached_tokens` か素通しの Anthropic の値、Claude Code はメッセージと結果の `usage`（再起動で前回の累計が分からないときは、結果からは付けず推定を残す）。Run の使用量と台帳に積む（記録を始める前の行は 0）。
- **呼び出しのログ**（`cost/calls.ts` の `CallLog`、`ctx.service('callLog')`、表 `llm_calls`、`CALL_LOG_DAYS` = 90 日で起動時に削除）：デーモンがするモデル呼び出し（会話・監督役・右腕のツールループ）1 回ごとに 1 行。誰が（`role`）・何回目（`turn`）・モデルとプロバイダ・結果（`ok` / `error` と `error_code` / `cancelled`）・所要時間と最初の応答までの時間・トークン（キャッシュの読み書きの内数）・費用。キャッシュの調査用に、送った**形**も残す（本文は残さない）：メッセージ数とツール数、ツール・先頭のシステムメッセージのハッシュ、次の呼び出しに残る部分（ツール＋先頭のシステムメッセージ＋最後の後ろのシステムメッセージの前までの履歴、`prefix_messages` 件）のハッシュ、**`prefix_continues`**（同じ会話・同じモデルの前回の残る部分で始まっているか。false はこちらがプロンプトの前を変えた＝こちらのバグ、true なのにキャッシュの読みが 0 ならプロバイダ側か期限切れ）と **`gap_ms`**（前回からの間隔。キャッシュは数分で切れる）。ログの失敗は呼び出しを止めない。エージェント（Claude Code）の呼び出しは含まない（使用量は台帳にある）。メソッド `usage.calls`（新しい順、会話・Run で絞れる）と `usage.stats`（期間のモデルごと：費用とトークンは台帳から、呼び出し・失敗・前が変わった回数・キャッシュの読み書きはログから。ログにない分をキャッシュの外れと数えないため、ログのないモデルの `cache` は null。`days` は期間の日ごとの費用とトークン（`models` にその日のモデル別の費用、多い順）で、使っていない日も 0 で入る）。どちらも人間と全体を見るエージェント（右腕）だけ。

### 2.18 定期実行（T6）

§1.9・§3.11。契約は `SchedulerService`（`rearm` / `fire`）、型は `ext/schedule.ts`、表は `schedules`（絞り込み列 `session_id` / `enabled` / `next_run_at`）。実装は `schedules/`：`time.ts`（いつ発火するか。純関数）、`scheduler.ts`（タイマーと発火）、`methods.ts`（`schedule.*`）。

- **時刻**：cron は 5 欄＋IANA タイムゾーン（`croner`、`mode: 5-part`。省略時は `settings.limits.timezone`）。`once` は 1 回だけ。作成・変更時に式・タイムゾーンを検証し、一度も実行されない設定（過去の `once`、過ぎた `expiresAt`）は `invalid_params`。`nextRunAt` は次の発火（`expiresAt` を越えたら null）。無効にすると null、有効に戻すと「いま」から次を計算する（止めていた間の分は取り戻さない）。
- **時計**：有効な定期実行のうち最も近い `nextRunAt` に setTimeout を 1 本だけ張る（unref、最長 2^31−1 ms で張り直す）。作成・変更・削除・発火のたびに張り直す。ポーリングしない。テストはタイマー（`TimerHost`）と spawner を `createSchedulesModule({ timers, spawner })` で差し替える。
- **取りこぼし**（`planDue`）：期限の来た定期実行ごとに、`nextRunAt` から「いま」までの発火のうち最新の 1 回だけを数える。遅れが `maxLatenessMin` 以内（`catchUp: latest`）／5 分未満（`skip`）なら実行、越えていれば `lastRun.outcome: missed`。起動時（モジュールの `start`）とタイマーの発火時（スリープ明けに遅れて来ても）に同じ規則を当てる。発火の前に `nextRunAt` を進めて保存する（途中で落ちても二重に走らせない）。
- **発火**（`fire`。発火と取りこぼしの処理は 1 本の列で順に行い、重なりの判定と子の作成が交錯しない）：
  1. 持ち主の会話がない・アーカイブ済み → `failed_to_start`。
  2. 重なり：直近の発火の子（`Session.scheduleId`）とその子孫に、終わっていない Run（created / queued / running / awaiting_approval）か、始まる前・実行中の Task（pending / ready / running）があれば `skipped_overlap`。終わった子（完了・失敗・人の出番待ち）は次の発火を止めない。
  3. 予算：人が作ったものは毎回 `run.budgetUsd` の根の予算。AI が作ったものは作った AI の会話の予算から毎回切り出す（空きが足りなければ `failed_to_start`＋出番 budget、予算が閉じていれば `failed_to_start`。AI の会話に予算が一度もなければ根の予算）。日次上限（`ledger.assertDailyLeft`）に達していれば `failed_to_start`。
  4. `spawner.spawn` を actor `system:scheduler` で呼ぶ：題 `<title> · 11/5 9:00`（定期実行のタイムゾーン）、依頼 = prompt（`includePrevious` なら直近の子の最新の成果物の題と冒頭 4,000 字を添える）、`mode` / `workspace`（agent のときだけ）/ `model` / `budgetUsd`（持ち主の会話がモックのモデル（`mock/…`、デモ）で定期実行にモデルの指定がなければ、agent は `runtime: 'mock'`、chat は `mock/echo`。費用のかからない木が、裏で毎週費用を使い始めないように）、`opts` = `{ scheduleId, scheduledFor, trigger: 'schedule', budget, supervise }`。子の `scheduleId`・最初のメッセージの `meta.schedule`・予算の作成は spawner が行う（`opts.budget` があれば依頼者の Run から切り出さず、`parentBudgetId` から `limitUsd` を切り出すか、null なら根の予算。足りなければ何も作る前に `budget_exceeded`）。`supervise` の発火は chat の子だけで、spawner がその子に指揮役のプリセット（`delegateSession`、lifetime `work`、同時 4 人、定期実行なし）を付け、最初の Run は `orchestrator` になる。
  5. `lastRun` を保存し `schedule.updated`（`["lastRun"]`）と `schedule.fired` を出す。
- **AI による作成**：permission `schedule.create`（ディスパッチャ）、持ち主の会話は自分の木の中（`CallScope.sessionIds`）、生きている（有効で次回のある）自分の定期実行は Grant の `limits.maxSchedules`（既定 5）まで（`limit_exceeded`）、`run.supervise: true` は `forbidden`、`createdBy` に agent を記録。発火はスケジューラ（system actor）が子を起こすので、spawn が agent にする検査を `assertAgentRun` が代わりにする：フォルダは持ち主の会話のプロジェクトの `folderPath` の中だけ、モデルは名簿の中だけ。作成・変更のときと、発火のたびに（その後プロジェクトや名簿が変わっていれば `failed_to_start`）。agent は人が作った定期実行を変更・実行・削除できない（根の予算を使わせないため。読むのは可）。フィルタなしの `schedule.list` は自分の木の分だけ返す。人間はどれでも止める・消すことができる。
- `schedule.runNow` は今すぐ 1 回発火する（`nextRunAt` は変えない）。始められなければエラー（重なりは `conflict`、予算は `budget_exceeded`）。`schedule.preview` は次の `count` 回（既定 5）。`schedule.delete` は発火で作った会話を残す。

### 2.19 ホームと状態（T7）

### 2.20 右腕（assistant）

構想は `concept.md` §1.3・§2・§3、仕様は `docs/snapshot/20261030_right-hand-spec.md`。「普段のチャットに権限を与えるだけで、ほかのエージェントを指揮してくれる」をそのまま形にした、**権限を持った 1 本の会話**。新しい実行エンジンはない。

- **1 つだけ**：`system.assistant` が返す（なければ作る。`kind: 'chat'`、題 `右腕`、モデルは空のまま）。何が右腕かは Grant で決まる（`reason: assistant`、`subject` がその会話。`AssistantService.currentId` はこの Grant から引く）。アーカイブと `session.delegate` は拒む（`conflict` / `invalid_params`）。
- **Grant**（`ASSISTANT_PERMISSIONS`、`lifetime: session`、`scope.allSessions: true`、`maxDepth: 0`、`maxSchedules: 20`）：見渡す `home.get`（`tool: true` にした）・`session.list/get/tree/messages/search`・`project.list/get`・`cost.summary`、動かす `assistant.startWork`・`session.send`・`session.stop/resume`、繰り返す `schedule.preview/create/update/delete/list/get`。**ない**：`attention.respond/dismiss`（出番は人のもの）、`session.spawn`（右腕の下に木ができるとホームが 1 本に潰れる。木は常に根）、`session.archive`、予算、設定、プロジェクトの変更、`system.*`。ツール一覧は Grant から生成されるので、プロンプトに書かなくても出番に答える道はない。
- **`assistant.startWork({ text, title?, delegate, projectId?, workspace?, model? })`**（人も呼べる）：`delegate` に既定値はなく、毎回決めさせる（既定が true だと「チャットを立てて」まで指揮役の木になった）。目安はプロンプトに：話したい・相談・「チャットを立てて」・一人でできる 1 つの作業は false（別のモデルで動かしたいだけなら名簿のモデルを渡せばよく、チームは要らない）、並行できる複数の部分があってまとめが要る仕事は true、迷ったら false（あとから人が ◇ で任せられる）。UI にあった create → delegate → send をデーモンに下ろしたもの。題は `title` か `text` の 1 行目（40 字）。`delegate` なら `session.delegate` の既定値（4 人・$3）で任せ、`text` を最初のメッセージとして送る（右腕が呼んだときは `createdBy` / `author` が system の `assistant`、会話では `◇ 右腕` から）。`text` は**右腕が書く、その会話への依頼**：いくつかに分けて立てるときは依頼もそれぞれの分だけにし（全文を各々に渡すと、どの会話も全体をやろうとして重複する）、人の言った固有の条件は残し、言っていないことは足さない。1 つだけなら人の言葉そのままでよい。右腕からは **1 Run に 3 本まで**（`limit_exceeded`、Run の終了で忘れる）。delegate なしで `workspace` があれば `agent` の会話。人が依頼に選んだ作業場所・モデル（`session.send` の `workPlace` / `workModel`）は、右腕の選択より優先し、その Run の trigger の発言から読む（`chosen`）。選択のある依頼は受信箱が 1 通ずつ別の Run にする（§2.13）ので、作業中に送った 2 つ目の依頼（別のプロジェクトでも 自動 でも）が 1 つ目の選択で動くことはない。
- **モデルと上限**：`resolveChatModel` が右腕を見分けて `settings.assistant.model` → `defaultModel`（名簿の「それ以外」）→ 接続先がなければ `mock/right-hand`、あれば最初の名簿を選んで保存（§2.11）。`delegate: false` で始める仕事には名簿から選んだモデルを渡す。右腕自身の呼び出しは `settings.assistant.dailyUsd`（既定 $2、null で無制限）まで。超えたら Run は `budget_exceeded`（「右腕は今日の上限（$2）に当たりました」）で失敗し、UI が欄の上に出す。立てた木の予算は任せ方の既定で、右腕の上限からは引かない。
- **履歴の覚え方**（`assistant/history.ts` `rememberPastRuns`）：終わった実行のツール往復は、呼び出しはそのまま（モデルが作る形のまま。文字の記録にすると真似される：本物の Haiku で確認）、結果は要約 `{ok, id, title, state, …}` か `{error}` に切り、reasoning は落とす。いまの実行の往復はそのまま。古い `home.get` や Session の JSON は次の瞬間には現実と違うので、状況は system prompt の `statusBlock` だけを正とする（Anthropic の context management が古い tool result を消すのと同じ考え方）。1 回の入力は「tools ＋ 役割 ≈ 7k ＋ 会話の文」でほぼ一定になる。
- **system prompt は 2 つ**（`assistant/service.ts` `systemPrompts`）：先頭（履歴の前）は実行をまたいで変わらない役割と会話自身の `systemPrompt`（tools と合わせてプロンプトキャッシュの接頭辞になれる）、2 つ目は毎回変わるもので**履歴の後ろ**に置く（前に置くと履歴がキャッシュされない）（最後の人のメッセージの `hint`（`作業場所の希望:`）と `statusBlock`）。`statusBlock`（`home.get` を 1 回呼んで、木ごとに 1 行：id・題・state・progress・needsYou・failed・nextRun。その下に子（12 人まで。題・state・now）と開いた出番の題、最後にプロジェクト一覧）。「今どう？」はツールなしの 1 回のモデル呼び出しで返る（本物の Haiku 5.5 で確認：`docs/snapshot/20261030_right-hand-real.md`）。
- **自分から話す**（`assistant/notify.ts` `AssistantNotifier`）：根の会話が `done` / `failed` になったら（`session.state_changed`。子と右腕自身は除く、根ごとに 1.5 秒の debounce、1 時間に 20 件まで、知らせる時点でまだその状態のものだけ）、右腕の会話に `system` メッセージ（`meta.wake`、`WAKE_MARKER` ＋「「題」が終わりました。できたもの: …」／「失敗しました」、成果物は最新 5 件）を置いて `inbox.deliver` で Run を始める。右腕はそれに 1 行で答える（プロンプトに規則あり。知らせから新しい仕事は始めない）。チャット Run では `meta.wake` のメッセージを監督役と同じく user の番として送る。
- **`mock/right-hand`**（`assistant/mockRightHand.ts`）：文の形で分ける。知らせ（`WAKE_MARKER`）はその本文をそのまま 1 行で返す。末尾 ？ か 今・どう・何 で始まる → `home.get` → 1〜2 行。止めて・停止 ＋ 木の題（文に題が含まれるか、動詞を切った残りが題に含まれる）→ `session.stop {tree}`。再開 → `session.resume`。毎朝・毎日・毎週（＋ N 時）→ `assistant.startWork {delegate: false}` → `schedule.create`（cron）。それ以外 → `assistant.startWork` → 「「題」を始めます。終わったら知らせます。」。同じ文を 2 回続けて返さない。ツールの失敗は「できませんでした。<理由>」。
- **UI**：§3 とユーザ向けの決めは `ui-design.md` §4.2・§5.1・§8.6。撮影の場面は `assistant.model` を `mock/right-hand` にし、`14-home-assistant`（今どう？の返事）と `62-assistant`（右腕の会話）を撮る。

### 2.21 AI 同士の会話（キャラ）

会議・壁打ち・ディベートのような「AI 同士で話す」ための専用の仕組みはない。指揮役（§2.13）が **キャラ（persona を持つ chat の子）** を立て、いつもの `session.send` で話を回す。新しい概念はキャラだけで、トークンを無駄にしない作りをデーモン側に置く。

- **キャラ**：`session.spawn` の `persona`（mode chat のみ、4,000 字まで。`Session.persona`、木のカードの `role: speaker`）。枠（`sessions/framing.ts`）に `<<<キャラここから>>>` で引用し、「その人物として話す・会話の 1 ターンとして短く（目安 300 字）・前置きやまとめを書かない」を足す。「依頼が済んだら結果をまとめる」は言わない。
- **発言は成果物にしない**：キャラの Run は `final_message` の文書を作らない（`outputs/finalize.ts`）。結論は指揮役が `artifact.publish` で残す（指揮役の Grant に `artifact.publish` を足した）。
- **発言は起床に本文ごと載せる**（`inbox/wake.ts` の `speakerReply`）：キャラの最新の Run の発言を `<<<「名前」の発言ここから>>>` で引用し（4,000 字まで）、`WakeItemView.reply` にも入れる。指揮役は読みに行くツール呼び出しが要らない。
- **発言は打ち直さずに渡す**（`session.send` の `forward`、8 件まで。`sessions/forward.ts`）：渡す相手の最新の発言（8,000 字まで）を名前つきの引用として、本文の前に text part で置く（`meta: { kind: 'forward', items }`）。指揮役の出力トークン（高い）と言い換えによるずれをなくす。渡す会話も呼び出し元の範囲に入っていること（scope）。まだ発言のない会話は `invalid_params`。`hint` / `workModel` / `workPlace` とは併用できない。
- **話している途中の発言をまとめて 1 回で起こす**（`Inbox.speakersHold`）：キャラのどれかが答えている間は、起床を最長 `SPEAKERS_HOLD_MS`（2 分）待つ。答え終わったキャラの項目がまた起床を予約するので、揃った時点で 1 回だけ起きる（キャラごとに指揮役を呼ばない）。キャラ以外の子は今までどおり。
- **人がキャラに直接話しかけた番は指揮役を起こさない**（`Inbox.evaluateChild`）：キャラの最新の Run の trigger が人の発言（立てたときの `brief` は除く）なら、その番は報告済みにして `child_update` を出さない（後からも出さない）。起こすと指揮役がもう 1 巡回して費用がかかるため。その番は `speakersHold` の「答えている」にも数えない。
- **回し方**はプロンプト（`orchestrator/executor.ts` の `DISCUSSION_GUIDE`）：2〜4 人、違うモデル（プロバイダをまたげるなら別々に）、同じ問いは同じ返事で全員に、反応させたいときは `forward`、1 人ずつ回すときは後の番の人を `start: false` で立てて番が来たら `session.send` で始める（「待って」と頼むと空の発言が出る）、発言は人に見えているので書き写さない・まとめない、雑談なら仕切らずに番を回すだけ、4 巡ほどで `artifact.publish` → 短い報告。右腕は「AI 同士で話させたい」を `delegate: true` で立てる（`assistant/prompt.ts`）。
- **トークンの形**：キャラの system（枠 + キャラ）は会話中変わらず、履歴は追記だけなので、各プロバイダのプロンプトキャッシュに乗る。指揮役は起床ごとに 1 回だけ呼ばれ、発言の本文を読みに行かない・書き写さない。
- **モック**：`mock/speaker`（`orchestrator/mockSpeaker.ts`。キャラの文から慎重派か前のめりかを決め、渡された相手に名前で反応し、意見 → 反応 → 具体案と進む）。モックの指揮役は「会議・壁打ち・ブレスト・ディベート・議論・話し合い・座談・対談」を含む依頼で 2 人（「3 人」なら 3 人）を立て、3 巡でまとめを公開する。木の行にはキャラに ` speaker` が付く（`SPEAKER_MARK`）。
- テスト：`orchestrator/discussion.test.ts`。撮影は監査シーンの D「朝食の定期便の企画会議」（`38-discussion`・`39-speaker`）。
- 話し手かどうかは `isSpeaker(session)`（protocol）：親があり、`persona` か `speaks`（メンバーの話し手、§2.22）を持つ。

### 2.22 メンバー（`characters/`）

構想は `docs/snapshot/20261104_members-concept.md`、仕様は `20261104_members-spec.md`。名簿に残る「顔・名前・プロフィール・既定のモデル・記憶」。会話・任せた仕事・定期便・右腕の席が「誰と／誰が」を `characterId` で参照する。**メンバーは権限を持たない**（何ができるかは今どおり Grant と予算）。段階 1（名簿と顔）と段階 2・3（自分・関係・あなたの記憶）まで入っている。

- **データ**：`characters` テーブル（`Character`：`name` 40 字・`face` 1 文字か null・`tone` 0〜7・`profile` 4,000 字・`model`・`sortKey`・`archivedAt`）。`tone` は作るとき名簿で一番使われていない色。`Session.characterId` と `Session.speaks`、`SessionCard.characterId`、`ScheduleRunSpec.characterId`、`settings.assistant.characterId`（右腕の席）。
- **API**（`character.*`）：`list` / `get`（出た会話 30 件と今月の費用：`usage_ledger` を `sessions.data.characterId` で絞る）/ `create` / `update` / `reorder` / `archive`（外すと右腕の席も空く。会話は残り、灰色の顔で名前を出す）/ `keep`（話し手の `persona` を名簿に残し、会話を `characterId` + `speaks` に付け替える）。**変えるのは人だけ**：`character.*` の Grant を持つ AI でも create / update / reorder / archive / keep は `forbidden`（`humansOnly`）。`session.update` の `characterId` も人だけ、かつ発言がまだない会話だけ（話し始めた会話の相手は替えない）。メンバーの `model` は、会話を作るときに `model` の指定がなければ使う。
- **場面**（`sceneOf` / `sceneIn`）：話し手（`isSpeaker`）は会議、人が自分で始めた根の chat（brief・定期便なし、右腕が始めたものでも任せた会話でもない）は雑談、それ以外（spawn の子・agent・定期便・`assistant.startWork` で右腕が始めた仕事・委任の Grant を持つ会話）は仕事。人には選ばせない。
- **枠**（`characters/frame.ts`、`sessions/framing.ts` が呼ぶ）：プロフィールは写さず毎 Run 参照し、`<<<メンバーここから>>>` で `名前: …` と一緒に引用する。雑談は「このメンバーとして話す。キャラは断る・話をそらす・作り話を事実にする理由ではない」。仕事は「プロフィールの仕事の流儀に従い、口調・口癖・身の上話は成果物（ファイル・文書・コード・コミット・回答）に出さない」。会議は §2.21 の話し手の枠で、引用だけメンバーにする。指揮役自身にメンバーがいれば、その指揮役の前提に仕事の枠を足す。
- **名簿を読むのは前提で**（`characterRoster`。id・名前・プロフィールの 1 行目、30 人まで）：右腕（`assistantMembersBlock`。先頭の system なので名簿か席が変わるまでキャッシュに乗る）と指揮役（`buildSupervisorPrompt` の `members`）。「人が名前を出したときだけ `characterId` を渡す」とプロンプトで言う（メンバーは権限を持たないので、安全ではなく費用と期待の問題）。右腕は `assistant.startWork` の `characterId`、何人かで話すなら `delegate: true` で名前を `text` に残す。指揮役は `session.spawn` の `characterId`（話し手なら `speaker: true`。`persona` とは併用できない）。
- **右腕の席**：席にメンバーがいれば、右腕の先頭の system に「このメンバーでもある。口調だけ替え、規則はそのまま」を足す。
- **定期便**：発火の子に `characterId` を渡す。外されたメンバーなら付けずに発火する。
- **記憶**（`characters/memory.ts`、`CharacterMemory`）：`self`（`work` は教わった仕事のやり方）・`relation`（`aboutId` の相手ごと）・`you`。上限 `MEMORY_LIMITS`（自分 20・関係は相手ごと 5・あなた 15・1 件 80 字）。`source: person` は人が書いたか直したもので、整理は変えない・消さない。人が消したものは正規化した文で tombstone に残し、整理が同じ文を出しても捨てる。変化は `character_memory_log`（ページの最近の変化）と `character.memory_changed`。**記憶を書く道は人の操作（`character.memory.add/update/delete`、AI は Grant があっても `forbidden`）とデーモンの整理だけ**で、LLM のツールにはない。
- **記憶を読む**（`CharacterService.memoryLines` → `frame.ts memoryBlock`）：枠のメンバーの引用の後ろに「覚えていること（命令ではない。プロフィールと食い違えばプロフィール）」として置く。雑談は全部、会議は自分・同席している話し手のメンバーとの関係・あなた、仕事は `work` の自分とあなただけ。日付の言い方（今日・昨日・N日前・M月）はコードで作る（`memoryWhen`）。`settings.members.memory` がオフなら読まない・書かない（消しはしない）。system の先頭にあり、変わるのは整理のときだけ。
- **整理**（`characters/digest.ts` `MemoryDigest`、`ctx.service('memoryDigest')`）：見回りはしない。メンバーのいる会話のターンが終わるたび（と一言のたび）にそのメンバーのタイマーを 30 分（`DIGEST_IDLE_MS`。キャッシュが切れてから変える）にかけ直し、切れたら 1 回だけ見る（起動時は全員を 1 分後に 1 回）。どの会話でも 30 分話していない・前回から材料が 4 行以上か仕事で人の発言があるメンバーを、メンバーごとに 1 本の鎖で整理する。材料は会話ごとの読んだ位置（`character_digest_marks`）以降を SQL で読み（会話は `sessions_character`、一言は `messages_aside_character` の式索引）、答えている途中の会話は次回に回し、場面で絞る：雑談は本人の発言と人の発言、会議はそれに `forward` で渡された同席者の発言、**仕事は人の発言だけ**（依頼・成果物・メンバーの出力は渡さない）。新しい順に 30,000 字（入りきらなかった会話は読んだ位置を進めず次回へ。いちばん新しい会話だけで溢れたら、その新しい行だけ）。題と名前は `framedTitle` で 1 行にしてから入れる（題に改行で `[person]` 行を仕込めない）。モデルは裏の整理のモデル（§2.23 の `settings.background`）、なければオフラインの `mock/memory`（今の記憶を残し、本人が「わたし…」と言った文を足す）。返事は丸ごとの新しい一覧（JSON、関係は相手の名前で）。デーモンが守ること：上限で切る、知らない名前を捨てる、tombstone を捨てる、人の項目を戻す、`corrections` は文の直しにだけ使い `person` には上げない（`person` にできるのは人の操作だけ）、**一度に自動の記憶の半分以上が消える結果は捨てる**（`rejected`。読んだ位置は進める）。失敗したらそのメンバーは 1 時間あけ、続けて失敗したら裏の整理全体が待つ（`BackgroundBackoff`）。人が書く記憶も同じ上限で断る。費用は ledger の `component: memory`（セッションなし）と `character_digests`（メンバーごと）。裏の整理の上限（§2.23）と全体の 1 日の上限で止まる。`character.digest` で今すぐ整理（人だけ）。`character.digestStatus` は整理の状態（記憶がオンか・今のモデルとそれがオフラインのモックか・まだ読んでいない行と足りているか・30 分静かになる時刻・失敗後の再試行と裏の整理全体の待ちの時刻・上限・前回の結果・最後の失敗の理由（デーモンが動いている間だけ））を返す。メンバーのページが「なぜ覚えないか」を出すため。
- **一言**（`character.aside`、`characters/aside.ts`。人だけ）：`@名前` で会話にメンバーを呼ぶ。ツールなしの 1 回の呼び出しで、system は短い専用の枠（メンバーの引用・その会話の場面の記憶。会議は雑談として読む）、user はその会話のあらすじ（§2.23。遅れていればその場で畳んでから）を `<<<あらすじここから>>>` で、あらすじより後の発言（24 件・12,000 字まで、ツール・通知・hint は除く、`あなた:` / `AI:` / メンバー名つき）を `<<<会話ここから>>>` で引用し、人の文を続ける。あらすじがない・使えないときは直近 12 件。モデルはメンバー → 会話 → `defaultModel`。答えが来てから、人の文（`meta: aside, reply: false`、作者は人）とメンバーの答え（`reply: true`、作者は system の `member`、role は user）を同じトランザクションで足す（失敗したら何も残らない）。どちらも Run を始めない。会話自身のモデルは次の番に `[メンバー「名前」から] …` として聞く（`SPEAKER.member`）。費用は会話の ledger と `character_calls`（メンバーの今月に足す。メンバー自身の会話での一言は二重に数えない）。一言は記憶の材料にもなる（`digest.ts`：その会話の場面で、仕事なら人の文だけ）。
- テスト：`characters/characters.test.ts`・`characters/memory.test.ts`・`characters/aside.test.ts`。撮影は監査シーンの `63-member-page`・`64-member-talk`・`65-member-aside`（「Excel の重複を消したい」にハクを呼んだ一言と、`@` の候補。ハクが右腕の席、定期便「朝のまとめ」の担当、人が書いた記憶 3 件、D のミナトを `keep`）。

### 2.23 会話のあらすじと裏の整理（`summaries/`、`llm/background.ts`）

長い会話の横に「あらすじ」を 1 つだけ持つ（`session_summaries`：本文・どこまで畳んだか・畳んだ件数）。**会話自身のモデルは読まない**（進行にもキャッシュにも触らない）。読むのは `@` の一言（§2.22）と検索。

- **更新のルールは 1 つ**：あらすじより後の発言（text のある user / assistant。通知・hint・ツールは除く）が `SUMMARY_FOLD_AT`（24 件）か 12,000 字を超えたら、新しい `SUMMARY_KEEP`（12 件）を残して古いほうを「前のあらすじ ＋ その発言」から書き直す（1,500 字まで。決まったこと・残っていること・名前や数字のような探す手がかりを残す）。読むのは差分だけなので、会話が長くなっても 1 回の費用はほぼ一定。24 件以下の会話にはあらすじを作らない。
- **いつ**：見回りはしない。会話のターンが終わったとき（`run.status_changed` の終わり）に、その会話だけを数える（読んだ位置より後を SQL で）。遅れていれば 1 回に 1 かたまり（24 件・12,000 字まで）を畳む。古い長い会話は使われるたびに少しずつ追いつき、触られない会話は裏で要約されない。`@` で呼んだときに遅れていれば、その場で 3 かたまりまで畳む（`ensure`）。会話ごとに 1 本ずつ。失敗したらその会話は 1 時間あけ、続けて失敗したら全体が待つ。
- **検索**（`session.search`）：あらすじにすべての語が入っている会話を、メッセージの当たりより先に返す（`source: summary`、`messageId: null`。開くと会話へ）。
- **裏の整理**（`settings.background`）：記憶の整理とあらすじは、モデル（null なら名簿でいちばん安いもの：ChatGPT にサインインしていれば `openai/…` は契約枠で 1 回あたり 0 なので最優先、その中では軽い層（Luna など、`isFastModel`）を先に。次に入力単価の安い順、単価不明は最後。名簿がなければオフラインのモック。`cheapestModel`）と 1 日の上限（既定 $0.5、空で上限なし）を共有する。費用は ledger の `component: memory` / `summary`（あらすじはその会話の費用）。1 日の呼び出し回数にも上限（`BACKGROUND_DAILY_CALLS` = 200、`background_calls`）。ChatGPT のプランでは 1 回 $0 で記録されるので、金額の上限だけではプランの枠を使い切りうるため。どれかの上限か全体の 1 日の上限に当たったら翌日まで止まる。オン／オフは `settings.members.memory` と `settings.summaries.enabled` で別々。
- `session.summary`（その会話のあらすじ、なければ null）と `session.summary_updated`。モック：`mock/summary`（前のあらすじと各発言の頭 40 字）。
- テスト：`summaries/summaries.test.ts`。

## 3. Desktop UI

- Tauri 2 のシェルは Core Daemon を起動（未起動なら）して接続情報をフロントへ渡すだけ。ロジックは持たない。
  - `get_connection`（`src-tauri/src/daemon.rs`）：`daemon.json` + `/health`（`service`・`pid` 一致）で既存デーモンを再利用、なければ detach 起動（Windows は `CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP`、可能なら `CREATE_BREAKAWAY_FROM_JOB`）して `daemon.json` を待つ。UI を閉じてもデーモンは残る。起動に失敗したら今回の起動ログの末尾を日本語のメッセージに付けて UI に返す。
  - 起動方法：`tauri dev` は `node --import tsx packages/daemon/src/main.ts`、ビルド済みアプリは同梱の `acc-node.exe`（固定版の公式 Node）+ `resources/daemon/main.mjs`（esbuild の 1 ファイル）。`ACC_DAEMON_ENTRY` で差し替え可能。
  - single-instance（2 つ目の起動は既存ウィンドウを前面に）、window-state（位置・大きさ・最大化を復元。表示は最初のページ読み込み後）、notification（OS 通知。capability は `is_permission_granted` / `request_permission` / `notify` だけ。UI は `lib/notify.ts` から直接 invoke）、枠なし + HTML のタイトルバー。
  - アプリを開いたまま `system.shutdown` すると、UI の再接続でシェルが新しいデーモンを起動する。だから UI の停止ボタンはデスクトップアプリでは `再起動` と呼ぶ。
  - Claude Code の CLI は同梱しない。デーモンが実行ファイルを探して Agent SDK に渡す（`runtime/claude/locate.ts`、見つからなければ理由つきで Run が失敗）。
- ブラウザ（`pnpm dev`）でも同じ UI が動く（Vite の開発ミドルウェアが `daemon.json` を渡す）。E2E テストはこの経路で行う。`/__acc/connection` は同じオリジンのページ（`Sec-Fetch-Site: same-origin`、`Origin` が自分）か、ブラウザ以外からの要求だけに答え（`scripts/same-origin.js`）、dev / preview サーバの CORS は切る（ほかのローカルポートのページにトークンを読ませない）。
- 状態：サーバ状態は TanStack Query、イベントストリームで無効化・差分反映。UI 状態は Zustand。
- 3 モード：Command（要対応を優先した俯瞰）/ Focus（1 セッション集中）/ Timeline（イベント時系列）。コマンドパレットとキーボード操作を一級に扱う。
