# 2026-10-29 Claude Code の Auto mode を Worker に使えるか

目標は「安全で、承認依頼 0」。承認は技術的にどうしても決められないときの妥協として残す。そのために Claude Code の Auto mode（`permissionMode: 'auto'` と安全判定の分類器）が Claude Agent SDK ランタイムで使えるかを、公開ドキュメントと本物の CLI（SDK 同梱 **2.1.312**）で確かめ、使えないときの規則ベースの代わりと、層に分けた権限の設計を決めた。本番コードはこの段階では変えていない。

## 結論

- **使える（条件つき）**：同梱 CLI は、我々の `ANTHROPIC_BASE_URL`（LiteLLM 経由）のままで `permissionMode: 'auto'` を受け付けた。Claude 名のモデルでも、gateway の別名（`team-sonnet`）でも、Claude 以外の名前（`gpt-5`）でも auto になった。拒否されたのは CLI が「古い」と知っている名前（`claude-sonnet-4-5`）だけで、そのときは**何も言わずに `default` で始まる**（`system/init` の `permissionMode` で分かる）。
- **分類器は同じ gateway に別リクエストで飛ぶ**：モデルは既定で `claude-sonnet-5`（Sonnet 4.6 のセッションだけは Sonnet 4.6）。`CLAUDE_CODE_AUTO_MODE_MODEL` か `ANTHROPIC_DEFAULT_SONNET_MODEL` で変えられる。LiteLLM がその名前で Claude（Sonnet 4.6 以上）を出せなければ、判定が必要な操作はすべて「判定できないので拒否」になる。つまり**実際に使えるのは「LiteLLM の裏に Claude がある」構成か、Anthropic API / Bedrock / Vertex / Foundry 直結**。Claude 以外のモデルだけの構成と、Claude 以外のランタイム（Copilot SDK など）では使えない → 規則ベースの「おまかせ」にする。
- **止められたら**：実行されず、モデルには理由つきのツールエラーが返り、エージェントはそのまま続ける（質問で止まらない）。3 回連続（または累計 20 回）で止められると、CLI は `canUseTool` に回す（＝我々の承認になる）。
- **フックとの関係**：`PreToolUse` フックは分類器より**先**に、すべてのツール呼び出しで走る。`deny` は分類器を呼ばずに拒否、`allow` は**分類器を飛ばして**実行、`ask` も分類器を呼ばずに `canUseTool`、何も返さなければ CLI の判断（作業ディレクトリ内の読み書きは自動許可、それ以外は分類器）。→ デーモンの絶対ルールはフックの `deny` で強制し、グレーゾーンは「何も返さない」で分類器に任せる。フックで `allow` / `ask` を返すと分類器が効かなくなる。
- **推奨**：(a) 絶対ルールはフックで拒否して理由をエージェントに返す（承認にしない）。(b) グレーゾーンは Auto mode の分類器、なければ「worktree の中で完結するものは許可」の規則ベース。(c) 承認は統合（保護ブランチへの反映）と、自動では決められなかったものだけ。(d) プロジェクトごとに 慎重 / 標準 / おまかせ、既定はおまかせ。(e) 統合テストの承認はおまかせ・標準では外す。(f) 自動判断はすべてイベントにして Timeline で後から見られるようにする。詳細は「推奨設計」。

## 実機プローブ

`packages/daemon/src/runtime/claude/contract/probeAutoMode.ts`（偽 API で分類器も演じる。記録するだけで何も検証しない）と、契約テストに足した 4 件（`sdk-contract.test.ts` の「auto mode」）。隔離は既存のハーネスと同じ（一時 HOME / `CLAUDE_CONFIG_DIR`、環境変数の許可リスト、外向きは全拒否のプロキシ、ダミートークン）。費用・本物の認証情報・この機械の `~/.claude` はなし。偽 API には、ツール一式を持たないリクエストを分類器として答える `intercept` と、本文を保存する `keepBodies` を足した（`fakeAnthropic.ts`）。

### 分類器リクエストの形

- 本体と同じ `POST /v1/messages?beta=true`。`tools` なし、`thinking: disabled`。2 段階：1 段目は `max_tokens: 64` で「疑わしければ止める」、1 段目が止めたときだけ 2 段目（`max_tokens: 8192`、考えてから答える）。許可なら 1 回、拒否なら 2 回。
- system は約 14 万文字（数万トークン、`cache_control: ephemeral`）の英語の規則集（脅威モデル、HARD / SOFT BLOCK、ALLOW の例外、Environment の各スロット）＋ Session Context。**Session Context に OS のユーザー名が入る**（ブランチ名の規則に使う）。
- messages は 1 件：`<transcript>` の中に、ユーザーの発言（**我々の Run のプロンプト＝ Task の目標がそのまま「ユーザーの意図」になる**）と、ツール呼び出しの要約（`{"Bash":"npm install left-pad"}`、`{"Write":"<パス>: <内容>"}`）。ツールの結果は入らない。CLAUDE.md は `settingSources: []` なので入らない。
- 答えの形はモデルで違う：Sonnet 4.6 は `<block>yes|no</block><category>…</category><reason>[規則名] …</reason>`（stop `</block>`）、既定の Sonnet 5 は `<severity>0-100</severity><category>…</category>`（50 が境目、stop `</severity>`）。`ANTHROPIC_DEFAULT_SONNET_MODEL` に任意の名前を入れると、その名前に `max_tokens: 2112` の `<block>` 形式で来た。
- 最初の本体リクエストには `safeguards: [{type: "dangerous_tool_use", classifier_context: {permission_mode, platform, live_cwd, home_dir, rule_roots, trusted_directories, rules…}}]` と beta `dangerous-tool-use-2026-09-03`、`afk-mode-2026-01-31` が付く（サーバー側レビューの依頼。cwd とホームのパスを含む）。偽 API は `safeguard_results` を返さないので、CLI は以後自前の分類器に切り替え、`system/informational`（warning）で「gateway が対応していないので分類器リクエストは課金される」と伝えた。`CLAUDE_CODE_AUTO_MODE_SERVER=0` なら `safeguards` も警告も出ない。
- インライン設定 `options.settings.autoMode`（`environment` / `soft_deny`、`$defaults` つき）は分類器の system に入った。

## 推奨設計：層に分けた権限

上から順に評価する。上の層が決めたら下には行かない。

1. **絶対ルール（デーモンが強制、フックの `deny`）**：どのプロファイル・どのランタイムでも同じ。
2. **人間が覚えさせた許可**（「この Task / Run / プロジェクトでは許可」）：フックの `allow`。
3. **グレーゾーン**：Auto mode が有効ならフックは何も返さず CLI（分類器）に任せる。無効なら規則ベースの「おまかせ」ポリシー（`canUseTool` で同じ純関数が答える）。
4. **決められないもの**だけ承認。統合の反映は常に人間。

### (a) 絶対ルール：拒否して理由を返す（承認にしない）

承認にすると「承認 0」に反するうえ、どれも Worker の仕事に要らない。拒否の理由は日本語で、代わりにどうすればよいかを書く（エージェントは自律的に別の手段を取るか、最終報告に「できなかったこと」として書く）。実機のとおり、`deny` は分類器より先に効き、モデルに理由が届く。

| 対象 | 例 | 理由として返す方針 |
|---|---|---|
| `.git` の改ざん | パスに `.git` を含む Edit / Write（gitdir、config、hooks、info）、`git config`（読み取り以外）、`git update-ref`、`git worktree`、`core.hooksPath` を設定する操作 | worktree の git はデーモンが管理する。今の「承認」から「拒否」に変える。Auto mode は保護パスでも分類器が許せば書かせるので、ここは分類器に任せない |
| worktree の外への書き込み | 外のパスへの Edit / Write、外のパスを引数に取るコマンド（`rm`、`cp`、`mv`、リダイレクト） | 字面＋実パスで判定（既存の `policy.ts`）。外の読み取りも、下の資格情報以外は拒否（標準・慎重では承認） |
| 資格情報とデーモンの秘密 | `~/.ssh`、`~/.aws`、`~/.config/gh`、`~/.claude*`、`~/.npmrc` などの読み取り、`ACC_HOME`（`daemon.json` のトークン、DB）、他プロジェクトの worktree | プロンプトに資格情報を入れない。字面で拾えるものだけで、コードの中からの読み取りは防げない（(e) 参照） |
| 反映・公開・リモート変更 | `git push`、`git remote add/set-url/remove`、`gh pr create/merge`、`gh release`、`npm/pnpm/yarn publish`、`cargo publish`、`docker push`、`git checkout/switch` で他のブランチへ、`git branch -D/-f` | 「コミットして終えれば Integration が反映する」。分類器の既定は作業中リポジトリへの push を**許す**ので、フックで止める必要がある |
| システム設定と常駐 | `sudo`、`reg`、`setx`、`Set-ExecutionPolicy`、`git config --global`、`npm install -g`、`pip install --user`、シェルの rc ファイル、`crontab`、`schtasks`、`systemctl`、`launchctl`、`nohup` / `setsid` / `disown` / 末尾 `&` / `Start-Process` / `start` で Run の外に残すプロセス | 本番では HOME はユーザー本人のもの。Run の外に残るプロセスと設定変更は後から把握できない |
| 自己昇格 | `claude` / `codex` など別のエージェント CLI の起動（`--dangerously-skip-permissions` などで規則を迂回できる）、デーモンの CLI や Control API への直接アクセス（トークンを読む、ポートに接続）、`.claude/settings*.json` の編集、無人に合わないツール（既存の `DISALLOWED_AGENT_TOOLS`） | Grant と予算はデーモンが持つ。エージェントは Control API を MCP（ディスパッチャ経由）でだけ使う |
| ダウンロードして実行 | `curl … \| sh`、`iwr … \| iex` | 依存はマニフェストから入れる |

判定は今の `decideToolPermission` に `deny` を足す形にし、Bash は既存の構文解析（`commands.ts`）を広げる。パイプ・`&&`・サブシェル・`bash -c` の中も見る。字面の判定はコードの中の操作（テストスクリプトが push するなど）を防げないことを明記し、本当の境界は (e) の OS レベルの隔離とする。

### (b) グレーゾーン

**Auto mode が使えるとき**（Claude ランタイムで、設定に「安全判定モデル」があり、init が `auto` を返したとき）：

- `permissionMode: 'auto'`。フックは絶対ルールなら `deny`、覚えた許可なら `allow`、それ以外は**何も返さない**（`ask` は分類器を飛ばして人間に回すので使わない）。
- `CLAUDE_CODE_AUTO_MODE_MODEL` に設定の「安全判定モデル」（LiteLLM で Claude Sonnet 4.6 以上を指す名前）を必ず渡す（既定の `claude-sonnet-5` という名前を LiteLLM が持っているとは限らない）。LiteLLM が `safeguards` / `safeguard_results` を素通しすると確認できるまでは `CLAUDE_CODE_AUTO_MODE_SERVER=0`（警告メッセージと余分なフィールドを避ける）。
- `options.settings.autoMode` を渡す（`$defaults` を残す）：`environment` に「隔離された git worktree で動く無人の Worker。反映はデーモンの Integration が人間の承認後に行う。push・リモート変更は不要」、`hard_deny` に絶対ルールの言い換え（フックの字面判定をすり抜けた場合の二重化）、`classifyAllShell: true`。
- init の `permissionMode` が `auto` でなければ、その Run は規則ベースに切り替える（古いモデル名など）。「判定できない」拒否が続いたら（安全判定モデルが LiteLLM にないなど）、`setPermissionMode('default')` で規則ベースに落とし、Timeline に「安全判定を使えないため規則で判断しています」と出す。
- **注意**：分類器は Run のプロンプトを「ユーザーの意図」として読み、soft block を解除しうる。Worker のプロンプトは Orchestrator（LLM）が書くので、意図を偽装された場合に備え、本当に越えてはいけない線は分類器ではなくフック（と `hard_deny`）に置く。

**Auto mode が使えないとき（規則ベースの「おまかせ」）**：mock ランタイム、Claude 以外のランタイム、Claude 以外のモデルだけの LiteLLM、古いモデル。絶対ルールに当たらず、worktree の中で完結するものは許可：

| 種類 | おまかせ | 標準 | 慎重 |
|---|---|---|---|
| worktree 内の読み取り・検索・編集（`.git` 以外） | 許可 | 許可 | 許可 |
| テスト・ビルド・lint・フォーマッタ・package.json の scripts（`pnpm test`、`npm run build`、`node --test`、`cargo test`、`pytest`） | 許可 | 許可 | 承認 |
| 自分のブランチでのローカル git（`add`、`commit`、`diff`、`stash`、`restore`、`rebase`、`merge`、`cherry-pick`、`reset`（worktree 内）） | 許可 | 許可 | 許可（読み取り以外は承認） |
| マニフェスト / ロックファイルからの依存インストール（`pnpm install`、`npm ci`、`pip install -r`、`cargo fetch`） | 許可 | 許可 | 承認 |
| 新しい依存の追加（`pnpm add x`、`npm install x`、`pip install x`） | 許可（Timeline に「依存を追加」と目立たせ、統合のレビューでマニフェストの差分を強調） | 承認 | 承認 |
| 読み取りだけのネットワーク（WebFetch、WebSearch、`git fetch`、データを送らない `curl` / `wget` の GET） | 許可 | 許可 | 承認 |
| データを送るネットワーク（`curl -d/-F/-T`、POST、`scp`、`rsync` でリモートへ、`ssh`、`nc`） | 拒否（理由つき） | 拒否（理由つき） | 拒否（理由つき） |
| 長時間のフォアグラウンド処理（dev サーバー、watch） | 許可（Bash ツールのタイムアウトで終わる） | 許可 | 許可 |
| worktree の外の読み取り（資格情報以外） | 拒否（理由つき） | 承認 | 承認 |
| 未知のツール | 拒否（理由つき） | 承認 | 承認 |

- ネットワーク：規則で見えるのはコマンドの字面だけで、テストやインストールスクリプトの中の通信は見えない。インストールスクリプトはテストと同じく「エージェントのコードを動かす」のと同じ重さなので、それ自体は許可する。後から把握できるよう、Run ごとにデーモンの記録用の外向きプロキシ（`HTTPS_PROXY`）を挟み、接続先を Timeline に出すのを次の段階で検討する（行儀のよいツールしか通らないので境界ではなく可視化）。
- バックグラウンド：`CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` は維持し、Run の外に残る起動は絶対ルールで拒否。Run の終了時にデーモンがプロセスツリーごと止めること（Windows はジョブオブジェクト）を確かめる。

### (c) 承認は決められないものだけ

- **統合の反映**（`integration.approve`）：常に人間。設計上の唯一の「承認」。
- **分類器が 3 回続けて止めた**（CLI が `canUseTool` を呼ぶ）：おまかせでは承認にせず「同じ操作が自動判定で繰り返し止められました。必要なら最終報告に書いてください」で拒否し、Timeline に「要確認」（Run は止めない）。標準・慎重は承認。
- **プロファイルが承認とした操作**（上の表）。
- 承認のカードに「今回だけ」「この Run の間」「この Task の間」「このプロジェクトでは常に」を付ける。覚えた許可はデーモンの DB に保存するポリシー規則（ツール名＋正規化したコマンドの先頭トークン列、またはパスの glob）で、CLI の設定ファイルには書かない（`settingSources: []` のまま）。絶対ルールは覚えた許可でも越えられない。`policy.rule.created` / `policy.rule.revoked` を記録し、プロジェクト設定で一覧・取り消しできる。Run / Task 単位の規則はその終了で失効。

### (d) プロジェクトごとのプロファイル

`Project.permissionProfile`：`careful`（慎重）/ `standard`（標準）/ `autonomous`（おまかせ、既定）。

- **おまかせ**：絶対ルール＋ Auto mode（使えなければ規則ベースのおまかせ）。承認は統合の反映だけ。10 並列でも普段は承認 0。
- **標準**：おまかせに加え、新しい依存・外の読み取り・未知のツール・分類器が止め続けたものを承認に回す。
- **慎重**：今の挙動に近い。読み取りだけの許可リスト以外のコマンドは承認、統合テストも承認。
- Auto mode の利用はプロファイルとは別の設定（「安全判定モデル」が設定され、ランタイムが Claude のとき）。プロファイルは「分類器も規則も決めなかったときにどうするか」を決める。

### (e) 統合テストの承認

レビューの回で足した「人間が始めていない統合のテストは承認を待つ」は、**おまかせ・標準では外し、慎重だけに残す**。

- 理由：新しいポリシーでは Worker が自分の worktree でテストやビルド（＝エージェントの書いたコード）を承認なしで動かす。統合のテストは、同じコードを同じ OS ユーザー・同じ環境変数の許可リスト（＋ `CI=true`、出力の秘密を伏せる）で、別の worktree で動かすだけで、守れるものが増えない。承認を残すと「Worker では動かすのに統合では止める」と一貫せず、Orchestrator の流れに必ず 1 回承認が入る。
- 正直に書くべき残りのリスク：エージェントのコード（Worker のテストでも統合のテストでも）は、同じ OS ユーザーとして `daemon.json` のトークンを読み、`integration.approve` を「人間」として呼べる（security-3、authority-2）。フックの字面判定・環境変数の許可リスト・WebSocket の Origin 検査はこれを防げない。今まで「統合テストの前の承認」で塞いでいたように見えた穴は、Worker がコマンドを自由に動かす時点で開いている。根本対策は OS レベルの隔離（エージェントを別の低権限ユーザー / Windows の AppContainer / macOS・Linux のサンドボックスで動かし、`ACC_HOME` を読めなくする）で、それまでは「人間だけの操作」は監査（誰がどの接続から呼んだかを記録し、UI 以外からの `integration.approve` を Timeline で目立たせる）で補う。architecture §2.1 の前提の記述はこのとおり更新する。

### (f) 後から見えること

- ツールごとの判断をイベント `tool.decided`（仮）で記録：`{ runId, toolUseId, toolName, summary, decision: allowed | denied | asked, by: rule | remembered | classifier | mode | human, rule?: 絶対ルールの ID, category?, reason?, profile }`。入力の値（コマンド全文など）は既存の `tool.called` と同じ扱い（伏せ字あり）。
- 情報源：自分のフックの判断（デーモンが決めたもの）、`system/permission_denied`（文書あり。分類器・モードの拒否と理由）、ユーザーメッセージの `tool_result_meta[].permission_decision`（文書なし。`decision`・`source: config | hook | user_temporary`・`reason_type: classifier | mode | hook` で許可の出どころも分かる。型にないので任意扱いにし、なければ「CLI が許可」とまとめる）、`canUseTool` の結果。
- Timeline：既定は拒否と承認だけを表示し、「自動許可も表示」で全部。拒否は理由とともに目立たせる（エージェントがその後どうしたかが続けて読める）。Run のヘッダに「自動許可 42 / 拒否 2 / 承認 0」。依存の追加・外部への通信は「要確認」の印。
- 費用：分類器の呼び出しは SDK の使用量に入らないため Budget が少なく数える。判定の回数（`reason_type: classifier` と分類器の拒否）を数えて見積もるか、LiteLLM の spend を取り込む。Budget の強制は見積もりで行い、ズレを表示する。

### (g) mock・デモ・E2E への影響

- mock ランタイムも同じポリシー（プロファイルつき）を通すので、おまかせでは mock の `run`（デモのテスト Worker の `node --test`）は承認なしになり、**デモで強制していた 1 回の承認はなくなる**。代わりにデモでは、Worker が `git push` しようとして絶対ルールで拒否され、理由を読んでコミットだけして終える、という「自動判断」を Timeline で見せる（mock の計画に拒否を起こす手順を足す）。統合テストの承認もなくなるので、デモの Orchestrator は統合のレビューまで止まらない。
- 承認 UI の E2E（`e2e:slice` の承認ループ、Ctrl+J → Y）は、慎重のプロジェクトか mock の `ask` 手順で承認を起こして残す。`e2e:conflict` は統合テストの承認の手順を外す。
- 単体テスト：ポリシーをプロファイル × 種類の表で検査、絶対ルールの拒否理由、覚えた許可の範囲と失効、`tool.decided` の記録。契約テスト：今回の auto mode の 4 件（下）を、本番で auto を使うときの回帰に使う。

## 実際の LiteLLM / 実モデルでないと確かめられないこと

- LiteLLM が `safeguards` を Anthropic に素通しし、`safeguard_results` を返すか（返せばサーバー側レビューで分類器の別リクエストと課金がなくなる）。LiteLLM の Anthropic パススルーと `/v1/messages` で違う可能性がある。
- 分類器の実際の判断の質と誤検知の頻度（偽 API では演じただけ）。Worker の典型操作（テスト、依存インストール、ビルド）が止められないか、`autoMode.environment` の書き方でどれだけ減るか。
- Claude 以外のモデルを分類器にした場合（形式どおり答えても、規則集は Claude 向け）。サポート外として扱う。
- 実モデルが拒否理由を読んで自律的に別の手段に移るか、絶対ルールの日本語の理由で十分か。
- 他 OS（macOS / Linux）。サンドボックス（OS レベルの隔離）との組み合わせ。
