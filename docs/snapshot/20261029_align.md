# 2026-10-29 UI を本物の契約に合わせる（track/align）

前回は UI（apps/desktop）とデーモンの新メソッドを並行で作り、UI 側は結果の形を推測していた。両方がマージされたので、`packages/protocol/src/api.ts` の契約に合わせた。仕様は `docs/persistent/ui-design.md`（§5.1 Task ボード、§5.4 統合のレビュー、§8.1 プロジェクトの追加、§8.5 通知、§8.6 設定）に反映済み。

## 変えたこと

| 項目 | 前 | 後 |
|---|---|---|
| `project.inspectRepo` | `{ path }` が `invalid_params` なら `{ repoPath }` で再試行、結果は `isRepo` / `root` / `uncommittedFiles` などの候補名を寛容に読む（`normalizeInspection`）。`system.info` にメソッドがあるときだけ呼ぶ | `{ path }` 1 回。protocol の `RepoInspection` をそのまま読む。`ok: false` は `reason` を表示、サブフォルダは `ルート … を使う`、`existingProjectId` は追加を止めて `このプロジェクトを開く`、`defaultBranch` を作成時に渡す。メソッドがない・接続断なら作成時に検証（従来どおり） |
| 差し戻し | `task.retry` / `task.rework` を探し、なければ `task.update(ready)` → `task.spawnWorker({ instructions })` の 2 段（途中で失敗すると review に戻すだけ） | `task.retry { taskId, feedback }` の 1 回だけ。デーモンが同じトランザクションで Task を running にするので、UI 側で中途半端な状態が生まれない |

| 設定 | なし | `LLM 呼び出しごとの予約額（USD）`（`llmCallReserveUsd`）、`再起動のあと Orchestrator を再開`（`autoResumeOrchestrators`） |

ついでに直したもの：コンフリクトで止まった試行のテスト結果が「テストコマンドが設定されていないため、検証を省略しました」と出ていた（実際はマージが止まったため）。`integrationSummary` が解消済みのコンフリクトを「コンフリクト N ファイル」と言い続けていた。

## なぜ `window.Notification` の置き換えを使わないか

プラグインは `window.Notification` を置き換える init script を入れるが、Windows ではその `permission` が最初 `denied` になり（`__TEMPLATE_windows__` 分岐）、`@tauri-apps/plugin-notification` の `isPermissionGranted()` もそれを先に見る。デスクトップのプラグイン本体は常に `Granted` を返すので、コマンドを直接呼ぶのが一番確か。npm パッケージも足さずに済む。

## 確認

- `pnpm check`：lint・typecheck・test（59 ファイル / 515 件）緑。
- `e2e:slice`（Vertical Slice 全体）・`e2e:board` 緑。
- `cargo check --locked` / `cargo test --lib`（6 件）緑（`src-tauri`）。`tauri-build` は `externalBin` / `resources` / `frontendDist` の存在を確かめるので、空のダミー（`binaries/acc-node-<triple>.exe`、`resources/daemon/main.mjs`、`dist/index.html`。いずれも gitignore 済み）を置いて確認し、あとで消した。`prepare-sidecar.js`（引数なし）は sidecar が「無いときだけ」コピーするので、ダミーを残すと dev 起動が壊れる点に注意。
- `tauri-plugin-notification` は 2.4.0（opener 2.5.5 と同じリリース、tauri 2.11.6・Rust 1.89 のまま。Cargo.lock は追加分だけ）。
- 新規 `e2e:conflict`：README.md に別々の節を足した 2 Task を統合 → コンフリクト → パレットからレビュー → `Integrator に解消を任せる` → 補足を入力して確定 → `fix` が完了して反映待ち。統合ブランチの README.md に両方の節があり、マーカーがなく、補足が Integrator に届き、main は動いていないことを git で確かめる（約 17 秒）。
- 新しい単体テスト：`task.retry` の 1 回呼び出しと失敗時の復元、中断 Task のセクション・`R` で再開、Worker Run の再試行の経路、resolveWithAgent の確認・ライブ進捗・結果・失敗・拒否、inspectRepo の各結果（ルートの提案、既存プロジェクト）、shutdown の force の扱いと conflict での聞き直し、設定の保存、Tauri 通知のコマンド。

## 残り

- `session.grantOrchestration` も契約になったが、`grantOrchestrator()` はまだ候補名を探して `invalid_params` なら `grant.create` に落ちる。動くが、次に触るときに型付きの 1 回呼び出しにする。デモの `system.setupDemo` の結果も寛容に読んだまま。
- 統合が「テスト失敗」のとき `task.retry { integrationId }`（失敗したテスト出力を Worker に渡す）を呼ぶ UI はまだない。
- OS 通知のクリックで該当場所を開くのはブラウザだけ（Tauri のプラグインはデスクトップでクリックを返さない）。
