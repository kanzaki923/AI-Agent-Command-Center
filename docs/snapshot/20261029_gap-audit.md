# 2026-10-29 現状と源泉のビジョンとの乖離（全画面の洗い出し）

ユーザーの指摘（文字での説明は悪、コーディングに特化しない、シンプルさと初回の負荷、5 秒テスト）を受けて、一般的な一日を再現したシーン（13 セッション、モックのみ）で全画面を撮り、6 つの観点で洗い出した。シーンは `pnpm --filter @acc/desktop e2e:audit --out <dir>` で再現できる。

**合格基準**：10 人のエージェントが同時に動いている状態で、アプリを 5 秒間眺める。チャットもログも開かずに、全体の進捗・問題・人間の出番が分かるか。→ **現状は不合格**。

## シーン担当の報告（抜粋）

## Bugs found while building the scene
1. **A long answer shows nothing while it is being written.** If the chat is opened or the app reloaded after streaming started, it shows only 「回答を生成中…」 until the very end, minutes in this scene (`21`). This is how `ChatStream.tsx` handles joining partway through, and the daemon cannot send the text written so far.
2. **The built-in mock orchestrator never stops.** After its final report it records a decision, gets called again, and writes the same report again, about every 2.6 seconds. It stays "running" forever and floods both its chat and the timeline (`32`, `60`, `62`). The cause is `finalSummary` in `mockModel.ts`, and demo mode uses the same model.
3. **The approval question repeats itself:** 「ツール「AskHuman」の使用を承認しますかを承認しますか？」. Ctrl+J then shows the raw JSON of the request (`50`).
4. **The goal header shows the wrong message.** It shows the user's first chat message (「…何から手を付けるべき？」), not the instruction that actually started the work.
5. **Workers get a doubled title**, 「Worker: Worker: …」, in the sidebar and the cards.
6. **Task descriptions show the mock plan's raw JSON block** in the detail panel (`13`). This is partly a side effect of the mock setup, but the daemon already has a function that strips it, and the UI does not use it.
7. **A worker's chat never shows the instructions it was given**, so the hand-off from the orchestrator is invisible there (`40`).
8. **Ctrl+N and Ctrl+Shift+N immediately create real sessions**, 「新しいチャット」 and 「無題のエージェント」, which then stay in the sidebar.
9. **The timeline splits one run into two groups** with an unrelated row in between (`62`).
10. **The "make this chat an Orchestrator" dialog on a writing chat with no project defaults to the coding repo acme-web** (`24`).

## What the product cannot show at all for this scene
- **Scheduled or recurring runs:** they don't exist. There is no API for them and no screen. The weekly report could not be set up as a recurring job.
- **AI starting plain chats:** the orchestrator permission set deliberately leaves out creating sessions, so an AI can only start workers, never a plain chat.
- **A non-coding agent without a git repository:** any worker needs a repository. The launch project had to be a git repo full of Markdown, and its test-command field still suggests `pnpm test` (`83`).
- **Cost per goal:** no total cost or remaining budget per goal anywhere. The goal header shows Task progress only. The $3 budget appears only in the orchestrator's own header ($0.62 / $3.00), which counts only its own spend. That hides the $2.20 handed to workers, so "near the limit" is invisible.
- **Cost per project or over time:** only "today" and the per-run total.
- **Which session started which, in the sidebar:** it is a flat list without project grouping. The relation appears only in the command room's Task tree and in the "parent" field of the detail panel.
- **A one-line summary of what each running session is doing:** rows say only 「作業中」 or 「回答を生成中」, never what is being done. Understanding a session still means opening it.
- **Something to review for non-code results:** finished documents are sent to "integration review" like code changes. There is no document preview.
- **Toasts for a fresh state change:** they appeared for a new failure, but there are no in-app notifications for anything else. OS notifications show as blocked in the browser.
- **Other things that do not exist:** connectors (GitLab, browser), automatically starting a waiting worker when another finishes, and the orchestrator re-planning or postponing work because of budget.

## 観点：ソースビジョン（source-vision.md の 2026-10-29 指摘・合格基準、concept.md の各約束）と現物のギャップ

結論：土台（Daemon・Control API・Grant・予算ツリー・worktree・統合レビュー・普段使いのチャット）はできている。ただ、ユーザーが「キラキラ」と呼んだ 5 本柱は、どれも目標に届いていないか、まったく無い。
5 本柱の状態：①10 並列を同時に操る UI は部分的（5 秒テストは不合格）、②AI がチャットをスポーンしてメタ的に介入するのは無い（Worker＝git worktree のコーディングエージェントだけ）、③定期実行は無い（API・UI・コミット、どれも 0）、④コスト管理は Daemon にはあるが UI に出ていない、⑤作業として破綻しないことは、デモの Orchestrator が無限ループしていて満たせていない。
いちばん重い構造の問題：Orchestrator は 1 本の長い Run の中で task.wait をブロックし続ける。そのため、いちばん話しかけたい作業中に「いま何してる？」を送ると『このセッションでは別の Run が実行中です』で拒否される。concept §3.2 の看板体験が設計上ありえない状態になっている。
汎用性が崩れている：Orchestrator・Worker・統合のどれも git リポジトリが前提。プレスリリースのような文書でも、ブランチ名・+9 −0・main へ反映・pnpm test が画面に出る。
開発の配分も偏っている：コミット 64 件のうち、権限・承認・安全性が 17 件、統合・worktree・テストが 18 件、定期実行・コネクタは 0 件。

### [critical] 【部分的】5 秒テスト不合格：司令室が「文章カードの縦積み」で、何をしているかが出ない

- 根拠：10-command-agents.png：1440x900 の 1 画面目は、目標ツリー 2 つと要対応カード 4 枚（段落 2〜3 行ずつ）だけで埋まる。実行中 5 件は 10-command-agents-2.png までスクロールしないと見えない。
実行中の行の 2 行目は「作業中」「回答を生成中」「Worker の完了を待機中」だけ。activity.ts は tool.called をそのまま流しているので、実機でも「docs/faq.md を編集」のようなツール単位の表示にしかならず、何のためにやっているかは出ない。
目標ヘッダーは「Task 0/2」で、両方レビュー待ちなのに 0 と出る。コストは無い。
サイドバー（11-sidebar.png）は要対応・実行中・最近のフラットな一覧で、プロジェクトの区切りも親子も無い。13 セッションの全体像をつかむには、チャットを開くか Task タブを切り替えるしかない。
- 提案：司令室の 1 画面目を「目標＝1 レーン」にする。各レーンの中身：
- 横一列の Worker チップ。状態色・アイコン・役割の 1 語。
- 進捗のセグメントバー（完了・レビュー・実行中・失敗）。
- 予算メーター（使用・配分・上限）。
- 「人間の出番」アイコン数。

チップには「何をしているか」の 8〜15 字ラベルを常に表示する。ツール名ではなく、Task 名と直近の意図を Daemon 側で要約したもの。要対応は段落カードをやめ、レーン上のチップを点滅・浮上させて表す（concept §7.1「承認待ちは自然に気づける位置へ移動」）。実行中は折り返さず 1 画面に収める。13 件までスクロールなしで見えることを合格条件にする。

### [critical] 【設計上不可】作業中の Orchestrator に話しかけられない（「いま何してる？」「一旦止めて」が成立しない）

- 根拠：- packages/daemon/src/orchestrator/executor.ts:54 の system prompt が「task.wait (mode "all", a long timeoutMs)」で Worker 全員を待てと指示している。そのため Orchestrator の Run は Worker が全員終わるまで running のまま残る（30-focus-orchestrator-launch.png「Worker の完了を待機（4 件）実行中…」）。
- packages/daemon/src/runs/manager.ts:183-187 は、同じセッションに走っている Run があると conflict『このセッションでは別の Run が実行中です』を返す。
- Composer.tsx:105-140 の send は、走っている最中でも送信を試みる。そして apps/desktop/src/daemon/actions.ts:120-126 で失敗表示になるだけ。キューに積む仕組みも、割り込む仕組みも無い。
- 「一旦止めて」：一時停止の API は無い。task.cancel だけで、workers.ts:52-54 の RETRYABLE に cancelled は入っていないので、止めたら再開できない。
- 「テスト担当を 2 人追加」：task.create と spawnWorker なら技術的には可能。ただし上の理由で、作業中には頼めない。
- 提案：Orchestrator を「1 本の長い Run」から、イベントで起こされる短い Run の連続に変える。
- Worker の完了・失敗・承認を Daemon がそのセッションに system メッセージとして積み、新しい Run を起こす。
- 人間のメッセージは割り込みとして、待機中の Run を中断し、次の Run に合流させる。
- task に pause / resume を足す（cancel と分ける）。
- 司令室の目標レーンに「この目標に話しかける」入力欄を置き、Orchestrator を開かずに指示できるようにする。

### [critical] 【欠落】AI がチャットをスポーンできない。Worker が git worktree のコーディングエージェント専用で、汎用になっていない

- 根拠：- packages/daemon/src/orchestrator/grant.ts:14-40 の ORCHESTRATOR_PERMISSIONS は、session.create と session.send を意図的に外している。
- api.ts の task.spawnWorker は『creates a git worktree, a worker session and an agent run』で、Worker になれるのは git worktree の上で動く coding agent だけ。
- grantOrchestration（grant.ts:60-66）は chat 種別で、かつ project が必須。

画面にもそのまま出ている：
- 非コーディングの「新製品ローンチ」も Markdown の git リポジトリとして作るしかなかった。
- 10-command-agents.png ではプレスリリースに「acc/ws-gvwm6vms」と「+9 −0」が付く。
- 44-focus-worker-done.png のタブは「変更・テスト」。
- 83-project-settings-1.png には「既定ブランチ main」「テストコマンド pnpm test」。
- 51-integration-review.png は文書を「main へ早送りで反映」と表示する。
- 24-grant-dialog.png：お詫びメールのチャットでも、対象の既定が acme-web になっている。
- 人間が始めたエージェントにも「Worker」ラベルが付く（board.ts:63、97-new-agent-task.png）。
- 提案：Worker を「チャット Worker」と「ワークスペース Worker」の 2 種類にする。チャット Worker はリポジトリ不要で、成果物はメッセージか添付ファイル。spawnWorker を「session.create＋指示送信」の上に作り直し、git が要るのは workspace 付きの場合だけにする。プロジェクトはリポジトリなしで作れるようにする。
ブランチ名・行数・テスト・main への反映は、リポジトリ付きプロジェクトのときだけ出す。それ以外のときは「下書き → 確認 → 確定」という語彙とアイコンに切り替える。人間が始めたセッションの役割ラベルは「エージェント」にする。

### [critical] 【欠落】定期実行がまったく無い（API・UI・CLI・コミット、どれも 0）

- 根拠：- packages/protocol/src/api.ts のメソッド一覧に schedule.*、trigger.*、cron.* が無い。
- grep で cron|schedul|定期 を探すと、runtime/tools.ts:56-70 がエージェントの CronCreate などを『禁止』するためのコードだけが出る。
- concept §3 は「定期実行を登録する」を Control API の操作として明記しているが、未実装。
- 20261029_handoff.md:51 は「Phase B 以降」と後回しにしている。
- ユーザーは 2026-10-29 に、これを「キラキラしている部分」として名指しした。
- シーンの週次レポートは手で 1 回送っただけ。しかも素のチャットには他セッションを読むツールが無いので、中身はモックが書いた作文（22-focus-chat-in-project.png）。
- 提案：Daemon に schedule.create/list/update/delete/runNow を足す（対象は「このセッションにこのメッセージを送る」か「このプロジェクトでこの目標を Orchestrator に渡す」）。トリガーは cron 式と次回実行時刻で表す。
UI は 3 か所に出す：
- サイドバー：時計アイコンの「定期」セクションに次回実行時刻を並べる。

実行結果は通常のセッションとして親（定期の定義）にぶら下げる。Orchestrator の権限にも schedule.* を含め、AI が定期実行を登録できるようにする。

### [high] 【部分的】「誰が誰を起動したか」が 1 か所（Task ツリー）でしか見えない

- 根拠：- 親子が見えるのは、司令室の目標ツリー（10）と詳細パネルの「親」欄（40-focus-worker-awaiting-approval.png）だけ。

- Worker のチャットには、Orchestrator から受けた指示が表示されない（40。バグ 7）。
- Orchestrator のチャットでは、起動した 4 人が「ツール実行 5 件・操作 5」の折りたたみの中に埋もれていて、子セッションへのリンクにもアバターにもなっていない（30）。
- 目標ヘッダーには、作業を始めた指示ではなく、最初の相談文「…何から手を付けるべき？」が出る（10。バグ 4）。
- 提案：サイドバーを親子のツリーにする（Orchestrator の下に Worker を字下げし、折りたためるようにする）。

目標のタイトルには、grant の後の最初の指示か、Task 分解のときに LLM が付けた目標名を使う。

### [high] 【破綻】デモと初回体験で Orchestrator が無限ループし、画面が埋まる

- 根拠：- 32-focus-orchestrator-web.png：同じ報告「2件のTaskが完了し、統合候補ができました…」が約 2.6 秒ごとに繰り返され、Run は running のまま「00:31」と時間を数え続ける。
- 60-timeline.png：画面全体が同じ判断と予算の reserved・settled で埋まる。
- 原因は mockModel.ts の finalSummary。demo モード（01-onboarding の「デモで試す」）も同じモデルを使う。
- そのほかの崩れ：
  - 承認文の二重化「…使用を承認しますかを承認しますか？」（10、40）。
  - Task 説明に acc-mock の JSON がそのまま出る（13-command-task-detail.png）。
  - ストリーミングに途中から入ると最後まで何も出ない（21）。
  - Ctrl+N で空のセッションがサイドバーに残る（97 の「新しいチャット」「無題のエージェント」）。
- 既知のまま放置されている（approval-zero_handoff.md 残課題 4）。
- 提案：Orchestrator のループを Daemon で強制的に止める。同じ decision が連続したら Run を完了にし、目標の状態を「レビュー待ち」として静止させる（プロンプトには頼らない）。
e2e:audit に次の不変条件を足して CI で落とす：「同じ assistant テキストが 3 回」「Run が N 分以上 running で、しかも新しいイベントが同じ文の繰り返し」。
途中から入ったストリームのために、Daemon が書きかけの本文のスナップショットを返す API を足す。
Ctrl+N は、最初に送信するまでセッションを作らない（遅延作成）。

### [high] 【欠落】複数セッションを「同時に操る」手段が無い。1 画面に 1 セッションしか触れない

- 根拠：- 分割表示・複数選択・一括操作が無い。grep で「一括|すべて承認|split」が UI に見つからない。複数選択（x）は handoff.md:51 で後回し。
- Focus は 1 セッションずつ。司令室で同時に触れるのは、カードのインラインボタン（承認 Y・拒否 N・再試行 R・レビューを開始）だけ（10）。
- 「この 3 件は承認するから統合して」は、GUI ならレビュー画面を 1 件ずつ開くしかない（51）。自然言語でも、上の通り作業中の Orchestrator には届かない。
- パレットの「AI に頼む」（commands.ts:142-152）は、フォーカス中か直近のチャットに文を送るだけ。アプリ全体を操作できる窓口ではない。
- 提案：司令室のレーンとチップを、どれも複数選択できるようにする（Shift・Ctrl クリック、x）。選択したものに一括の操作バーを出す：承認・停止・再開・まとめて統合・指示を送る。
2〜4 分割の Focus（同じ目標の Worker を並べて見る）を用意する。
「AI に頼む」は、権限付きの常設コンダクターセッション（全プロジェクトの読み取り、作成・停止・統合の要求）に送るようにし、どの画面からでも 1 つの入力欄でアプリを操作できるようにする。

### [high] 【部分的】「実際に何が完成したの？」は、コードなら答えられるが、それ以外では自己申告どまり

- 根拠：- コードの場合：統合レビュー（51-integration-review.png）で、手順・テスト結果・統合後の差分が 1 画面に出る。ここはよくできている。
- 非コードの場合：プレスリリースも行番号付きの git diff でしか見られない。文書としてのプレビューが無い。
- Task の完了条件（TaskDetail.tsx:239-256）は、status が done になったら全部にチェックが付き、それまでは全部空の丸。条件ごとの検証は無い。
- resultSummary は Worker の最後の発言そのまま（workers.ts:500 lastAssistantText）で、つまり自己申告。
- 司令室の目標進捗は「Task 0/2」（10）。レビュー待ちが完了に数えられず、何ができたかが数字に出ない。
- 提案：Task ごとの「成果物カード」を作る。中身は、生成・変更したファイルのレンダリング済みプレビュー（Markdown・画像・表）と、完了条件ごとの ✓ / ✗ / 未検証。✓ は検品 Run（Reviewer）か、人間のクリックで付く。
目標レーンには「できたもの」のサムネイル列を出し、開かなくても完成物が見えるようにする。進捗のセグメントバーは、レビュー待ちと確定済みを別の色で数える。

### [high] 【部分的】「人間が暇になる」：承認 0 件は進んだが、留守中のことを後から把握する仕組みが無い

- 根拠：- 進んでいる点：おまかせプロファイルで承認 0 件（approval-zero_handoff.md）、再起動からの自動再開（resume.ts）、OS とアプリ内の通知（80-settings-1.png）。
- 足りない点：
  - 依存が終わったら待っている Worker を自動で起動する仕組みが無い（Orchestrator 任せ）。
  - 予算を見た延期も無い。
  - Timeline は生のイベント列で、「AI Orchestrator 応答 / ツール / 判断 / システム 予算 reserved・settled」が並ぶだけ（60）。何が起きたかの要約にはなっていない。
  - 「離席中に起きたこと」をまとめる画面が無い。通知は 1 件ずつのトースト（90、91）。

## 観点：coding bias（コーディング前提の偏り）: データモデル・フロー・UI 配置・文言・オンボーディング・デモ

結論から言うと、いまのプロダクトは「汎用のエージェント指揮アプリ」ではなく「git worktree で Claude Code を並列に走らせるツール」です。コーディングの前提は文言の表面ではなく、背骨の 3 か所に入っています。
1. Project はリポジトリが前提です。
2. Task の完了は git の統合を通さないと得られません。
3. 成果物は diff としてしか存在しません。
その結果、新製品ローンチのような非コードの目標も、ブランチ名・+N -M・「統合する」・テストタブ・「main へ反映」で表示されます。完成したプレスリリースの本文はどこにも出ず、進捗も 0/4 のままです。
直す順番は (a) コア概念の中立化（完了・成果物・作業場所・人間への質問）→ (b) git/統合/テストを「コード」kind のプラグインに隔離 → (c) 文言・デモの差し替え、です。文言だけを先に直しても、構造が「統合待ち」に戻ってきます。

### [critical] (a) Task の『完了』が git 統合でしか得られず、統合しても done にならない

- 根拠：packages/daemon: Task の状態を変えるのは orchestrator/workers.ts の running(133,252) / review(495) / ready(517) / failed(537) と tasks/service.ts の依存スケジューラだけ。integration/service.ts の apply（〜761 で status:'applied'）は Task に触れず、Task を 'done' にするコードはどこにもない（grep で確認）。UI の目標進捗は done だけを数える（CommandView.tsx:118）。screenshot 10 / 81: 新製品ローンチはプレスリリースが完成しても「Task 0/4」、acme-web も統合が反映待ちのまま「Task 0/2」。Worker 完了後の出口は review → 統合（merge + testCommand + main への早送り）の一本道。
- 提案：Task の状態を中立の『作業中 → 確認待ち → 採用 / やり直し』に作り直す。Task 行と確認カードに『採用』（✓ボタン、Y キー）と『やり直し』（↺、指摘入力）を置き、採用で done にする。git の統合は coding kind の『採用アクション』の 1 実装に格下げし、反映が承認された時点でデーモンが含まれる Task を done にする。目標の進捗バーは done と確認待ちを 2 色で塗り分け、『完成したのに 0/4』をなくす。

### [critical] (a) 成果物が diff・commit・test_result しかなく、中身を見る面がない

- 根拠：protocol/src/domain.ts:392 の ArtifactKind = diff|commit|test_result|file|note。runtime/executor.ts:159-165 は Worker の終了時に commitAll と recordDiff を呼ぶだけ。UI で成果を見せるのは TaskDetail.tsx の『変更ファイル』DiffBrowser、TaskTree.tsx の +N -M 列、IntegrationView の CombinedDiff だけ。screenshot 44: プレスリリースの完成画面の右パネルは『変更 1 ファイル +9 -0』で、本文のプレビューがない。screenshot 51: 認証ドキュメントは緑の『+』行の diff として読まされる。41-3: FAQ 作成の Worker に『テスト結果はまだありません』と出る。
- 提案：Artifact を『種類（文書 / 表 / レポート / リンク / メッセージ下書き / コード変更）＋プレビュー』に一般化する。Worker が `artifact.publish` のツールで成果物を明示的に登録する形にする。司令室の行とカードには成果物チップ（文書アイコン＋『press-release.md』＋1 行の冒頭）を出し、クリックでパネルに Markdown をレンダリングする。diff ビューアとテスト結果は coding kind のときだけ出すタブにする。

### [critical] (a) Project とエージェントの作業場所が git リポジトリ必須

- 根拠：domain.ts:42 に『Logical unit of work: a repository plus settings』とある。task.spawnWorker は必ず createWorktree を呼び（workers.ts:623-640）、repoPath がなければ invalidParams（workspace/service.ts:105-108『リポジトリ（repoPath）が設定されていません』）。UI のプロジェクト追加は git ルートが必須（ProjectDialog.tsx:121『Git リポジトリのフォルダ』、181、274、説明文『エージェントはこのリポジトリから作った worktree で作業します』）なので、リポジトリなしのプロジェクト（社内報告）は API からしか作れない。session.grantOrchestration は projectId が必須（orchestrator/grant.ts）で、screenshot 24 ではお詫びメールのチャットの対象に acme-web が既定で入る。シーンでは非コードのローンチ企画を Markdown だらけの git リポジトリにするしかなかった。
- 提案：Project を『作業の箱（作業フォルダ・コネクタ・既定モデル・予算・定期実行）』に再定義し、repoPath は任意の『コードを接続』に移す。WorkspaceKind に git なしの `scratch`（ACC_HOME 配下のフォルダ）を足し、Worker の既定にする。プロジェクトの追加は名前だけで作れるようにし、フォルダとリポジトリはあとから足すアイコンボタンにする。プロジェクトのないチャットに Orchestrator 権限を与えたときは、その場で scratch の箱を作る。

### [high] (a) Orchestrator・Worker のプロンプトと実行環境がコーディング固定

- 根拠：orchestrator/executor.ts:32『You lead coding agents… You never edit code』、52『without editing the same files』、53『Each works in its own git worktree; …recorded as a diff』、55-57 は統合・テスト・コンフリクトの手順。runtime/executor.ts:265-267 は Worker への指示の末尾に『専用の git worktree…完了すると変更は自動でコミットされます』を付ける。claude/runtime.ts は systemPrompt に preset 'claude_code' を使い、AUTO_MODE_SETTINGS（100-106）は『Tests, builds, linters… are the normal work』。本物のモデルなら、ローンチ企画の目標でもファイル分割 → 統合 → テストの流れに誘導される。
- 提案：プロンプトを『中立のコア（目標の分解・委任・監督・まとめ・報告）』と『kind の断片』に分けて合成する。Worker にも kind のプリセットを持たせる（リサーチ = Web と要約、文書 = 1 ファイルの成果物、データ = 表、コード = claude_code）。Orchestrator が task.create のときに kind を選び、デーモンがランタイム・ツール・作業場所・確認方法をそれに合わせて解決する。

### [high] (a) 人間への質問・判断が『ツール使用の承認』にしかならない

- 根拠：本物のランタイムでは AskUserQuestion が禁止されていて（runtime/tools.ts:62）、AUTO_MODE_SETTINGS は『Nobody answers questions during the run』と書いている。人間に聞く経路は mock の `ask`（mock/runtime.ts:136）だけで、それも tool_use の Approval として出る。ApprovalKind は tool_use|integration|budget|grant|other で、質問・判断の種類がない。screenshots 10 / 40: 『価格を FAQ に載せてよいか』という経営判断が『ツール「AskHuman」の使用を承認しますかを承認しますか？』と『危険度 中』の表示に『今後も許可…』まで付いて出る。
- 提案：Approval に `decision`（質問文と 2〜4 個の選択肢、自由記述も可）を足し、すべてのランタイムに `human.ask` ツールとして渡す。カードでは危険度バッジと『今後も許可』を出さず、選択肢をそのままボタンにする（例『980 円で載せる』『発売時にお知らせ』）。サイドバーと司令室では『判断待ち』を『承認待ち（権限）』と別のアイコンにする。

### [high] (b) 『確認待ち』の状態語とアイコンが git（統合待ち・GitMerge）

- 根拠：lib/status.ts:22 で DisplayState の review が『統合待ち』、ui/StatusIcon.tsx:144 では review のアイコンが GitMerge、Sidebar.tsx:30 のセクション名も『統合待ち』。一方 TASK_STATUS_LABEL の review は『レビュー待ち』。screenshot 10 では同じ状態が、ツリーの行で『レビュー待ち』、カードで『統合待ち』と同じ画面に並ぶ。プレスリリースのような文書にも git のマージアイコンが付く。目標見出しのボタンは『統合する』（TaskTree.tsx:340-358、GitMerge アイコン）と『統合: 反映待ち』。
- 提案：状態語を中立の『確認待ち』1 つに統一し、アイコンは受信箱か目のマークにする。『統合』『反映』『main』は coding kind の統合ビューの中だけで使う。目標見出しの右端は、確認待ちの件数バッジと『まとめて確認』ボタンにする。

### [high] (b) 司令室ツリーで一番幅を取るのがブランチ名と diff 統計

- 根拠：TaskTree.tsx:150-165 では w-48 の GitBranch＋ブランチ名の列と w-16 の +N -M の列が固定で、何をしているかや何ができたかを出す列はない。screenshot 10: ローンチの 4 行に `acc/3-krj9atyj`、`acc/faq-10-vpb1a9vh`、`—` が並ぶ。Focus の見出しにもブランチ名が出る（40・44 の `acc/faq-10-vpb1a9vh`）。合格基準『5 秒眺めて進捗・問題・出番が分かる』に対して、一番広い領域が無意味な識別子に使われている。
- 提案：ブランチ列とdiff列を 1 本の『いまの一言 / 成果』列に置き換える。実行中は Run.activity（例『競合 3 社の価格表を作成中』）、確認待ちは成果物チップ、判断待ちは質問の要約、失敗は原因の 1 行を出す。ブランチと diff は coding kind の行だけ、ホバーのツールチップに入れる。

### [high] (b) 詳細パネルのタブが全セッション共通の『概要 / 変更 / テスト / ログ』

- 根拠：store/ui.ts:6 で PANEL_TABS = ['overview','changes','tests','logs'] が固定。DetailPanel.tsx:53-58。screenshot 24: 普通の会話のお詫びメールチャットにも『変更』『テスト』タブが出る。Worker の欄は『worktree』と『権限 worktree 内』（DetailPanel.tsx:224、44）。

## 観点：作業として破綻しないこと（再起動・中断・表示の鮮度・完了の真偽）とコスト管理（可視化・上限の強制・警告）

結論から言うと、予算は「実装されているように見えるだけ」で、主役の Claude Worker には実行中まったく効かない。費用は Run が終わったときにまとめて計上され、SDK の maxBudgetUsd も渡していない。
さらに Worker の未使用予算が親に戻らない。このため $3 の Orchestrator は「配分済み $2.20・使用 $0.60・空き $0.20」で、次の LLM 呼び出し（予約 $0.25）ができずに詰む。スクショ 31 がちょうどこの状態。
画面のコスト表示も実態と合っていない。ヘッダーの「$0.62 / $3.00」は、ツールチップでは「配分込み」と書いているのに、実際は自分の Run の合計だけ。残りの額、ゴール単位のコスト、Worker の予算、80% 警告はどこにも出ない。
破綻しにくさの面では、既定の「この実行のみ」権限だと、デーモンを再起動したあと Orchestrator が再開しない。監視も LLM のポーリング頼みで、80 ターンで黙って「完了」（緑のチェック）になる。429 や 5xx の一時エラーにも自動リトライがない。
上限の仕組みもない。1 日・プロジェクト・全体の上限はなく、通常チャットと人間が起動したエージェントは予算を設定する手段自体がない。auto mode の分類器の費用も計上されていない。

### [critical] Claude Worker の費用は Run 終了時にしか計上されず、予算が実行中に効かない

- 根拠：packages/daemon/src/runtime/claude/normalize.ts:213-216,467-470：usage は SDK の `result` メッセージ（query の最後）でしか出さない。assistant メッセージごとの usage は捨てている。
runtime/executor.ts:42-44 のコメントは「During the run, reportUsage stops it at the limit」と書いているが、Claude ランタイムでは reportUsage が終了時に 1 回しか来ないので事実と違う。開始前の assertBudgetLeft() しか効いていない。
runtime/claude/runtime.ts は SDK の `maxBudgetUsd` を渡していない（SDK の sdk.d.ts:1984 にはこのオプションがある。maxTurns も渡していない）。
policy/budget.ts:259-268 の recordSpend は、子が上限を超えて使っても子の spentUsd が増えるだけ。親の allocatedUsd は子の上限額のままなので、超過分は親プール（Orchestrator の $3）に反映されない。
その結果、$0.55 を割り当てた Worker が 1 回の Run で数ドル使えて、ゴールの $3 も実質的な上限にならない。実行中の盤面には ≈$0.00 が出続け、終わった瞬間に跳ね上がる（スクショ 10-command-agents-2 の Worker 行は「≈$0.01」）。
- 提案：(1) SDK の query に `maxBudgetUsd: 予算の残り` と `maxTurns` を必ず渡し、`error_max_budget_usd` を budget_exhausted に対応させる。
(2) assistant メッセージごとの usage から推定費用を出し、Run の usage と予算の両方に途中経過として計上する。result で確定値に差し替え、推定と確定の 2 段階で扱う。
(3) 子の超過分を祖先へ伝播させる。親の free を「上限 − Σmax(子の上限, 子の使用額)」で計算すれば、ゴールの上限が本当の上限になる。
(4) 盤面の Worker 行にミニ予算バー（使用/上限）を置き、実行中でも伸びていくようにする。

### [critical] Worker の未使用予算が親に戻らず、Orchestrator が自分の予算で詰む

- 根拠：スクショ 31 のポップオーバーは「予算 $3.00 · 配分済み $2.20 · 使用 $0.60」で、空きは $0.20 しかない。一方、LLM を呼ぶたびに予約する額は既定 $0.25（設定 80-settings-2、protocol/domain.ts:711）。
llm/toolLoop.ts:100 の reserveBudget → runs/manager.ts:988-997 で、予約額を確保できないと budget_exceeded になる。つまり task.wait から戻った次の呼び出しで Orchestrator が「予算の上限に達しました」で失敗し、統合までたどり着けない。
budget.release() を呼ぶのは API ハンドラ（policy/index.ts:115）だけで、Worker の Run が終わっても自動では返却しない。grep で確認した。concept §5 の「未使用の予算を親へ戻せるようにする」は実装されていない。
ORCHESTRATOR_PERMISSIONS（orchestrator/grant.ts:18-40）は budget.* を意図的に外しているので、Orchestrator が自分で返却することもできない。
予算を増やす API（budget.update / increase）がない。grant を付け直すと、そのたびに新しい root 予算ができる（grant.ts:80-87）。古い予算と子の配分は宙に浮き、ヘッダーには新しい方の上限しか出ない。
Worker の再試行は、予算が active なら同じ予算を引き継ぐ（workers.ts:230-236）。使い切った予算でも引き継ぐので、assertBudgetLeft で即座にまた失敗する。
- 提案：(1) Worker の Run が終端状態になったら、その Worker の予算を自動で releaseTree して空きを親へ戻す（Task が review / failed になる時点）。
(2) Orchestrator 自身の呼び出し分は、子に配る前に先に確保する（配分は「空き − 予約額 × N」まで）。
(3) 予算チップに「＋$1 / ＋$5」ボタンを付ける。押すと同じ予算ノードの limitUsd を増やす（budget.raise を新設し、人間だけが使える）。付け直しで root を増やすのはやめる。
(4) 予算切れで止まった Run の再試行は、予算を足す操作と 1 つにまとめる（下の「予算切れ」の項目を参照）。

### [high] ヘッダーの「使用額 / 上限」が実態と違い、残額・警告・ゴールのコストがどこにも出ない

- 根拠：apps/desktop/src/components/focus/FocusView.tsx:79,107-113：ツールチップは「このチャットの予算（Worker への配分を含む使用額 / 上限）」と書いている。しかし表示している数字は `sumUsage(runs)`、つまりこのセッション自身の Run の合計で、配分は含まない。
そのためスクショ 30 では「$0.62 / $3.00」と出て $2.38 残っているように見える。実際の空きは $0.20 で、しかもポップオーバーの「使用 $0.60」とも一致しない（予算が付く前のチャット Run $0.02 を含めているため）。
予算を表示しているのは `session.kind === 'chat'` のときだけ（FocusView.tsx:78）。Worker（$0.55）の予算は、フォーカス画面にも詳細パネル（スクショ 43：コスト「≈$0.00」だけ）にも盤面にも一切出ない。
TaskTree / TaskBoard / TaskDetail / IntegrationView には Cost も budget も 1 つもない（grep で確認）。ゴールのヘッダーは「Task 0/4」と進捗バーだけ（スクショ 10）。
80% 到達の警告や「残り僅か」の表示はなく、grep しても「残り」「警告」の UI は出てこない。
タイムライン（スクショ 60）には「$0.00 / $5.00 · reserved」「settled」が LLM 呼び出し 1 回につき 2 行ずつ並び、ただのノイズになっている。
- 提案：(1) 予算チップを 1 本の積み上げバーにする：使用（濃い色）＋Worker に配分（中間色）＋空き。数字は「残り $0.20」の 1 つだけにする。
(2) 盤面のゴールヘッダー（Task 0/4 の横）にも同じバーを置き、ゴール全体の使用額 / 上限が 5 秒でわかるようにする。
(3) 空きが 20% を切ったら、バーをアンバーにして要対応のゾーンへ上げる（承認待ちと同じ扱い）。0 になったら赤。
(4) タイムラインでは予算の reserved / settled を既定で隠す。代わりに「50% / 80% / 上限到達」の節目だけを 1 行のイベントにする。

### [high] 既定の権限（この実行のみ）では、再起動後に Orchestrator が再開しない

- 根拠：権限ダイアログの既定は「有効期間: この実行のみ」（スクショ 24、apps/desktop/src/model/grant.ts:118 `lifetime: 'run'`）。
policy/grants.ts:536-555 の expireForRun は、Run が終わると（中断を含む）そのセッションの lifetime=run の grant を取り消し、そこから委譲した Worker の grant もまとめて取り消す。
orchestrator/resume.ts:70-71 は `grantValid` が偽なので再開しない。設定「再起動のあと Orchestrator を再開: オン」（スクショ 80-settings-3）は、既定の付与ではまったく働かない。
core/recovery.ts:57-66 は保留中の承認を取り消すので、人間への質問（スクショ 10 の「価格（月額 980 円）を FAQ に載せてよいですか？」）も消える。
実行中だった統合は failed になる（integration/index.ts:116）。
つまり OS の再起動やアプリの更新が 1 回あるだけで、進行中のゴールはすべて止まる。Task は「着手可能 / interrupted」のまま残り、人間が権限を付け直して指示を送るまで誰も動かない。
- 提案：(1) Orchestrator の grant の有効期間を「このゴールが終わるまで」（Task がすべて終端になるまで）に変え、既定にする。「この実行のみ」はゴール単位の概念と合っていない。
(2) 再起動時の中断（daemon_restart / daemon_shutdown）では grant を失効させない。
(3) 再起動で取り消した承認は、再開した Run で同じ内容をもう一度出す。
(4) 再開できなかったゴールは盤面のヘッダーに「⏸ 再起動で停止 ・ 再開」ボタンとして出す（文章のお知らせではなく、ボタン 1 つにする）。

### [high] Orchestrator の監視が LLM のポーリング頼みで、80 ターンで黙って「完了」になる

- 根拠：task.wait の timeoutMs は最大 600_000、既定 60_000（protocol/api.ts:635）。タイムアウトのたびに会話の全文脈を載せた LLM 呼び出しが 1 回走る。人間が承認を夜まで放置すると、待っているだけで呼び出し（費用）が積み上がる。
ORCHESTRATOR_MAX_TURNS = 80（orchestrator/executor.ts:9）。runToolLoop は上限に達すると `stopReason: 'max_turns'` を返すが（llm/toolLoop.ts:95-96）、executor は戻り値を見ていない。grep しても max_turns を扱う箇所がない。その結果、途中で打ち切られた Orchestrator が「完了」（緑のチェック）になる。
ループを検知する仕組みもない。モックの Orchestrator は同じ報告を 2.6 秒ごとに繰り返し、入力 47,340 トークンになっても「実行中」のままで、要対応には上がらない（スクショ 32、60）。
- 提案：(1) 待機は daemon 側のイベントで起こす：Worker の終了・失敗・承認依頼のときにだけ Orchestrator を起こし、LLM にポーリングさせない。
(2) max_turns に達した Run は「completed」ではなく専用の状態（打ち切り）にし、要対応に出す。
(3) 同じツール呼び出しや同じ文章が 3 回続いたら停止し、「ループの疑い」として要対応に上げる。
(4) Run の行に「最後に進展してから 12 分」を表示する。時刻は Task の状態が最後に変わった時点を基準にする。

### [high] auto mode の分類器の費用が予算にも表示にも入っていない

- 根拠：docs/snapshot/20261029_auto-mode-cost.md:15 に「この額は SDK の total_cost_usd に入らない（Budget は少なく数える。未対応のまま）」とある。設定画面（スクショ 80-settings-2）にも「分類器の費用はまだ予算に含まれません」と書いてある。
手元の分類器だと、判定 1 回あたり約 $0.011、キャッシュが冷えていると $0.126。runtime/claude/runtime.ts:115 の `classifyAllShell: true` で、シェルコマンドはすべて判定にかかる。
上流が `safeguards` に対応しないとき（LiteLLM の先が Bedrock / Vertex など、社内でよくある構成）は手元の分類器に自動で切り替わる（同じ snapshot の表、30 行目）。そうなると Worker 1 人が 100 コマンドを実行するだけで $1 以上が帳簿に載らない。$0.55 の Worker 予算の 2 倍が見えないところで消える。
- 提案：(1) Run.permission.judge が client のあいだは、分類器を通した判定 1 回ごとに推定額（設定値、既定 $0.011）を recordSpend し、costSource を estimated にする。
(2) 判定の数は tool.decided ですでに数えているので、Run の詳細のコスト欄を「本体 $x ＋ 安全判定 $y」の 2 段に分ける。
(3) サーバー判定から手元の分類器に落ちた瞬間、予算チップに小さな「判定に課金中」アイコンを出す。

### [high] 1 日・プロジェクト・全体の上限がなく、予算なしで無制限に走る経路が多い

- 根拠：予算を作れる場所は Orchestrator の権限ダイアログだけ（grant.ts:80-87、orchestration.ts:144-165）。
通常チャットと、人間が起動したエージェントには予算を付ける UI がない（スクショ 97 の新しいエージェント画面、設定にもない）。sessions/index.ts:217 の sessionBudgetId が null を返すと、その Run は予算なしの無制限になる。
権限ダイアログには「なし」の選択肢がある（スクショ 24）。さらに予算の作成に失敗しても権限は付与される（orchestration.ts:78-79「A failed budget does not undo the grant」、toast は「権限は付与済みです」）。
costSource が unknown（価格のわからないモデル）だと費用は 0 として計上され、予算は永遠に減らない（llm/openai.ts:226-247）。
resume.ts:94 は予算が active でないと `budgetId: null` で再開する。予算がない側に倒れる（fail-open）。
設定にもプロジェクト設定（スクショ 83）にも、1 日やプロジェクトの上限欄がない。
LiteLLM のキーの予算超過エラーも分類していない（llm/gatewayErrors.ts は model_not_found / cooldown だけ）。社内の LiteLLM キーの上限に当たると、10 本が一斉に原因不明の失敗として並ぶ。
- 提案：(1) 設定に「1 日の上限」と「プロジェクトごとの月の上限」を置き、すべての予算の根（global / project ノード）にする。予算のない Run は作れないようにする。
(2) タイトルバーの「今日 $0.70」を「$0.70 / $20」の小さなリングに変える。
(3) unknown の費用は、モデルのトークン数 × 保守的な単価で推定計上し、0 にしない。
(4) LiteLLM の budget_exceeded と 429 を分類し、「社内キーの予算切れ」として 1 枚の要対応カードにまとめる。

### [medium] 一時的なエラー（429 / 5xx）で Orchestrator やチャットの Run が即座に失敗する

- 根拠：llm/openai.ts:376-383 は 429 / 5xx に「しばらく待ってから再試行してください」という文言を付けるだけ。daemon の llm/ 以下には retry や backoff の実装がない（grep で確認）。
10 本を並列で LiteLLM に流すとレート制限に当たりやすいのに、1 回の 429 で Orchestrator の Run が failed になり、ゴールが止まる。再開するには人間が再試行を押す必要がある。
- 提案：gateway に、指数バックオフで 3 回まで自動リトライする処理を入れる（429 / 529 / 5xx と接続断が対象。Retry-After を尊重する）。
リトライ中は Run 行のステータスに小さな「再接続中」アイコンを出し、失敗にはしない。

### [medium] アーカイブ（E キー 1 回）で、実行中のセッションが画面から消えるのに Run は止まらない

- 根拠：session.archive（sessions/index.ts:129-148）は archivedAt を立てるだけで、active run を止めない。
model/board.ts:109 は archivedAt のあるセッションを盤面から外す。ショートカットは `archive: { keys: 'E' }`（lib/shortcuts.ts:37）で、実行中でも確認なしにアーカイブできる（CommandView.tsx:387-389）。
アーカイブしたあとも、見えない Run が費用を使い続ける。
ゴール単位で止める手段もない：Orchestrator を停止しても子の Worker は止まらない。parentRunId をたどって cancel する処理がなく、UI にも「このゴールをすべて停止」がない（grep で確認）。
- 提案：(1) 実行中のセッションでは、アーカイブを「停止してアーカイブ」に変えて確認を出す。
(2) ゴールヘッダーに ■（ゴールを停止）を置き、Orchestrator と、その配下の Worker・Integrator の Run をまとめて cancel する。
(3) 盤面の「実行中」の件数は、アーカイブ済みの Run も数える。

### [medium] 予算切れが普通の「失敗」として表示され、再試行が必ずまた失敗する

- 根拠：runs/manager.ts:506-517 は budget_exhausted を failed にする。UI の盤面（model/board.ts:119）は他の失敗と同じ扱いで、「再試行 R」ボタンを出す（スクショ 10 の失敗カードと同じ見た目）。
run.retry は同じ budgetId を引き継ぎ（runs/index.ts:96）、Worker の場合は task.retry が使い切った予算をそのまま使う（workers.ts:230-236）。だから押しても即座にまた失敗する。
apps/desktop/src/daemon/errors.ts:50 には「予算の上限に達しました」というトーストがあるだけ。
- 提案：予算切れの専用状態とアイコン（空の財布や $ に斜線）を作る。カードのボタンは「＋$1 して続ける」「＋$5 して続ける」「やめる」の 3 つにする。
再試行ボタンは出さない。

### [medium] 「完了」と言っていることと実際に完了したことの区別が弱い

- 根拠：workers.ts:490-501 は、Worker の Run が completed なら、完了条件（acceptanceCriteria）を照合せずに Task を review にする。resultSummary には Worker の最後の発言（主張）がそのまま入る。
Orchestrator の報告は「2件のTaskが完了し」と言っているが、Task は「レビュー待ち」で、盤面の表示は「Task 0/2」（スクショ 32 と 10）。同じ画面の中で「完了」の意味が食い違っている。
acceptanceCriteria を表示しているのは TaskDetail.tsx だけ（grep で確認）。統合レビュー画面（スクショ 51）には完了条件がなく、テストが通ったかどうかと diff しか出ない。
変更のない Worker も review（no_changes）になって、完了したように並ぶ。
- 提案：(1) 統合レビュー画面と Task 行に、完了条件をチェックリストのアイコン（✓ / ？）として並べる。
(2) Worker の最後に「完了条件ごとの自己申告」を構造化して出させ、根拠（ファイルや diff）のないものは ？ にする。
(3) Orchestrator の報告文にある「完了」は、daemon の Task 状態と合わない場合には使わせない。プロンプトで縛るのではなく、tool の結果に状態の語を固定で渡す。

### [medium] worktree と統合ブランチが増え続け、片付ける手段がない

- 根拠：workers.ts:65-66 には「the worktree and branch are always kept」とある。workspace.remove の API（workspace/index.ts:89）はあるが、UI からは一度も呼んでいない（apps/desktop には sync / timeline のイベント処理しかない）。統合を反映したあとの自動削除もない（integration/service.ts）。
10 本の並列を毎日回すと、worktree（それぞれ依存パッケージ込み）が数百単位で溜まり、ディスクとブランチ一覧が膨らむ。
- 提案：main に反映した Task、または却下・キャンセルした Task の worktree は、7 日後に自動で削除する（ブランチ名はログに残す）。
プロジェクト設定に「worktree 12 個・3.4GB・片付ける」の 1 行を置く。

### [medium] 再接続や再読み込みのあとの表示が古い・ずれる

- 根拠：途中から開いたストリーミングは、生成が終わるまで「回答を生成中…」しか出ない（scene のバグ 1、スクショ 21、ChatStream.tsx）。Claude Worker の費用は終わるまで ≈$0.00 のまま（上の critical 項目）。
Run 履歴は attempt 番号を出しているので、別のメッセージの Run が「#1 実行中」「#1 完了」と並ぶ（スクショ 30、DetailPanel.tsx:109-113）。
タイトルバーの「今日」は run.createdAt で絞っている（TitleBar.tsx:62-65）ので、日をまたいで続く Run の費用は今日の分に入らない。司令室の「合計 ≈$0.70」（CommandView.tsx:81,98）は、何の合計なのか（盤面に出ている全期間？）がわからない。
- 提案：(1) daemon が「ここまでの部分テキスト」を run.get / session.messages で返し、途中から開いても続きから見えるようにする。
(2) Run 履歴は通し番号と、きっかけになったメッセージの冒頭で区別する。
(3) 費用の集計は「使った時刻」を基準にする（usage イベントの時刻ごとに集計）。「合計」というラベルはやめて「今日」に統一し、期間ごとの内訳は 1 つのコスト画面（日・プロジェクト・ゴールの棒グラフ）に集める。


## 観点：オペレーター側に立つLLMと自動化（権限付与からのセッション作成・管理・停止、普通のチャットを生やす、再割り当て、「いま何してる？」、定期実行、コネクタ/MCP、AIが代わりにやったことの見える化）

「普通のチャットに権限を渡すと、そのAIがアプリを動かす側に回る」という核は、Worker を起動して統合に回す一本道でしか成り立っていない。
いちばん重い問題は、動いている Orchestrator に話しかけられないこと。「いま何してる？」「2人追加して」「止めて」は、どれもセッション使用中の衝突（conflict）で送信に失敗する。
定期実行は protocol にも daemon にも UI にもまったく無い。コネクタ/MCP もゼロで、strictMcpConfig により外部 MCP は完全に遮断されている。
AI が起動できるのは git worktree で動くコーディング Worker だけで、普通のチャットは生やせない。Orchestrator のプロンプトも「You lead coding agents」に固定されている。
権限ダイアログに出る「できること」が、daemon が実際に与える権限と食い違っている。また '*' プリセットでは、AI が作った子チャットが予算の外で動ける。
誰が何をなぜ起動したかは、詳細パネルの「親」欄と、機械的な行で埋まったタイムラインからしか読み取れない。

### [critical] 実行中の Orchestrator に話しかけられない（「いま何してる？」が送れない）

- 根拠：packages/daemon/src/runs/manager.ts の start(): セッションに active な Run があると conflict（このセッションでは別の Run が実行中です）を返す。Orchestrator の Run は task.wait（最大600秒の long-poll。executor.ts の手順3で long timeout を指示）で Worker の完了まで居座るため、作業中はずっと active のまま。Composer.tsx は実行中でも送信でき、placeholder は「何でも聞いてください」（30-focus-orchestrator-launch.png、32）。actions.ts の sendMessage は、失敗したメッセージを failed にするだけ。concept 3.2 の「今何してる？」「テスト担当を2人追加」「API改修は止めて」は、作業中の会話としては一つも成立しない。
- 提案：Orchestrator の Run に inbox を持たせる。実行中に届いたユーザーメッセージは inbox に積み、task.wait と integration.wait は interruptedBy=user_message で即座に返す。モデルは次のターンでそのメッセージを読む。UI は実行中、コンポーザーを「割り込み指示」モードにし、送ったメッセージには割り込みバッジを付ける。conflict では落とさない。状況を尋ねる質問には、読み取り専用の並行 Run で即答できるようにする。

### [critical] 定期実行が存在しない（API・スケジューラ・画面のどれも無い）

- 根拠：protocol/src/api.ts に schedule 系のメソッドが無い。runtime/tools.ts は CronCreate/CronList/ScheduleWakeup/RemoteTrigger を「scheduling belongs to the daemon」という理由で禁止しているのに、daemon 側にもスケジューラが無い（core に timer や cron の module が無く、tasks/service.ts の SCHEDULER は依存関係の解決だけ）。development.md は「アプリを閉じてもデーモンは動き続ける（定期実行のため）」と書くが、実体が無い。scene の週次レポートも定期実行として設定できなかった。source-vision では、キラキラしている部分として定期実行を名指ししている。
- 提案：protocol に schedule.create/list/update/pause/delete/runNow を追加する（cron とタイムゾーン、スリープ明けの取りこぼし方針、対象テンプレートはチャット/エージェント/Orchestrator のどれか、毎回の予算と grant）。daemon に scheduler module を置き、発火ごとに新しい Run を作って createdBy に system:scheduler を記録する。権限パターン schedule.* を設け、AI も grant の範囲内で登録できるようにする。UI は司令室に「次の予定」レーン（時計アイコン、次回までのカウントダウン、前回の結果アイコン）を置き、サイドバーにも時計付きの行を出す。

### [high] AI が普通のチャットを生やせない。Worker はコーディング専用

- 根拠：orchestrator/grant.ts の ORCHESTRATOR_PERMISSIONS は session.create と session.send を意図的に外している。workers.ts の spawn は常に kind:'agent' で、workspaceFor（git worktree）を必須にしている。executor.ts の buildOrchestratorPrompt は「You lead coding agents」「You never edit code」「git worktree」「test command」で始まり、ローンチ準備のような業務でもコーディング前提で動く。launch プロジェクトは Markdown だけの git リポジトリにする必要があり、テストコマンド欄には pnpm test が出る（83）。
- 提案：task.spawnWorker に kind（chat か agent）を足す。チャット Worker は worktree を作らず、成果物を note や file の Artifact として残す。session.spawnChat を作り、親セッション・予算スライス・権限の継承を daemon が自動で付ける。Orchestrator のプロンプトは「Task を分けて担当を起動し監督する」という中立の文に変え、コーディング固有の手順はプロジェクトに repo があるときだけ足す。

### [high] 権限ダイアログの「できること」と実際の権限が違う

- 根拠：apps/desktop/src/model/grant.ts の GRANT_PRESETS.orchestrate は session.create/session.send/grant.create/budget.allocate を含む。ダイアログはこのリストから「ほかのセッションへの指示」「予算の配分」「Worker への権限の委譲」のチップを出す（24-grant-dialog.png）。ところが daemon/orchestration.ts は、プロジェクトがあると session.grantOrchestration を呼び、daemon の ORCHESTRATOR_PERMISSIONS を付与する。こちらにはそれらが無いので、付与後のポップオーバー（31）では項目が減っている。「すべての操作」は「設定の変更」を出すが、settings.update は tool:false なので AI からは使えない。
- 提案：プリセットの定義を protocol に一本化する。チップは付与後に返る grant.permissions から作る。付与前のプレビューにも daemon の dry-run を使い、表示と強制される内容が必ず一致するようにする。

### [high] '*' プリセットでは、AI が作った子チャットが予算の外で動ける

- 根拠：sessions/index.ts の session.send は sessionBudgetId(子セッション) を使う。AI が session.create したチャットには予算が無いため budgetId は null になる。runs/manager.ts は budgetId が無いと予算チェックも記帳もしない（825-826行、968行）。policy/grants.ts の assertAgentMayStartRun は、親子関係とセッション grant の有無しか見ない。予算付きの Orchestrator が子チャットに LLM を呼ばせると、上限に数えられない。「制約はプロンプトでなく Core Daemon が強制」に反する。
- 提案：agent が始める Run（session.send や run.retry）には、呼び出し元の予算から切り出した子予算を必須にする。呼び出し元に予算があり、子に予算が無ければ拒否する。UI の予算表示も、子チャットの消費を親の目標にまとめて出す。

### [high] Orchestrator を止めても Worker は止まらず、終了後に監督する者がいない

- 根拠：run.cancel は子 Run に連鎖しない（parentRunId は保存されるだけで、manager.ts に cascade が無い）。commands.ts の stop 確認文は「作業内容は worktree に残ります」とだけ書き、Worker が動き続けることに触れない。既定の lifetime は run（DEFAULT_GRANT_INPUT と makeOrchestrator）で、Run が終わるとチャットはツールを失う。その後 Worker が終わっても Orchestrator を起こし直す仕組みは無く、再開はデーモン再起動時の resume.ts だけ。ORCHESTRATOR_MAX_TURNS=80 に達しても同じ状態になる。concept 2.2 の「完了したので待機していた担当を起動」が成り立たない。
- 提案：停止ダイアログで「Worker も止める / Worker は走らせたまま」を選べるようにし、子の数をアイコン付きで見せる。task の review/failed、承認の決着、統合の完了といった出来事で Orchestrator の新しい Run を自動で起こす（event 駆動の wake）。その Run は daemon が要約した状態から始める。長い待機を一つの Run で抱え続ける設計をやめる。

### [high] 自然言語の入口が、権限の無いチャットに落ちる

- 根拠：app/commands.ts の askAi（パレットの「AI に頼む」）は、フォーカス中か最新のチャットに送るだけで、権限を見ていない。sessions/chat.ts は、grant が無いチャットにツールを一つも渡さないので、状態を読まずに答える（推測で答えかねない）。最新のチャットは実行中の Orchestrator であることが多く、そうなると conflict で失敗する。「GUI と自然言語のどちらでも同じ機能」（concept 3.2）が成り立たない。
- 提案：常設の「オペレーター」セッションを一つ置く。読み取りと、AI がしてよい操作の preset を既定で持たせ、パレット・司令室・グローバルショートカットから呼べるようにする。普通のチャットにも、状況を照会する読み取り専用ツール（session.list、task.list、run.get、budget.get）を既定で渡す。

### [medium] 再割り当て・増員・延期・人間への質問の手段が無い

- 根拠：task.retry は元の Worker セッションにしか差し戻せない。別の担当やモデルへの再割り当て（task.reassign）、延期（defer）、優先度にもとづく実行順の調整、予算を見た再計画の API が無い。maxWorkers の引き上げは、人間が「設定を変える」で付け直すしかない（31）。AI が人間に質問する手段も無い。AskUserQuestion は禁止されていて、AskHuman は audit-scene.ts のモックにしか無く、approval.respond は承認/拒否とメモだけ。そのため「価格980円で載せてよいですか？」がツール承認として出て、「承認しますかを承認しますか」と文言も重複する（40）。
- 提案：task.reassign（別セッションや別モデルへ、worktree を引き継ぐ）と task.defer を追加する。grant.requestIncrease を作り、AI からの増員要請を承認カードに出して、人間が1クリックで上限を上げられるようにする。Approval に question 種別を足し、選択肢と自由回答を受けられるようにする。回答できるなら Orchestrator が先に受け、できなければ人間に回す。

### [medium] 誰が何を何のために起動したかが一覧で見えない

- 根拠：サイドバーは平坦なリストで、parentSessionId を使っていない（desktop で親子を使うのは DetailPanel.tsx の「親」欄と、司令室の Task ツリーだけ）。Task を持たない子チャットはツリーにも出ない。Worker のチャットには受け取った指示が出ない（workers.ts は instructions があるときだけメッセージを追加する）。目標ヘッダには、最初の雑談メッセージが表示される（10）。タイムラインは1ターンごとに状況・使用量・予算 reserved/settled の行が並び、判断（理由）の行は全体のごく一部（62）。
- 提案：サイドバーを親子のツリーにして、インデントと起動者のアバター（人/AI）で関係を見せる。Worker のチャットの先頭に「依頼カード」（依頼元 Orchestrator、目的、受入条件、予算）を固定する。目標ヘッダは、Orchestrator が実際に受けた指示か Task の親を出す。タイムラインの既定フィルタは「判断＋状態変化」だけにし、予算の reserve/settle や「状況」行はまとめて畳む。

### [medium] コネクタ/MCP がゼロで、外部 MCP は意図的に遮断されている

- 根拠：runtime/claude/runtime.ts は settingSources: [] と strictMcpConfig: true を指定し、使える MCP は in-process の acc（Control API）だけ。protocol にも settings にも connector や mcp の型が無い。チャット Run は LiteLLM のツールループに apiTools しか持たず、Web もファイルも使えない。concept 10.2 の GitLab、ブラウザ、社内システムへの足場が無い。
- 提案：connector レジストリ（connector.list/enable/configure）と、プロジェクトごとの MCP サーバー設定を protocol に入れる。権限は connector.gitlab.* のようなパターンにして grant と予算に乗せ、呼び出しは events に記録する。UI ではコネクタをアイコンのチップで出し、どの AI が何を使えるかを権限ポップオーバーに並べる。

### [medium] Orchestrator の繰り返しや暴走を daemon が検知しない

- 根拠：モックの Orchestrator が同じ最終報告と recordDecision を約2.6秒ごとに繰り返しても、daemon は止めない。止まるのは maxTurns=80 に達したときだけ（32、62。チャットとタイムラインが同じ内容で埋まる）。concept 11 の「同じ失敗を繰り返した場合の停止・相談」が実装されていない。
- 提案：daemon 側に繰り返し検知を入れる。同じツールと引数、または同じ本文が N 回続いたら Run を一時停止し、司令室に「繰り返しています」の要対応カードを出す（再開・停止・指示ボタン付き）。

### [low] Orchestrator が1プロジェクトに固定され、プロジェクト必須

- 根拠：grant.ts の grantOrchestration は projectId が無いと invalidParams を返し、scope を1プロジェクトに固定する。そのためプロジェクトの無い文章チャットでは、ダイアログがコーディングリポジトリ acme-web を既定で選び、ローカルパスまで表示する（24）。複数プロジェクトをまたぐ監督（毎朝の全体確認など）ができない。
- 提案：プロジェクト無しの Orchestrator を許す（チャット Worker だけを起動できる）。対象は会話の文脈から推定し、推定できなければ空のまま「選んでください」にする。複数プロジェクトの scope も選べるようにし、ローカルパスはダイアログに出さない。
